# Emitter coverage for every §3-facing number

**Read this before the freeze, not after.** It is written *before* the tag is cut, on purpose:
ROADMAP criterion 5 asks that every §3-facing number have a generating emitter in the frozen code,
and the remedy for a missing emitter is **to add one** (D-18). After the sha is frozen an emitter
cannot be added without re-cutting the tag, and by Phase 29 it is too late entirely. A coverage
walk assembled after the run records what the run happened to produce; this one records what the
code is *obliged* to produce.

This is a **report, not a gate** (D-16). Its input — `numbers-ledger.tsv` — lives outside this
repository and is the author's to edit, which is precisely the shape plan 23-02 warned about: a
verification gate that cannot pass is worse than no gate. The ledger is **read-only from this
repo**; nothing here was written back to it.

Scope: the ledger's **131 rows / 27 distinct artifacts** (78 `KEEP-VERIFIED`, 46 `EDIT`, 7
`KEEP-FROZEN-5f`). Ledger rows are cited by `id` only — never by their `current_text` or
`target_text` — because this file becomes public when the frozen branch is pushed.

## 2. An emitter existing does not make the number right

**This report proves wiring, never correctness.** A `file:line` in the table below establishes one
thing only: that a run of the frozen code is obliged to write that artifact. It says nothing about
whether the value inside it is the value the manuscript should quote, whether the seed band is
wide enough to support the claim, or whether the derivation in the ledger's `derivation` column
selects the right rows.

The repository already states the general form of this in `EXPECTATIONS.md` §4 — *existence and
row count are not correctness*. The emitter-specific form is sharper, because an emitter is even
weaker evidence than a green completeness gate: a completeness gate at least confirms the file
appeared. **A `file:line` here confirms only that the code intends to write it.**

Three consequences worth stating explicitly:

- A **NO EMITTER count of 0 does not close §3.** It closes criterion 5, which is a traceability
  criterion. Accuracy remains Phase 29's problem.
- **`EMITTER-BACKED, NOT REGENERATED` is not a weaker grade of backing.** Those rows are
  deliberately frozen provenance (§5), and re-deriving them would be the defect, not the fix.
- **The `derivation` column is not verified here.** Where the ledger states a derivation
  (`file=...;filter=...;value=...;report=...`), this walk confirms the named `file` is emitted. It
  does not confirm the filter selects the intended rows.

### Notes on the marked rows

**† `real_rig_metrics.json` — 16 rows, but 7 of them are frozen.** Nine rows are `KEEP-VERIFIED`

**‡ `diagnostics.json` — a KNOWN, DELIBERATELY-DEFERRED gate-coverage hole.** *(Author ruling,

The library writes it on every calibration run — `save_diagnostic_report` at

**What is missing is gate coverage, not the number.** The two rows on it (`RL-pnp-rejected`,
`RL-pnp-translation`) are emitter-backed and regenerate correctly; what no completeness gate will
notice is if they *fail* to. Reading them means going to the production run's own `output_dir` by

**Deliberately not fixed in the freeze window.** Adding a copy-out to `experiments/e2_real_rig.py`
was considered and declined: the freeze window is for defects that would cost the run, and this

**§ `linux32gb_scope.json` has no emitter, and that is by design — THE ONE JUDGEMENT CALL IN THIS
DOCUMENT.** *(Author ruling, 2026-08-19: the grade STANDS. Criterion 5 closes as it is; the freeze

It is the `results_linux32gb/` tree's scope and confound-control statement, hand-written to be read
*before* anything from that tree is cited. It records the machine and the two contributing shas
explicitly.

**Why the grade is EMITTER-BACKED, NOT REGENERATED and not NO EMITTER — stated explicitly, because
every other row in the table is mechanical and this one is not.** The distinction turns on *what a
number is traceable through*:

- **Every other EMITTER-BACKED row is traceable through code that writes the file itself.** Point
  at the artifact, follow the `file:line`, and you reach the write call that produced it.
- **This row is traceable through the neighbouring artifacts it quotes, not through any code that
  writes it.** Nothing in the frozen repository emits `linux32gb_scope.json`; a human assembled it.
  But its numeric claims are not free-standing assertions — each is a quotation from a committed
  artifact sitting beside it in the same tree, and each of *those* has a named emitter:
  `e2_cv413/` (`experiments/e2_real_rig.py:717`–`:759`), `e4/benchmark_grid.csv`
  (`experiments/e4_benchmark_grid.py:2156`), `e2_timing/` and `e2_memory/`
  (`src/aquacal/io/benchmark.py:568` via `src/aquacal/calibration/pipeline.py:1793`).
- **The tree is deliberately never re-run**, so "not regenerated" is the accurate second half of
  the grade rather than a concession.

Criterion 5's target is a number *hand-asserted with no artifact behind it*. This file is
hand-*written* but not hand-*asserted*: the artifacts behind it exist, are committed, and are
emitter-backed. That is why it is one indirection away from the rest of the table rather than
outside it — and it is still the first row to spot-check, because that indirection is a reader's
to accept, not a script's to prove.

## 5. The seven `KEEP-FROZEN-5f` rows

All seven name `real_rig_metrics.json`. They are **EMITTER-BACKED, NOT REGENERATED at the row
level**: the artifact is written by `experiments/e2_real_rig.py:740` and this run does produce a
fresh copy, but these seven values are deliberately held at their committed five-significant-figure
form rather than re-derived.

The reason is the **OpenCV 4.13 pin**. `pyproject.toml` hard-pins `opencv-python==4.13.*` because
4.14.0 detects 1.95% fewer corners and moves reconstruction RMSE by +7.8% on the published
real-rig dataset. The published numbers were produced under 4.13; the pin is what keeps them
reproducible. **Re-deriving them would be the defect, not the fix** — which is why the correct
grade is "not regenerated", not "unverified".

This intersects a live risk on the run target. Per D-26, the target's existing conda environment
carries **OpenCV 4.14.0** — exactly the version the pin exists to exclude. Plan 27-12 builds a new
environment at 4.13. **If that step slips, these seven rows are the first place it will show.**
