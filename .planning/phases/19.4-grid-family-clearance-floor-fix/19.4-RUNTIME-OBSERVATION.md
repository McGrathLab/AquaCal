# Observation for plan 19.4-10: E4 wall times moved by camera count, not uniformly

**Status: OBSERVATION, NOT A FINDING. Do not put a causal claim in the manuscript
or the response letter on this evidence.**

**Recorded:** 2026-08-05, mid-run (queue stage 3 of 8, HEAD `2a623f9`).
**Written but deliberately NOT committed while the queue is in flight** (D-19.4-16
rule 4). Commit it with the run's artifacts once all eight stages complete.

## Why this matters more than scheduling

E4 (`e4_benchmark_grid`) is the experiment whose per-cell
`seconds_stage3_interface_optimization`, `seconds_stage3_intrinsic_pass` and
`peak_bytes_*` columns **are** the published performance numbers answering
reviewer point **R1.5** ("runtime and memory consumption under configurations of
8/12/16 cameras and varying calibration frame counts"), and feeding **R3.2**.
A change in these numbers is a change in a published claim, not just a change in
how long the overnight queue takes.

| 13 | 200 | 1591.4 | 1591.4 | 1.00 | (E2 real_rig row — unchanged, not produced by this queue) |

**The 12-camera cells got FASTER; the 8- and 16-camera cells got 2-3x SLOWER.**

## Why this is not yet attributable

1. **n = 1.** These are single-run wall times on both sides. This project has a
   documented three-recurrence history of attributing pure noise before measuring
   a noise floor — once producing a decomposition of noise that nearly reached the
   manuscript. Runtime is among the noisiest quantities available.
2. **Every 200-frame cell reports `near_physical_ceiling`** at ~10-11 GB peak, in
   BOTH runs. Those cells are paging. A 2-3x swing on a paging workload can be
   scheduling luck rather than an algorithmic change.
3. **The structure is suggestive but not conclusive.** A uniform thermal or
   background-load cause would scale all cells together; this does not. It is
   organised by camera count, with the 12-camera baseline — the geometry E4's
   baseline cell and E6's baseline both use — improving while the off-baseline
   counts degrade. That is *consistent with* the interface fix changing
   conditioning differently per camera count, but consistent-with is not evidence.

Queue-level context, for calibration: e6_repeat1 took 167 min against a measured
estimate of 100, and e4 took 214 against 132.5 — roughly 1.6x on both. That
initially looked machine-level and uniform; the per-cell table above shows it is
not, which is what makes the question worth a real measurement.

## Proposed measurement (a follow-on, NOT this phase)

- Re-run **E4 alone, after a clean reboot**, with **2-3 repeats at the same seed**,
  to establish a wall-time noise floor. Without repeats, a 2x real effect and 2x
  jitter are indistinguishable.
- Watch the three `near_physical_ceiling` cells specifically. If a clean reboot
  moves those substantially while the `clean` cells barely move, the story is
  memory pressure — and the published runtimes are partly measuring this box's RAM
  ceiling rather than the method.
- Do NOT fold this into the current queue: re-running E4 mid-flight would violate
  the abort protocol and split the run's one-git-sha-per-artifact property.

## Cross-box option (user has access to a ~32 GB machine)

On a 32 GB box the same 11.3 GiB peak is ~35% of RAM and should classify `clean`.
That makes a cross-box run an attractive discriminator, with one caveat and two
ways around it:

**Caveat:** if the other box has a different CPU, comparing absolute wall times
confounds RAM with CPU and settles nothing.

1. **Categorical signal (box-independent):** does `memory_pressure` flip from
   `near_physical_ceiling` to `clean` on the three 200-frame cells? That is a
   threshold on peak-vs-total, not a timing comparison, so CPU differences do not
   enter.
2. **Within-box ratios (CPU-normalised):** compare each box's 200-frame time to
   *its own* 50-frame time at the same camera count. If this box's 200-frame cells
   are disproportionately slow against their own baseline and the 32 GB box's are
   not, that isolates memory pressure.

**Provenance decision this forces:** if published numbers come from two machines,
MF-08 and the response letter must state which box produced which number, and one
box should be chosen deliberately as the reference for published figures — not
whichever happened to run last.

## Sequencing decision (USER, 2026-08-05): debug here first, port later

**Decided:** continue all development and debugging on this box until `src` is
solid and fully debugged. Only then consider re-running on the ~32 GB box, and if
that happens, re-run the WHOLE suite there and take the paper's numbers from that
single machine.

This is the right order, and the reason is that **the inertness proof is a
same-box question.** SC-3 asks whether E1/E3/E5/E7 are unchanged *by the interface
fix*. Answering it requires holding everything constant and changing exactly one
thing. Re-running the suite on different hardware changes two things at once, and
any deviation becomes unattributable — fix, or machine?

Things that move numbers independently of this repo's code:

- **Library versions.** The `environment` block pins `numpy 2.4.2`,
  `scipy 1.17.0`, `opencv 4.13.0`, `python 3.12.12`. Different versions change
  numerics on their own.
- **BLAS threading.** `cpu_count_logical = 20` here. A different core count
  changes reduction order, hence summation order, hence the last bits — and on
  ill-conditioned solves that can exceed `--check`'s rtol.
- **Instruction set / CPU generation.** Different vectorization, different
  rounding paths.

Note `--check` compares float columns at a relative tolerance
(`compare_experiment_csv(..., rtol=...)`), not byte-exactly. That absorbs small
differences but does not make the cross-machine question safe.

**Why tonight's run is not wasted under this plan.** It is the CONTROL: same box,
same env, one variable changed (the fix). When the 32 GB run happens:

- *Everything matches within rtol* → use that box's numbers wholesale, with this
  run as corroboration that two machines agree. Best case.
- *Something deviates* → it is attributable to hardware/env **because** this
  control exists. Re-baseline there and re-anchor the inertness argument to that
  box.

Without the control, neither outcome is interpretable.

**Prerequisites before any 32 GB run** (do not skip, or the comparison is void):
reproduce the conda environment exactly, pin `OMP_NUM_THREADS`, and start from a
clean checkout at a known sha.
