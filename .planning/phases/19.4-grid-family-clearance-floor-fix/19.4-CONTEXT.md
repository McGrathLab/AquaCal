<domain>
## Phase Boundary

Every synthetic scenario models **one flat water surface shared by all cameras**, matching the
physical premise the method and the manuscript rest on. The per-camera *interface distance*
variation is preserved by moving it onto camera height, where it belongs. The three affected
experiments are re-measured; the three unaffected ones are **proven** unaffected.

**In scope:** `generate_camera_array`'s jitter (`synthetic.py:259`); the resulting re-derivation
of `GRID_DEPTH_RANGE`; a scenario-invariant test asserting one `water_z` per scenario; the
legality sweep; fail-fast; archiving pre-correction artifacts; the full seven-stage re-run plus
E7's 10-seed band; and updating MF-05 and MF-08.

**Out of scope:** `board_clearance_floor`'s `margin_factor`; the refractive model itself; E2
(real data, no synthetic scenario); Phase 17's per-camera interface *ablation mode*, which is a
legitimate **solver option** and is untouched — this phase changes only what the GROUND TRUTH
generates, never what the solver may fit.

**Explicitly in scope, and new: published numbers WILL move.** E4, E6 and E7 change. This is the
opposite of 19.3's constraint and of this phase's own earlier draft. The movement is the point.

</domain>

<decisions>
## Implementation Decisions

- **D-19.4-09: the jitter moves from `water_z` to `C_z`; the surface becomes one shared plane.**

  ```python
  delta   = 0.0 if i == 0 else rng.normal(0, height_variation)
  C_z     = -delta                    # camera height carries the variation
  water_z = height_above_water        # ONE plane, shared by every camera
  ```

  `h_c = water_z − C_z` is preserved **exactly** per camera (verified on all 12 at seed 42), so
  the modelling intent — cameras at slightly different distances from the surface — survives.
  What changes is that they now look through the *same* surface.

  **Why not simply set `height_variation = 0`:** it would remove the `C_z ↔ water_z` degeneracy
  that E7 exists to probe. With every camera at `C_z = 0` that degeneracy is artificial; with
  real height spread and one shared plane it is live, and E7 becomes a clean test — shared mode
  is the *correct* model, per-camera is over-parameterised.

  **Evidence this is a defect, not a design choice:** `Interface`'s own docstring
  (`interface_model.py:8-22`) says the value is *"the Z-coordinate of the water surface in world
  frame"* and that *"after optimization this is the same value (water_z) for all cameras."* The
  parameter is documented as *"Std dev of per-camera **height** variation."* The intent was
  camera height; the implementation moved the interface. Three of the five scenario sources
  already do it correctly.

- **D-19.4-10 (USER DECISION): archive before changing.** Pre-correction artifacts for E4, E6
  and E7 go to `experiments/archive/e{4,6,7}-2026-08-XX-pre-interface-fix/` with a provenance
  README matching `e2-2026-07-30-pre-pnp-guard/README.md`. Seven such archives already exist;
  this is the established convention, not a new one.

- **D-19.4-11 (USER DECISION, carried from the superseded draft): fail-fast.** The long runs
  abort on the FIRST cell/configuration recording `status="failed"`, **exit non-zero**, and print
  the configuration key, the exception, and — for a clearance rejection — both the supplied
  minimum and the derived floor. Opt-out must be explicit (`--no-fail-fast`), since 19.2-21
  pre-authorised E4's 16×200 cell to fail as a recorded row. Today's blanket `except Exception`
  records failures as rows and continues, which cost 74 and 84 min at seeds 47/50 while exiting 0.

- **D-19.4-12 (USER DECISION): keep per-scenario derivation, demoted to hygiene.** After the fix
  `max(water_zs) == height_above_water` at every seed, so the floor is genuinely seed-invariant
  and a module constant is *correct*. Deriving per-scenario is still better practice — it stays
  right if someone passes a different `height_above_water` — and costs nothing. It is no longer
  the phase's thesis. The helper lives in `experiments/e4_benchmark_grid.py` beside
  `default_xy_extent_for_layout`, and **takes `water_zs` as a parameter** rather than rebuilding
  an array internally (carried from the superseded D-19.4-07, whose reasoning still holds).

- **D-19.4-13 (USER DECISION): re-run the full seven-stage queue plus E7's 10-seed band.**
  Measured costs from 19.3's queue on this box under exclusivity:

  | stage | wall clock |
  |---|---|
  | e3 | 12 s |
  | e7 | 5.6 min |
  | e1 | 5.7 min |
  | e5 | 22.1 min |
  | e6 ×2 (determinism pair) | 196.0 min |
  | e4 | 132.5 min |
  | **full queue** | **6 h 02 min** |
  | E7 band, 9 further seeds (D-19.4-14) | + 50 min |
  | E1 band, 9 further seeds (D-19.4-14) | + 57 min |
  | E6 at seed 43, formerly-failing (D-19.4-15) | + 99.6 min |
  | **total** | **≈ 9 h 30 min — one overnight run** |

  **All seven stages run, not just the three that change.** E1, E3 and E5 must be *proven* inert
  by byte-comparison, not assumed — they cost 28 min of the 6 h and "airtight" means proof.
  E1 is inert by construction (`ideal` uses `height_variation=0.0`, so the corrected code reduces
  to `C_z = 0`, `water_z = height_above_water`); E3/E5 never call `generate_camera_array`.

  **E4 and E6 bands are deliberately NOT in this phase** — E6 ×10 is 16.6 h and E4 ×10 is 22.1 h,
  ≈39 h together. Neither carries an accuracy claim, so neither needs a band for the manuscript.
  Recorded in Deferred Ideas with its cost.

- **D-19.4-14 (USER DECISION): fold a `--seeds` mode into E1 and E7 so their bands are
  reproducible artifacts, not planning-document tables.**

  Today the bands are **not reproducible.** 19.3 produced them with ad-hoc harnesses writing to
  `seed_sweep_19_3/`, which is **gitignored** — the raw output does not survive a cleanup. What
  survives is summary tables in MF-08, which a reviewer must take on trust. That directly
  contradicts the standard this phase is held to: a reviewer re-runs and gets the same results.

  Both modules already carry the five-flag CLI contract (`--seed`, `--out`, `--force`, `--smoke`,
  `--check`). Add a plural `--seeds` that runs N seeds and emits a committed band CSV:

  | experiment | band artifact | size | why it is load-bearing |
  |---|---|---|---|
  | E7 | `interface_ablation_band.csv` | 10 × 48 = 480 rows | MF-05's per-arm bands; **the milestone's only surviving accuracy claim** |
  | E1 | `exp1_band.csv` (name at implementer's discretion) | 10 × per-depth rows | the 97–178x ratio spread and the "2 of 10 seeds exceed 2 mm" finding, both cited in MF-08 |

  `--seed 42` remains the default so the existing production artifacts and CLI contract are
  untouched. The seed list is recorded in each experiment's `*_provenance.json`.

  **E4 and E6 do NOT get this** in the same phase — their bands cost ≈39 h and neither carries an
  accuracy claim. The `--seeds` mechanism should be written so adding them later is configuration,
  not new code.

- **D-19.4-15: E6's seed-locking is cured BY the interface fix — verified, not assumed.**

  With `water_z` shared, `max(water_zs) == height_above_water` exactly, at every seed and every
  camera count. Measured over **3,000 draws** (500 seeds × {8,12,16} cameras × calibration and
  holdout): **exactly one distinct derived floor, 1.176215948246.** The guard cannot fire.

  `GRID_DEPTH_RANGE[0]` must be re-derived from 1.181852154 to **1.176215948** — a drop of
  5.636 mm, which is exactly cam7's seed-42 jitter, the camera whose water surface sat deepest.
  The old constant was anchored on `max(water_zs) = 1.031 + 5.636 mm`.

  **Consequence for verification:** the earlier rationale for running E6 at seed 43 — "the
  raised-floor path has never been run" — **no longer applies**, because post-fix there is no
  raised-floor path; the floor is identical at every seed. A seed-43 run is now a general
  robustness check rather than a targeted proof. Retained anyway (see D-19.4-13) because E6's
  brokenness is this phase's origin and demonstrating it completes at a formerly-failing seed is
  the end-to-end evidence that the origin defect is gone.

- **D-19.4-16 (USER CONCERN, 2026-08-04): the queue runs RISK-FIRST, not cheapest-first, and a
  src bug means abort-and-restart — never a midstream edit.**

  19.3's queue ran cheapest-first, which optimises for "most stages finished" rather than
  "earliest signal on the riskiest path". Cumulative start times under that order: e6 at 33.6 min
  but **e4 at 230 min** — and with the new band stages inserted, later still. E4 is arguably the
  highest-risk stage: it is the only one exercising the `n_cameras` axis, it carries the
  **10.26 GiB** peak on its 16-camera cells, and it is 132.5 min of exposure.

  **Required order:**

  | # | stage | completes at |
  |---|---|---|
  | 1 | e6 repeat1 | ~100 min |
  | 2 | **e4** | **~232 min** |
  | 3 | e6 repeat2 | ~328 min |
  | 4 | e6 seed 43 | ~428 min |
  | 5 | e7 + band | ~484 min |
  | 6 | e1 + band | ~547 min |
  | 7 | e5, then e3 | ~569 min (9 h 30) |

  Both high-risk stages complete inside 4 h instead of 6. Same total wall clock.

  **The abort protocol is pre-committed so it is not decided mid-run:**

  1. A src defect discovered at any stage → **abort the queue, fix, restart from stage 1.**
  2. **NEVER edit `src/` or `experiments/` while the queue is in flight.** 19.3's run holds one
     git sha across every artifact; a midstream edit destroys that silently and yields a result
     set assembled from two different trees. That is unreportable, and the damage is invisible
     until someone diffs provenance.
  3. Each stage records its git sha; a cross-stage sha mismatch is a **hard failure**, not a
     warning.
  4. Commit nothing while the queue runs — per-cell `git rev-parse` would split an artifact's
     recorded sha across the boundary (`.planning/knowledge-base.md`).

  **Front-loading risk is what makes rule 1 affordable.** Restarting after 100 minutes is a
  nuisance; restarting after 400 is how people talk themselves into the midstream edit.

  **The cheap-gate ladder still runs first** and catches the scenario-construction class before
  any production stage: legality sweep (13,500 scenarios, ~8 s), bit-inertness (~10 s), E6
  `--smoke` (5–10 min), full unit suite (~25 min). What it cannot catch is convergence or memory
  behaviour at production scale — which is precisely what this reordering is for.

### Constraints inherited and NOT reopened

- `board_clearance_floor`'s `margin_factor` is not touched.
- The library stays camera-agnostic; validation derives from input data, never assumed hardware.
- E6 records a per-configuration failure as a row, so an all-failed run exits 0 today. Check
  `status` counts, never the exit code. D-19.4-11 changes this; the habit stands regardless.
- Never quote an optimality figure beyond one significant figure.

### Blocking anti-patterns — carried from 19.3, all still binding

| # | Anti-pattern | severity | mechanism in this phase |
|---|---|---|---|
| 1 | Merging 19.2's `worktree-agent-a1a99b5a5289e9e05` | **blocking** | nothing here touches worktrees |
| 2 | Judging convergence by reprojection RMS | **blocking** | optimality and guard count are the discriminators |
| 3 | Relaxing a determinism / byte-identity gate to make it pass | **blocking** | the inertness gates are on E1/E3/E5, where inertness is *expected*. If one fails, the FIX moves — never the tolerance |
| 4 | Concluding a fix works from a low frame count | **blocking** | all acceptance runs at production frame counts; `--smoke` is not proof |
| 5 | Tuning `k` to make a failing case pass | **blocking** | `margin_factor` out of scope |
| 6 | Letting a subagent background a long run and return | warning | every executor prompt states foreground-only and names what it must not run; claims verified against git, never return text |
| 7 | **Treating a single-seed difference as a real effect** | **blocking** | **applies to this phase's own headline.** The 1.42 px figure is ONE seed, ONE trajectory. Enough to establish the defect is real and dominant; **not** enough to quote as "the effect size" anywhere near the manuscript |
