### Pattern 1: Cross-module grid-family helper (the layer recommendation)

**What:** Add one function to `experiments/e4_benchmark_grid.py`, e.g.
`grid_effective_depth_range(water_zs: Mapping[str, float], extent_factor: float = 1.0) -> tuple[float, float]`,
that computes `max(GRID_DEPTH_RANGE[0], board_clearance_floor(GRID_BOARD_CONFIG, water_zs, 15.0))`
as the floor and resolves the ceiling from `extent_factor` (default 1.0 reproduces
`GRID_DEPTH_RANGE[1]` exactly at seed 42, matching D-19.4-02's inertness requirement).
`e6_generalization_sweep.py` imports it exactly as it already imports `default_xy_extent_for_layout`.

**When to use:** Every grid-family scenario construction site — `build_grid_scenario`'s own
`depth_range=None` fallback (e4:589), `run_grid_cell`'s two calls (e4:744, 806 — these already go
through `build_grid_scenario`, so fixing 589 alone fixes them, confirmed by reading `run_grid_cell`
this session: it calls `build_grid_scenario(n_cameras, n_frames, seed)` with no explicit
`depth_range`, so it inherits whatever `build_grid_scenario`'s default resolves to), and E6's
`_scaled_depth_range`/`SCALE_AXIS_VALUES` (e6:147-180), which currently hardcodes
`floor = GRID_DEPTH_RANGE[0]` at import time — this is the same defect class as the main one and
must be re-derived per scenario, not just per-seed at import.

**Existing precedent this pattern extends, verified by reading it in full this session
(`default_xy_extent_for_layout`, e4:462-484):**
```python
# Source: experiments/e4_benchmark_grid.py:462-484 (read in full this session)
def default_xy_extent_for_layout(n_cameras: int, layout: str, spacing: float) -> float:
    """Convenience wrapper: D-28's derived `xy_extent` from
    `(n_cameras, layout, spacing)` alone, without building a full scenario.

    Used by E6 to derive its scale axis from E4's geometry constants rather
    than hardcoding a second copy (D-28). Camera XY positions do not depend
    on `seed` -- only per-camera roll and height jitter do
    (`generate_camera_array`) -- so any seed value yields the same span;
    `seed=0` is used here for clarity, not reproducibility.
    """
    _, extrinsics, _ = generate_camera_array(
        n_cameras=n_cameras, layout=layout, spacing=spacing, seed=0
    )
    camera_positions = {cam: ext.C for cam, ext in extrinsics.items()}
    return _default_xy_extent(camera_positions)
```
This function already solves "E6 needs a grid-family quantity without hardcoding a second copy"
for `xy_extent`. `depth_range` needs the identical treatment. **Important asymmetry, verified this
session:** `default_xy_extent_for_layout` is safe to call with a fixed `seed=0` because XY span is
seed-invariant (only height/roll jitter is seeded — confirmed by its own docstring). A depth-range
helper does NOT have this property — `max(water_zs)` IS the seed-dependent quantity the whole
defect is about — so the new helper must take `water_zs` as a parameter from the caller's own
already-constructed scenario, never re-derive its own camera array internally the way
`default_xy_extent_for_layout` does. This is the one respect in which the two helpers must NOT be
symmetric; flagging it because the surface-level similarity invites copying the wrong part of the
pattern.

### Pattern 2: `_e5_real_rig_depth_range` — the single-consumer version of the same idea

**What:** One function, called at both the calibration and holdout trajectory sites within the
same module, so both scenes are guaranteed to resolve the same way.
**When to use:** Reference implementation for the *shape* of the fix (one function, two call
sites, no drift). Not directly reusable — it is real-rig-specific (`generate_real_rig_array`
takes no seed at all) and private (`_`-prefixed, module-local), whereas the grid-family version
needs public-enough visibility for a second module to import it.
```python
# Source: experiments/e5_index_sensitivity.py:164-178 (read in full this session)
def _e5_real_rig_depth_range(water_zs: Mapping[str, float]) -> tuple[float, float]:
    """Single source of E5's `depth_range`, called at BOTH the calibration
    trajectory site and the held-out trajectory site (D-19.3-04).
    """
    return (
        board_clearance_floor(BOARD_CONFIG, water_zs, _E5_ROTATION_RANGE_DEG),
        2.0,
    )
```

### Anti-Patterns to Avoid

- **Re-deriving a camera array to get `water_zs`, instead of threading the one already built.**
  `build_grid_scenario` already computes `water_zs` at line 580 before it resolves
  `depth_range` at line 589 — the fix uses that value, it does not call `generate_camera_array`
  a second time. (This is what the diagnosis's fix snippet already does; noting it here only
  because `default_xy_extent_for_layout`'s seed=0 re-derivation pattern, immediately above it in
  the same file, is the wrong model to copy for this specific quantity — see Pattern 1's
  asymmetry note.)
- **Deleting `GRID_DEPTH_RANGE`.** D-19.4-02 is explicit: it is the lower bound of the `max()`
  and the thing that makes seed-42 inertness provable. Rename it (e.g.
  `GRID_DEPTH_RANGE_PUBLISHED_ANCHOR` or similar — naming is Claude's discretion per CONTEXT.md)
  but keep it as a real constant other code can reference.
- **Changing `_SCENARIO_IDENTITY_KEYS`'s key set.** D-19.4-03 already resolves this: keep
  recording the resolved absolute `depth_range` tuple in the checkpoint payload, not a factor.
  This means `_SCENARIO_IDENTITY_KEYS = ("n_cameras", "layout", "n_water", "depth_range",
  "xy_extent", "spacing", "normal_fixed")` (e6:595-603, read in full this session) needs NO
  change — only what populates the `"depth_range"` value inside the recorded `config` dict
  changes (from the SCALE_AXIS_VALUES literal to the resolved-at-construction-time tuple), and at
  seed 42 that resolved value is bit-identical to today's, so every one of the twelve committed
  `e6_configs/*.json` files still matches under `--check` with zero migration.

## Common Pitfalls

### Pitfall 1: Fixing only `build_grid_scenario`'s `depth_range=None` fallback and missing the scale axis

**What goes wrong:** `_scaled_depth_range` (e6:147-161) computes `floor = GRID_DEPTH_RANGE[0]`
and bakes it into `SCALE_AXIS_VALUES`' absolute tuples at import time — a SECOND frozen-constant
site with the same defect shape as the main one, but it passes an EXPLICIT `depth_range` (not
`None`), so it is invisible to a fix that only changes the `None`-fallback branch.
**Why it happens:** `_scaled_depth_range`'s docstring explicitly designs this as intentional
("keeping the floor itself fixed at GRID_DEPTH_RANGE[0] (D-19.3-07)... every scale value is legal
by construction: `factor=0.5` cannot violate the clearance requirement... because the floor never
moves") — the ORIGINAL design assumed the floor was seed-invariant, which was true only because
E6 had never been run at a non-42 seed until 19.3. This design intent must change along with the
fix, not survive it.
**How to avoid:** Already identified as call site #3 in the diagnosis's own table (`e6:160`). This
research confirms it independently by reading the current `SCALE_AXIS_VALUES` construction
(e6:164-180) and `test_e6_scale_axis_...` (test_experiments_e6.py:160-192, read in full this
session) — the test explicitly pins `half_depth_range[0] == pytest.approx(floor)` where
`floor = e4.GRID_DEPTH_RANGE[0]` (a fixed value), which will need to become
`floor = grid_effective_depth_range(water_zs)[0]` (a per-scenario value) after the fix. This test
IS the regression net that catches an incomplete fix — do not weaken it to pass, rewrite its
assertion to check the new per-scenario relationship.

### Pitfall 2: Treating `_BASELINE_EXTENT_ABOVE_FLOOR` as already-correct because it does not appear in the diagnosis's six-site table

**What goes wrong:** `_BASELINE_EXTENT_ABOVE_FLOOR = GRID_DEPTH_RANGE[1] - GRID_DEPTH_RANGE[0]`
(e6:141, read this session) is a module-level constant computed FROM the frozen `GRID_DEPTH_RANGE`
at import time. It is not itself independently seed-dependent (it is a difference of two
constants), so it will not raise or produce wrong legality — but it defines "the baseline extent"
used by `_scaled_depth_range`'s `factor * _BASELINE_EXTENT_ABOVE_FLOOR` term. Once the floor
becomes per-scenario, this constant's semantic (extent above THE published anchor) and the new
per-scenario floor (extent above THIS scenario's derived floor) are two different reference
points that must not be silently conflated.
**Why it happens:** It is not a bug today (no test fails, no scenario is illegal because of it)
so it is easy to leave unexamined. It is, however, a second consumer of `GRID_DEPTH_RANGE` beyond
the six sites the diagnosis names, and the fix's `_scaled_depth_range` rewrite touches it directly.
**How to avoid:** When rewriting `_scaled_depth_range` per Pitfall 1, re-derive what
"baseline extent above floor" means in the new design explicitly (it should almost certainly stay
anchored to the PUBLISHED anchor's extent, i.e. this constant's current definition can likely be
kept as-is — the extent shape is not the seed-dependent part, only the floor is) — but this
decision should be made deliberately during planning, not left as an unexamined survivor of the
old design. Flagging because a reader following only the diagnosis's six-row table could miss it.

## Checkpoint Identity Migration Precedent (Question 3)

**Precedent found:** `19.2-16-SUMMARY.md` (`.planning/phases/19.2-experiment-execution-and-provenance/19.2-16-SUMMARY.md`,
read in full this session) is the source of `_SCENARIO_IDENTITY_KEYS` and the `--check`
reconstitution guard (WR-03, T-19.2-63) that D-19.4-03 already cites. Two directly relevant facts,
confirmed by reading the summary:

1. **The narrowing precedent.** `_SCENARIO_IDENTITY_KEYS` itself is documented in
   `e6_generalization_sweep.py:584-594` (read this session) as a correction: comparing the FULL
   configuration identity (including label fields like `axis`, `axis_value`, `config_key`) once
   produced false mismatches, because those fields "only LABEL which row a configuration
   illustrates and do not change what gets computed." The fix was to narrow the compared set to
   only the fields that determine the scene. This is direct precedent for CONTEXT.md's own
   approach in D-19.4-03: narrow scope of what changes (keep `depth_range` in the identity, change
   only what value populates it) rather than widen the key set to accommodate a new payload shape.

2. **The exemption precedent.** 19.2-16's own decisions record: *"Checkpoints written before this
   plan (no 'config' key) are trusted, not flagged, by the WR-03 guard — the twelve committed
   `e6_configs/*.json` files are only regenerated in wave 4."* This establishes that this codebase
   has, at least once before, deliberately exempted pre-existing checkpoints from a stricter guard
   rather than forcing an immediate migration, and regenerated them in a LATER wave rather than the
   same one that introduced the guard.

**Does it apply here?** Only partially, and the planner should know why. 19.2-16's exemption
covered checkpoints missing a KEY that didn't exist yet (an additive schema change — old files
simply lacked a field the new guard checked for). This phase's situation is different: D-19.4-02
already guarantees BIT-IDENTICAL resolved values at seed 42, so — per D-19.4-03 — no exemption
