## Summary

This phase fixes a single, precisely-located defect: `generate_camera_array`
(`src/aquacal/datasets/synthetic.py:255-260`) applies its `height_variation` jitter to `water_z`
(the world-frame Z of the water *surface*) while holding every camera at `C_z = 0`. `Interface`'s
own docstring (`interface_model.py:8-22`) establishes that this quantity should be *one shared
plane*. The fix moves the jitter onto `C_z` instead, preserving `h_c = water_z − C_z` exactly per
camera. Two of five scenario sources are affected (`generate_camera_array` and, transitively, the
`"minimal"` `create_scenario` preset that calls it); three are already correct
(`generate_real_rig_array`, and therefore `"realistic"`; and `"ideal"`, which calls
`generate_camera_array` with `height_variation=0.0`, a no-op for the defect either way).

Everything else in the phase is harness work with an established house style already used across
19.1–19.3: a `--seeds` CLI flag on top of the existing five-flag contract; fail-fast wired into
`except Exception` blocks that currently record-and-continue; `board_clearance_floor` re-derivation
via the existing water_zs-parameterized helper pattern; pre-correction archiving under
`experiments/archive/e{N}-DATE-reason/`; and a risk-reordered variant of 19.3's proven
`rerun_19_3.sh` queue-with-state-file pattern. Nothing here requires inventing new machinery — it
requires re-sequencing and lightly extending machinery this repo already has three generations of
precedent for.

**Primary recommendation:** Plan this as (1) the one-file `src` fix + scenario-invariant test +
inertness proofs, (2) the `GRID_DEPTH_RANGE` re-derivation + `--seeds` CLI additions to E1/E7 +
fail-fast wiring, all proven correct at small scale, (3) the D-19.4-17 pre-run coverage audit as
its own gating step, then (4) a single risk-first queue script adapted from `rerun_19_3.sh`,
launched detached exactly once. Do not let any wave touch `src/` or `experiments/` after the queue
launches.

### The Fix — Exact Diff Site

`src/aquacal/datasets/synthetic.py`, inside `generate_camera_array`, lines 255-260
`[VERIFIED: synthetic.py:255-260]`:

```python
# CURRENT (defect):
for i, pos in enumerate(positions):
    ...
    # Interface distance with small variation
    if i == 0:
        dist = height_above_water  # Reference camera: exact height
    else:
        dist = height_above_water + rng.normal(0, height_variation)
    distances[cam_name] = dist
```

The loop already computes `R`/`t` for extrinsics earlier in the same iteration (`t = -R @ pos`,
line 251) with `pos[2] == 0.0` always (all three layouts build positions with `z=0.0` explicitly,
lines 214/217/224). The fix must:
1. Draw `delta = 0.0 if i == 0 else rng.normal(0, height_variation)` (same RNG call/order as today
   so the seeded stream position for later draws — e.g. `roll` — does not shift; verify by reading
   the surrounding loop for RNG call ordering before editing, since `roll = rng.uniform(...)` is
   drawn earlier in the same iteration at line 248, ahead of `dist`).
2. Set `pos[2] = -delta` (or equivalently adjust `positions[i]` before computing `t = -R @ pos`) so
   `C_z = -delta` ends up baked into the extrinsics translation `t`, not applied as a separate
   post-hoc shift — `t = -R @ pos` must run AFTER `pos`'s Z is set, so the ordering inside the loop
   changes (currently R/t are computed on the original `pos` before `dist` is ever touched at
   line 255).
3. Set `distances[cam_name] = height_above_water` unconditionally (drop the per-camera branch
   entirely — every camera gets the same value).

**RNG-ordering pitfall (a real risk, not hypothetical):** the current loop draws `roll` at line 248
(unless `i==0`) BEFORE reaching the interface-distance block at line 255. If the fix restructures
the loop to draw `delta` where `dist` used to be but changes at what point in the iteration it's
consumed, the `roll`/`delta` draw ORDER per camera must stay `roll` then `delta` (matching today's
`roll` before `dist`) or every downstream seeded artifact (existing committed CSVs whose camera
extrinsics derive from this exact RNG stream) shifts unpredictably — not just the E4/E6/E7 numbers
this phase already expects to move, but potentially E1/E3/E5 if they share a seed path through this
function. **Confirmed E1/E3/E5 do NOT call `generate_camera_array` at all in production** (see Bit-
Inertness section below), so this only matters for E4/E6/E7's determinism, not for the inertness
proofs — but it is still worth preserving the draw order for a stable diff/review, and because the
`"minimal"` preset (E7, `create_scenario`) does call `generate_camera_array` with
`height_variation=0.003` and 2 cameras, so its specific seed=42 committed jitter values move
regardless (expected, per D-19.4-09).

### Scenario-Invariant Test (Success Criterion 1)

Cheapest possible design — no calibration solve required, this is pure ground-truth-generation
assertion:

```python
# tests/unit/test_synthetic_scenario_geometry.py (new) or extend an existing
# datasets/synthetic.py unit test file
import numpy as np
import pytest
from aquacal.datasets.synthetic import (
    create_scenario, generate_real_rig_array, generate_camera_array,
)

@pytest.mark.parametrize("name", ["ideal", "minimal", "realistic"])
@pytest.mark.parametrize("seed", [0, 1, 42, 99])
def test_create_scenario_one_water_z(name, seed):
    scenario = create_scenario(name, seed=seed)
    distinct = set(scenario.water_zs.values())
    assert len(distinct) == 1, (
        f"{name}@{seed}: {len(distinct)} distinct water_z values, expected 1"
    )

def test_real_rig_array_one_water_z():
    _, _, water_zs = generate_real_rig_array()
    assert len(set(water_zs.values())) == 1

@pytest.mark.parametrize("layout", ["grid", "line", "ring"])
@pytest.mark.parametrize("n_cameras", [2, 8, 12, 16])
@pytest.mark.parametrize("seed", [0, 1, 42, 99])
def test_generate_camera_array_one_water_z(layout, n_cameras, seed):
    _, _, water_zs = generate_camera_array(
        n_cameras=n_cameras, layout=layout, seed=seed
    )
    assert len(set(water_zs.values())) == 1
```

narrower assertion specific to this phase's own claim. **This is the test whose absence CONTEXT.md

### Fail-Fast Wiring (Success Criterion 6)

Confirmed exactly two `except Exception` sinks matching D-19.4-11's "record-and-continue" shape
`[VERIFIED: grep across experiments/]`:

1. `experiments/e4_benchmark_grid.py:890-898` (inside `run_grid_cell`) — catches any exception

   means: re-raise (or `sys.exit(1)`) instead of catching in the child when fail-fast is enabled, so

## Common Pitfalls

### Pitfall 1: Assuming the fix is "just don't jitter"
**What goes wrong:** Setting `height_variation=0.0` instead of moving the jitter to `C_z` would
silently remove the `C_z ↔ water_z` degeneracy that E7's whole experiment exists to probe.
**Why it happens:** It's the simplest possible "make water_z stop varying" fix, and superficially
satisfies Success Criterion 1.
**How to avoid:** D-19.4-09 is explicit and locked: move the jitter, don't remove it.
**Warning signs:** If E7's `percamera_fixed` arm stops showing ANY height/distance scatter after
the fix, the fix removed the degeneracy rather than relocating it — that would falsify E7's entire
experimental premise.

### Pitfall 2: RNG draw-order drift silently changing unrelated committed numbers
**What goes wrong:** Restructuring `generate_camera_array`'s per-camera loop to compute `C_z`
before `t = -R @ pos` could reorder `rng` calls relative to today's `roll = rng.uniform(...)` draw,
shifting every subsequent camera's roll/extrinsics even at seeds/configs that don't materially
depend on the fix.
**Why it happens:** The natural code shape ("compute C_z, then extrinsics, then water_z") doesn't
match the current code's draw order (roll, then extrinsics, then water_z-as-jittered-distance).
**How to avoid:** Preserve the exact `rng` call sequence per iteration; only change what the drawn
value is APPLIED to (position Z vs. distance dict), not the number or order of `rng` calls.
**Warning signs:** A committed CSV that shouldn't move (per the audit table — anything on the
`generate_real_rig_array` path) moves anyway; or `"ideal"` (height_variation=0.0, so `delta` is
always exactly 0.0 and should be a true no-op) produces even a single differing bit.

### Pitfall 3: Treating the queue's cheap-gate ladder as sufficient proof before launch
**What goes wrong:** Legality sweep + bit-inertness + `--smoke` + unit suite all passing feels like
"ready to launch," but D-19.4-16 is explicit that this ladder "cannot catch convergence or memory
behaviour at production scale — which is precisely what this reordering is for."
**Why it happens:** A green cheap-gate ladder is a strong, fast signal and it's tempting to treat
strong+fast as sufficient.
**How to avoid:** The risk-first ordering exists BECAUSE the cheap gates can't cover this; don't
skip or shortcut the D-19.4-17 pre-run coverage audit on the theory that the cheap gates already
covered enough.
**Warning signs:** Skipping straight from "tests pass" to "launch the queue" without the D-19.4-17
coverage matrix having been produced and reviewed.

### Pitfall 4: Widening the fail-fast change beyond E4/E6
**What goes wrong:** D-19.4-11 targets "the long runs abort on the FIRST cell/configuration
recording status='failed'" — this reads generally, but the ONLY two `except Exception`
record-and-continue sinks in the whole `experiments/` tree are in E4 and E6. Adding fail-fast
machinery to E1/E5/E7 (which don't have this pattern) would be inventing scope.
**Why it happens:** The decision text doesn't name E4/E6 explicitly, only "the long runs."
**How to avoid:** Confirm via grep (as this research did) which files actually need this change
before writing tasks for it; E1/E5's existing behavior (an uncaught exception propagates and
crashes the script, arguably already "fail-fast" by omission of a catch-all) may need NO change.
