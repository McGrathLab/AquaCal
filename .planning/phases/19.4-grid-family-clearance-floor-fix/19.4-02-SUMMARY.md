# Phase 19.4 Plan 02: Relocate generate_camera_array's jitter from water_z to C_z Summary

**Moved `generate_camera_array`'s per-camera `height_variation` jitter from the water surface (`water_z`) onto camera height (`C_z`), so every synthetic scenario models one flat interface shared by all cameras, with `h_c = water_z - C_z` preserved exactly and proven by an independent RNG-stream replay.**

## Decisions Made
- Implemented D-19.4-09 exactly as specified in CONTEXT.md, with no deviation on the jitter-relocation mechanics.
- Regenerated `discard_anchor.json` rather than treating `test_matches_frozen_anchor`'s failure as a defect: this fixture has an established precedent (D-19.3-09) of being regenerated whenever an intentional, documented geometry-default change moves the "minimal" preset's calibrated output. The blocking anti-pattern against relaxing inertness/determinism gates does not apply here -- this is not one of the E1/E3/E5 cross-run bit-inertness proofs the anti-pattern names; it is a frozen numerical anchor explicitly designed to move under intentional scenario-construction changes (see its own docstring history).
- Narrowed `test_run_grid_cell_holdout_matches_calibration_geometry`'s camera-position assertion to XY only. Investigated `run_grid_cell`'s actual data flow first: the holdout scenario's own extrinsics are discarded (only its `board_poses` are used, paired with the calibration scenario's own camera geometry -- see the source comment at `experiments/e4_benchmark_grid.py:796-804`), and `xy_extent` derivation (`_default_xy_extent`) depends only on XY span. Z divergence between differently-seeded internal `generate_camera_array` calls is therefore real (not floating-point noise, unlike before) but functionally inert.

## Issues Encountered

**Tool-timeout-forced backgrounding of the full suite run.** The environment's Bash tool hard-caps any single invocation at 600s regardless of the requested `timeout` value, but the unfiltered suite takes ~25-51 min. Every full-suite invocation was therefore moved to background by the tool itself, not by choice. This was handled by launching an `until grep -Eq "passed|failed" ...; do sleep 10; done` polling loop via `run_in_background: true` after each 600s auto-background event, and reading the actual pytest output file directly once the loop signaled completion -- never trusting a summary or partial read as a substitute for the real `N passed, M failed` line. The suite was run to genuine completion twice (once before Task 3's repairs, confirming exactly 3 failures with two independent runs agreeing on the same 3; once after, confirming 0 failures), consistent with CLAUDE.md's directive to verify against real output, not return text.
