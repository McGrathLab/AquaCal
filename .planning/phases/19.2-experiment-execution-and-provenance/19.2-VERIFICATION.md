### Assessment of the SEEDLESS_LEGACY_RECORDS carve-out

This was a specific focus of the review and it holds up. The carve-out is exactly scoped and actively defended, not a quiet exemption:

- Exactly six members, all named, all Phase-19.1 records that genuinely predate `solver_config["seed"]`.
- `test_seedless_carve_out_is_exact` asserts each member exists on disk **and still genuinely lacks a seed** — so the exemption self-destructs the moment a record is regenerated with one.
- `test_seedless_carve_out_has_exactly_six_members_and_excludes_e2` pins the cardinality and explicitly asserts E2's `benchmark.json` is not a member.
- `test_e1_and_e7_records_already_comply_on_environment` keeps the six under the environment check even though they are exempt from the seed check — the carve-out is one field wide, not blanket.

The provenance test is a real gate, not a decorative one. Its weakness is not the carve-out — it is that `test_new_phase_csvs_carry_a_seed_column` is the *only* coverage E5/E6 receive, and it checks one field of four.

### Gaps Summary

Four of the six ROADMAP success criteria are cleanly met, and the experimental content is strong: E3's three CSVs are complete and self-checking, E4's ten-row grid is fully populated with per-cell provenance and a mechanically asserted one-machine constraint, E5's band and E6's three axes are present with the correct tidy schema, and E6's baseline reproduces E4's 12×100 cell to the last digit. The README provenance table is genuinely complete. The full fast suite is green at 1033 passed with a clean tree and every artifact tracked.

The phase fails on the two things it exists to guarantee.

**First, EXP-11 is not met.** Its wording is specific — seed, AquaCal version, git SHA, *and* environment, for every committed result across E1–E7. E5 and E6 carry the seed and nothing else. This is not a subtle omission that grep had to infer: neither script imports any of the three provenance helpers the other experiments use, so no version, SHA, or environment block was ever captured for them, and the twelve `e6_configs` checkpoints carry no `schema_version` and are consequently invisible to every check in the provenance test. The mechanical gate does not catch this because the one test covering those two files checks only for a `seed` column, and both the test docstring and the README narrate that narrow check in language that reads like full coverage — the README even opens the section with a universal claim ("Every committed result … carrying its seed, AquaCal version, git SHA, and the Python/NumPy/SciPy/OS environment") that the same paragraph then quietly contradicts. This is exactly the failure mode the phase was meant to eliminate: a provenance claim that is true of most artifacts, asserted as if true of all.

**Second, the goal's traceability clause fails on `newton_iterations.csv`.** The file traces to one script and one output file, but the number it publishes is not the number it says it is. The producing diagnostic's docstring affirmatively claims to measure "the shipped projection path used inside every residual evaluation"; the residual evaluation in `_optim_common.py:635` runs a different, separately inlined Newton loop with a whole-array termination rule and no per-point convergence flag. The committed `n_not_converged=0` column is therefore a property of a loop the optimizer never executes. Provenance that points at the wrong implementation is worse than absent provenance, because it is citable.

Neither gap is deferred: no later milestone phase (20 Refractive Index Helper, 21 Documentation & Dataset Refresh, 22 Release Cut) mentions provenance backfill or Newton-path unification.

Two warnings do not block but should travel with the gaps: E4's resume path nulls the metrics of already-complete cells (review CR-01, confirmed in source — the committed grid is unaffected because every row is `ok`, but the documented resumability story does not work), and `.planning/REQUIREMENTS.md` still marks EXP-07/09/10/11 as `Pending` while the phase is recorded 14/14 Complete.
