`layout=line` failed at the full 12-camera/100-frame production scale. This is **not** the anticipated `ConnectivityError: No frames with 2+ cameras detecting the board` text observed for `scale_half_scale` in plan 10's smoke run -- it is a bare `KeyError` referencing a specific camera name. Classified as "something else" per the plan's own read-first guidance, rather than confirmed as the anticipated pose-graph connectivity failure mode; a line topology at 12 cameras plausibly still produces disconnected/partial coverage for the farthest camera, and this error is consistent with (but not verified equal to) a downstream symptom of that disconnection. Per the plan's explicit instruction, this configuration was recorded as `status=failed` with its `status_reason`, was **not** dropped, **not** retried at a different camera count, and the axis was **not** narrowed. The root cause was not further chased inside this production-run plan, since `experiments/e6_generalization_sweep.py` and its dependencies (shared library / E4's `build_grid_scenario` generator) were not modified and this plan's scope is measurement, not remediation -- this is worth flagging to the orchestrator as a candidate follow-up investigation, not a fix applied here.

`scale_half_scale` **did not fail in the production run**, unlike the smoke run (which failed at only 8 frames with a `ConnectivityError`). At the full 100-frame count it converged to `status=ok`, using 37 of the possible frames for held-out scoring, with metrics in a normal range (0.71 px reprojection RMS, 0.17 mm reconstruction RMSE) -- the plan 10 summary anticipated this exact resolution ("the `scale_half_scale` connectivity failure observed at smoke-mode's reduced 8-frame count should not recur at the full sweep's 100 frames").

`scale_double_scale` reported `status="ok"` (no exception raised, `exit_code`-equivalent success) but with catastrophically degraded metrics: reprojection RMS of ~1536 px and reconstruction RMSE of ~1.33 million mm are consistent with a divergent optimizer solution rather than a genuine, physically-sane calibration at 2x rig+tank scale. This is recorded **as measured**, without a verdict, threshold, or re-run at different scope, per D-12 -- it is a real, bounded characterization that the generalization sweep's scale axis breaks down (in a divergence sense, not merely gradual accuracy loss) somewhere between 1x and 2x scale, and the manuscript must characterize it as such rather than smoothing it into a small delta.

### `--check` result

Run (not skipped): before running, `_run_check`'s source was read and confirmed to reconstitute rows exclusively from existing `e6_configs/*.json` checkpoints and never re-run a configuration -- so it was safe to run in the foreground rather than risk another ~33 min re-run.

**Exit code: 1.** Worst offending cell: `key={'axis': 'index', 'axis_value': '1.333'} column='status_reason' committed=nan fresh=''`. 13 of 14 cells mismatched, all on the same `status_reason` column. This is the same class of defect 19.2-09 documented and partially fixed in `experiments/_io.py`'s `compare_experiment_csv` (an all/mostly-empty-string column round-trips through CSV as float-dtype `NaN`): the 09 fix prevents the crash, but a `NaN` vs `''` value is still not byte-identical under the comparator's non-float exact-compare path, so a nonzero `--check` exit persists as an inherent property of this column shape rather than evidence the 14 configurations fail to reproduce. Not treated as a data defect and not further chased, consistent with 19.2-09's own documented caveat about `--check` false negatives on structurally-unrecoverable columns.
