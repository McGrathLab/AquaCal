## Implementation Decisions

### E4 — the benchmark grid substrate (EXP-08)

- **D-01 — E4 is a direct-call synthetic grid, not a real-config sweep.** The relocated
  `experiments/e4_benchmark_grid.py::run_sweep` subsamples a *real* 13-camera YAML and calls
  `run_calibration_from_config`. That cannot satisfy EXP-08: a real run is 48–87 min (nine of
  them is days of wall-clock against a 2026-08-21 deadline), and **16 cameras is unreachable
  from a 13-camera rig**. Rewrite the module around
  `generate_camera_array` + `generate_board_trajectory` -> `calibrate_synthetic` ->
  `assemble_benchmark_record` — the exact D-09 path E1 and E7 already run in production.

  **A third option was ruled out by inspection, not by preference:** running synthetic data
  through the real pipeline so `benchmark.json` would be pipeline-written. Verified —
  `run_calibration_from_config` (`pipeline.py:766`) starts from videos/framesets and has **no
  precomputed-detection entry point**, so this would mean rendering synthetic images. Do not
  reopen it.

  Note the consequence for EXP-08's wording ("reporting only what `benchmark.json` recorded"):
  for the nine synthetic cells the record is *assembled* by the experiment from library-supplied
  blocks, not written by the pipeline. That is still "recording, not recomputing" — D-09's
  established reading — but D-02 makes it visible rather than implicit.

- **D-02 — `benchmark_grid.csv` carries `timing_scope` and `record_source` on every row.**
  `timing_scope` ∈ {`optimization_only`, `end_to_end`}; `record_source` ∈ {`assembled`,
  `pipeline`}. The nine synthetic cells are Stage 2 + Stage 3 only; E2's tenth row is
  end-to-end (detection + Stage 1 + Stage 2 + Stage 3). The LaTeX fragment renders the
  real-rig row **in its own labeled block, not as a tenth point on the scaling curve** — nine
  comparable points draw the curve; the real row anchors it to reality and answers R3.2's
  13-camera wall-clock question separately.

- **D-03 — One scene family; only the two swept variables change.** All nine cells use
  `generate_camera_array(layout="grid")` at fixed noise (0.5 px), fixed board, fixed working
  distance, varying only `n_cameras` ∈ {8, 12, 16} and `n_frames` ∈ {50, 100, 200}.

  **AMENDED 2026-07-28 after research — the original "matches `create_scenario('realistic')`
  exactly" clause was IMPOSSIBLE and is withdrawn.** Verified: `create_scenario("realistic")`
  calls `generate_real_rig_array()` (`synthetic.py:761`), a **fixed 12-camera real-rig layout
  with no `n_cameras` and no `layout` parameter** — a different generator entirely from
  `generate_camera_array`. E4 has no choice in the matter: 8- and 16-camera arrays exist nowhere
  but `generate_camera_array`, so the grid family is forced. The 12-camera cell is therefore a
  grid-family scene like the other eight, **not** `realistic`.

  The cross-experiment anchor moves accordingly: **E4's 12-camera cell and E6's baseline are the
  same grid-family scene** (see the amended D-11). E1 and E5 share the *other* anchor — both run
  on `generate_real_rig_array` geometry, since that is what `realistic` is. Two reference scenes,
  each shared by two experiments, rather than one shared by three.

- **D-04 — Every declared cell emits a row unconditionally, with `status` and `status_reason`.**
  `status` ∈ {`ok`, `failed`, `skipped_existing`}; metric columns are null when not `ok`. Nine
  declared cells always produce nine rows, so a coverage gap is countable rather than invisible.
  This is P4 ("the grid is data, not control flow") enforced in the artifact rather than in a
  log line. Note the concrete risk this guards: the 16-camera / 200-frame cell may not fit
  16.9 GB (see D-05).

### E4 — hardware and memory (EXP-08, R1.5, R3.2)

- **D-05 — The paper's hardware spec is this machine, already recorded.** From E2's committed
  `experiments/results/benchmark.json`: Intel64 Family 6 Model 154 (20 logical cores),
  16,857,190,400 bytes RAM, Windows 11, Python 3.12.12, NumPy 2.4.2, SciPy 1.17.0,
  OpenCV 4.13.0. Constraint 11 (one machine for the whole grid) is therefore satisfied by
  running the nine synthetic cells here. This closes the response plan's last named open input
  ("Hardware spec to report for benchmarks — Tucker to pick").

- **D-06 — `calibrate_synthetic` gains an optional `memory_out: dict[str, dict] | None = None`,
  mirroring the `timings_out` precedent exactly.** Populated in place at the same two stage
  boundaries the function already times (`stage3_interface_optimization`,
  `stage3_intrinsic_pass`) plus a baseline. Default `None` leaves every existing caller
  bit-identical — guard it with exact-equality tests, the established Phase 16/17/19 pattern.
  Without this, the synthetic rows would carry whole-run peak while the real row carries
  stage-attributed peak, reintroducing in a second column the comparability problem D-02 fixes.

- **D-07 — ⚠️ USER OVERRODE the recommendation: E2 is re-run with `benchmark_memory: true`
  rather than carrying `memory: null` with a reason.** User's rationale: the numbers should be
  identical, and having the measurement on hand is worth ~50 min even if the published table
  later omits it; the stage the peak occurred in must be visible, at least at
  detection-vs-optimization granularity.

  **Verified feasible, with three findings the planner must carry:**
  1. **The re-run is bit-identical library code, not merely "the same version."**
     `git diff --stat f193d60..HEAD -- src/` is **empty** — all twelve commits since E2 ran are
     docs/planning. This upgrades the re-run from a drift check to a genuine determinism check
     (see D-08).
  2. **Stage attribution already exists and is finer than requested.** The pipeline samples
     `capture_peak_memory()` at six labeled boundaries — `_baseline` (`pipeline.py:1086`),
     `stage3_interface_optimization` (`:1101`), `stage3_rerun` (`:1230`),
     `stage3_intrinsic_pass` (`:1324`), `auxiliary_registration` (`:1497`), `validation`
     (`:1627`) — and the readings are documented monotonic high-water marks (Phase 19 D-18),
     so **consecutive deltas attribute the peak's growth to a stage**. `psutil` 7.2.2 is
     installed, so the mode will be `psutil_peak_wset`.
     **Granularity limit, stated deliberately:** `_baseline` is captured *after* Stage 1
     (`:841`) and Stage 2 (`:935`), so detection, Stage 1, and Stage 2 all fold into the
     baseline figure. The available split is **pre-optimization vs. per-optimization-stage**,
     which covers the requested detection-vs-optimization view. Separating detection from
     Stage 1/2 would need a new capture point and is explicitly **not** in scope.
  3. **The re-run must use the same input.** Per `19.1-E2-FRAMESET-PROVENANCE.md`, the run of
     record was a **full local-frameset run against the release config**, not the Zenodo
     archive. Re-running against the Zenodo archive will move §3 numbers for reasons unrelated
     to memory. `benchmark_memory` defaults to `False` (`schema.py:364`), so the config needs
     `internals.benchmark_memory: true` — one line.

- **D-08 — A moved §3 number in the E2 re-run is a DEFECT and a hard stop, not a prose gate.**
  Identical source + identical frameset + seeded holdout (`seed=42`) should reproduce. A moved
  number means nondeterminism in the real-rig path, which is a finding worth having before
  submission — the plan halts and reports rather than writing an explanation and continuing.
  **This is explicitly NOT a second D-16-style human gate:** 19.1's gate existed because moved
  numbers were *expected* (two feature releases had landed) and each move was a manuscript
  prose decision. Here the code is unchanged, so there is no manuscript decision to make — only
  a bug to chase. Do not schedule a human-verify checkpoint for it.

### E5 and E6 — the sensitivity and generalization sweeps (EXP-09, EXP-10)

- **D-09 — E5 sweeps on `generate_real_rig_array` geometry.** Synthetic ground truth built from
  the actual 13-camera layout (plus `generate_real_rig_trajectory`), because the whole R2
  argument is about how index error maps into depth bias *at realistic incidence angles* —
  oblique rays across the full tank, not a near-normal best case. This is what the brief means
  by "the real rig's actual geometry"; the physical rig data cannot serve, because a sweep needs
  a known `n_true` that only synthesis supplies.

- **D-10 — E5 and E6 are two fully independent scripts. The brief's "run them together, not
  twice" was evaluated with numbers and deliberately dropped — do not re-raise it as an
  oversight.** The arithmetic: E5's fine band (±0.01 around 1.333 at ~0.002 steps, ~11 points)
  and E6's coarse index axis (1.33→1.55 at ~0.03 steps, ~6–8 points) **coincide at exactly one
  configuration**, the 1.333 baseline. And D-09 puts E5 on real-rig geometry while E6's axes run
  on `generate_camera_array` families, so even that one point has a different cache key and
  shares nothing. Against ~29 total configurations at roughly 2–10 min each (from 19.1's
  measured E1/E7 runtimes), a shared cache saves **under 5% of wall-clock and plausibly 0%**,
  in exchange for coupling two scripts and a cache-key correctness risk. The real time saving
  is D-24's **within-script** per-configuration resumability, which already exists in `_io.py`
  and matters most for E6 as the largest sweep.

- **D-11 — E6 baselines on the grid-family 12-camera scene; each axis is genuinely
  one-dimensional; camera count is E4's axis and is not re-swept.**

  **AMENDED 2026-07-28 after research — the baseline is NOT `create_scenario("realistic")`.**
  The original text named `realistic` and described it as "grid layout," which the code
  contradicts (see the amended D-03: `realistic` is `generate_real_rig_array()`, a fixed
  real-rig arrangement). Keeping it would have broken the axis design at the exact point that
  matters: the layout axis's three values all come from `generate_camera_array`, so a
  `realistic` baseline would sit off its own axis and **no axis value would equal the
  baseline**. Baseline is therefore
  `generate_camera_array(layout="grid", n_cameras=12)` — identical to **E4's 12-camera cell**,
  which is the surviving cross-experiment anchor.

  The three axes: **index** 1.33→1.55 (requires D-23), **layout** ∈ {grid, ring, line} at a
  fixed 12 cameras — the `grid` value *is* the baseline, so the axis passes through it — and
  **scale** (tank size / working distance, separately controllable per 16-02). The brief and
  WP5 both phrase the layout axis as "grid vs. ring vs. varied camera count," which is two
  dimensions; splitting count out to E4 keeps every axis one-dimensional and avoids re-treading
  E4's sweep under a different label. **D-14 closes the gap this opens** — see it.

  Considered and rejected: keeping `realistic` as the baseline (ties E6 to E1/E5 but leaves the
  layout axis not passing through its own baseline), and adding `generate_real_rig_array()` as a
  fourth layout value (a stronger R1.4 answer, but a layout axis whose values come from two
  generators, plus an extra run).

- **D-12 — A degrading axis value is reported as measured; no pass/fail verdict is baked into
  the CSV.** E6's stated finding ("parameter recovery and held-out reconstruction accuracy hold
  across the sweep") can genuinely fail — a line layout or n=1.55 may degrade. R1.4 asked
  whether the method generalizes, and a bounded, characterized degradation ("holds to n=1.5,
  degrades beyond") is a better answer than a claim of universal invariance a reviewer can poke.
  The script asserts nothing about the science; interpretation is manuscript work. Rejected:
  a declared accuracy threshold with a pass/fail column (the threshold would be an invention,
  and picking it after seeing the data is exactly what the provenance discipline exists to
  prevent), and narrowing the swept range to where it holds (choosing the range from the
  results, with no defensible answer to "why does the index axis stop at 1.5?").

- **D-13 — E5 expresses depth/scale bias against the same yardstick the response plan argues
  from.** WP4 bounds the bias against "the held-out noise floor (0.674 mm RMSE on 60 mm ≈
  1.1%)" — an E2 number. E5's CSV and panel should carry the bias in those same terms so the
  comparison is direct rather than left to the reader to perform. Also: **do not quote WP4's
  back-of-envelope figures** (~0.075% worst case) as results; they are a sanity target for the
  sweep, and the earlier dev-time analysis they came from is not committed anywhere in the repo.

### Post-research amendments (2026-07-28) — the `n_true` / `n_assumed` wiring

- **D-23 — `calibrate_synthetic` must honor the scenario's own `n_air` / `n_water` when
  generating detections. This is a BUG FIX closing a documented contract, not a new feature.**

  **The defect, verified.** `calibrate_synthetic`'s `n_water` argument is threaded into
  `estimate_extrinsics` (`pipelines.py:95-98`), `optimize_interface` (`:125-126`), and
  `joint_refinement` (`:148`) — it is the **assumed** index. But the detection call
  (`pipelines.py:69-77`) omits `n_air`/`n_water` entirely, so `generate_synthetic_detections`
  falls back to its defaults (`synthetic.py:472-473`) and **ground truth is ALWAYS generated at
  1.333**. Meanwhile `SyntheticScenario` carries `n_air`/`n_water` fields that
  `create_scenario` populates, and `create_scenario`'s own docstring states *"Callers must pass
  the same values to `generate_synthetic_detections`"* — which this caller does not. So
  `create_scenario(n_water=1.55)` silently produces detections at 1.333 today.

  **Blast radius, and what it does NOT break:**
  - **E5 (EXP-09) needs no library change and never did.** Its procedure — generate at
    `n_true`, calibrate assuming `n_assumed`, with `n_true` fixed at 1.333 — is exactly
    `calibrate_synthetic(scenario, n_water=n_assumed)` as shipped. This is the same mechanism
    E1's non-refractive arm already uses (`n_water=1.0` against 1.333 ground truth). The
    research return framed this as a blocker for E5; it is not. **Do not add a parameter for
    E5's sake.**
  - **E6's index axis (EXP-10) IS broken by it.** Sweeping 1.33→1.55 to demonstrate the
    arbitrary-index-ratio claim requires ground truth generated at each value. Without the fix
    every scenario in the sweep is generated at 1.333 and the axis measures nothing — a silent
    null result that looks like data.

  **The fix:** pass `n_air=scenario.n_air, n_water=scenario.n_water` into the
  `generate_synthetic_detections` call. The assumed index (the function argument) and the true
  index (the scenario field) then become independently controllable, which is what both E5 and
  E6 need and what the docstrings already promise.

  **Guard it as a zero-numerical-change fix.** Every existing caller (E1, E7, the tutorials)
  uses scenarios built at the default 1.333, so behavior must be bit-identical — assert that
  with exact-equality tests, the established Phases 16/17/19 pattern, rather than assuming it.
  Rejected: a new explicit `n_true` parameter (leaves `SyntheticScenario.n_water` as a field
  that lies about what was generated — the same trap for the next caller), and having E6 bypass
  `calibrate_synthetic` and call the three stages directly like E7 (a fourth copy of the
  calibration sequence in `experiments/`, against P2).

- **D-24 — `experiments/_io.py::write_direct_call_benchmark` gains an optional
  `memory_readings` parameter.** Found by pattern mapping, not by the discussion: the wrapper
  hard-codes `memory_readings=None` (`_io.py:427`) with a docstring citing 19.1's D-11
  ("BENCH-02's opt-in memory discipline is pipeline-side"). That was correct for 19.1 and is
  now the blocker for D-06 — E4's synthetic cells cannot record memory through a wrapper that
  discards it. Add `memory_readings: dict | None = None` and forward it; the default preserves
  E1's and E7's existing behavior exactly, so no committed record changes.
  Note also that the wrapper restricts stage keys to
  `{"stage3_interface_optimization", "stage3_intrinsic_pass"}` — E4 must use that settled
  Phase-18 vocabulary rather than inventing grid-local stage names.

- **D-25 — Correction of record: the bit-exactness test file is
  `tests/unit/test_datasets_pipelines.py`, not `tests/unit/test_pipelines.py`.** The latter does
  not exist (`tests/unit/test_pipeline.py`, singular, is the pipeline module's own test file and
  is a different thing). The established guard pattern to extend for D-06 and D-23 lives at
  `test_datasets_pipelines.py:67` (`test_default_unchanged_gauge`) and `:154`
  (`test_bit_exact_repeat`) — copy those shapes rather than inventing an assertion style.

### Holistic review against the reviewer response plan (user-requested, 2026-07-28)

All four experiments were re-checked against
`.../papers/aquacal/reviewer_response_plan.md`. **Coverage is sound:** WP2→E4, WP4→E5,
WP5→E6, WP6→E7 (shipped in 19.1); WP1/WP3/WP7/WP8 are prose and correctly outside this phase;
every decline (analytic Jacobian, physical multi-medium, running CalibMar) is substituted, not
gapped. Three adjustments were adopted and one was rejected.

- **D-14 — E4's CSV carries the `accuracy` block, making the grid answer accuracy-vs-camera-count
  as well as cost-vs-camera-count. This is the highest-value item found in the review.** It is
  the only one that answers something otherwise **unanswered**: WP5 asks for generalization
  across camera count, D-11 routes count to E4, and E4 was scoped as a cost experiment — so
  nothing would have measured whether accuracy holds from 8 to 16 cameras. That gap matters
  precisely because the manuscript's hedge, "a dozen or more cameras" (`main.tex:350`), is a
  claim about *count*, and R1.3 asks whether the method "stably adapts" to N>10 — currently
  answered structurally and by assertion, not by measurement. This is R1.3's empirical leg.

  **AMENDED 2026-07-28 during planning — "free" was WRONG for the direct-call path, and copying
  the block would have published fabricated zeros.** The `accuracy` block does carry
  `reprojection_rms`, `validation_3d_error_mean`, and `validation_3d_error_std` in **E2's
  pipeline-written** record — that part was verified correctly. But `calibrate_synthetic`
  **hardcodes** `validation_3d_error_mean=0.0` and `validation_3d_error_std=0.0`
  (`pipelines.py:183-184`), because a direct-call run has no held-out set. E4's nine synthetic
  cells therefore must **measure** held-out accuracy via a separate holdout scored with
  `evaluate_calibration` — not copy `result.diagnostics.validation_3d_error*`, which would
  write two fabricated zeros into the grid and read as "held-out error is exactly zero at every
  camera count." Only `reprojection_rms` is genuinely copyable. Caught by the planner, not by
  the discussion; the plan carries a grep gate forbidding reads of those two fields.

- **D-15 — `dense_threshold` becomes E3 tier 1's fifth constant, and E4 reports each cell's
  Jacobian element count.** WP3 item 4 states as fact that `make_sparse_jacobian_func` returns a
  dense Jacobian below a ~4 GiB threshold, that the 13-camera/200-frame rig sits at ~200M
  elements "comfortably in the dense/QR regime," and that N up to ~30 does too. Verified live:
  `_optim_common.py:653`, `dense_threshold: int = 500_000_000`. This is exactly the shape of
  tier 1's other four constants — a source literal the supplement states as fact — and it was
  simply missed when the brief's table was written; it is a live instance of the failure mode
  tier 1 was invented to prevent. E4 reporting `n_residuals x n_params` per cell turns the
  dense-regime claim from an assertion into a measured column.
  **Caveat that must reach the prose:** E4 tops out at 16 cameras, so tier 1 can assert the
  constant and E4 can measure the 13-camera rig's element count, but **nothing measures the
  "N up to ~30-ish" claim.** It stays an extrapolation and must not be written as though tested.

  **AMENDED 2026-07-28 during planning — the element count needs a fourth library addition.**
  "Near-free; the element count is `n_residuals × n_params`, both already in the record" was
  half wrong: `n_params` is recorded, but **`n_residuals` appears nowhere** in
  `_observability.py` or `io/benchmark.py`. It is computed as `jac_sparsity.shape[0]` inside
  `build_jacobian_sparsity` and never surfaced. Add `n_residuals` to `SolverDiagnostics`,
  following the existing `n_params`/`n_groups` absent-metric convention verbatim; it reaches
  `benchmark.json` through `dataclasses.asdict` with no edit to `io/benchmark.py`. The
  alternative — having E4 re-derive the residual row count — would mean re-implementing the
  `min_corners` filter inside a script, exactly the P2 violation E3 tier 3 exists to prevent.

- **D-16 — E4 surfaces CPR columns by copying them from its own record, and E3 tier 3 does not
  re-derive P/groups for any configuration E4 already ran.** WP2 wants the CPR speedup inside
  the benchmark table ("directly answers R1.2's cost question"), and `benchmark.json` already
  records `n_params`, `n_groups`, and `fd_reduction` per stage — E2's committed record shows
  P=1269, 13 groups, **97.6x** for `stage3_interface_optimization` and P=1317, 17 groups, 77.5x
  for `stage3_intrinsic_pass`. Naively adding these columns to E4 would create a *second origin*
  for numbers `cpr_grouping.csv` also produces — the "one number, one origin" violation this
  phase exists to prevent. So: **E4 copies from its own `benchmark.json`; E3 tier 3 covers only
  the declared `tab:cpr` rows outside E4's grid** (3 cameras/3 frames, and the 13/200 real-rig
  row from E2). Each configuration keeps exactly one origin, and the benchmark table is
  self-contained.

- **D-17 — REJECTED: enabling `save_conditioning` across E4's cells.** Considered as extra
  R1.3/R4.3 evidence (condition number vs. N, supporting WP3 item 4's intrinsic-ill-conditioning
  argument). Rejected on three grounds: R4.3 is already answered by E7's four arms with the
  conditioning report, which is *targeted* evidence about shared-vs-per-camera rather than a
  question no reviewer asked; it is the only reviewed item with real cost (a dense SVD per
  cell); and the 16-camera/200-frame cell is already the memory risk on a 16.9 GB box (D-04),
  so this is the most likely way to make a grid cell fail. Recorded so a planner does not
  re-raise it.

### E3 — derived quantities and code constants (EXP-07)

- **D-18 — The declared constants table is declared ONCE, in `tests/`, and imported by the E3
  script.** A single module-level table of (claim, source location, declared value) lives in
  the test file that asserts it, so **CI owns the gate and breaks first** when a default
  changes; `e3_derived_quantities.py` imports that table to render `code_constants.csv` with
  its pass/fail column. One declaration, two consumers, no possible drift.
  Knowingly accepted: `experiments/` importing from `tests/` inverts the usual direction. It is
  the same shape as `tests/synthetic/ground_truth.py`'s re-export shim, and `experiments/` never
  ships (`pyproject.toml:73-74`), so nothing leaks into the wheel. Rejected: declaring it in
  `experiments/` (puts the owner of a CI gate outside the test suite, so an experiment-script
  edit could weaken an assertion without touching `tests/`), and declaring it twice with an
  equality test (ceremony guarding a self-inflicted duplication).

  Tier 1's rows: the brief's four (verified 2026-07-24 — `water_z` bounds `[0.01, 2.0]` and
  refined intrinsics 50–200% at `_optim_common.py:519-520,534-536`; Huber `f_scale = 1.0 px` at
  `interface_estimation.py:343,677`; the 100 px invalid/TIR penalty at `_optim_common.py:639`
  and `interface_estimation.py:654`; Newton tolerance `1e-9` with `max_iterations = 10` at
  `refractive_geometry.py:330`), plus **`dense_threshold`** per D-15, plus the solver
  tolerances — which are now assertable rather than inferred, because **BENCH-06 landed**:
  `ftol`/`xtol`/`gtol` are passed explicitly at `1e-8`
  (`interface_estimation.py:359-361,368-370,728-730`, `refinement.py:262-264,275-277`) with
  `max_nfev_source="scipy_auto"`.

- **D-19 — Tier 2's Newton iteration counts come from a new PUBLIC diagnostic in
  `src/aquacal/core/refractive_geometry.py`, not from the script.** Verified gap:
  `_refractive_project_newton` (`:325`) is private and returns `Vec2 | None`, reporting no
  iteration count — so P2 ("the library computes; the experiment orchestrates") requires a hook,
  the Phase 16 pattern. Add a small public function that runs the same root-find and returns the
  iteration count and final residual per ray, sharing the loop body rather than duplicating it.
  **The projection path itself stays untouched**, so there is no bit-exactness risk to guard on
  the hot path — which is why this is preferred over threading an `iterations_out` out-parameter
  through a function called inside every residual evaluation.

  Worth recording for the prose: the supplement's "converges ... in two to four steps" currently
  traces to that function's own docstring ("typically 2-4 iterations") — a comment, not a
  measurement. This is the same hand-carried-number pattern the phase exists to close.

- **D-20 — Tier 2 measures over the real rig's working volume, and reports the full
  distribution.** Sweep points across the working volume against `generate_real_rig_array`'s
  camera positions — the same geometry E5 uses (D-09) — so incidence angles span what the
  physical rig actually sees, including its most oblique corners. **Report min / median / max /
