## Issues Encountered

**Acceptance criterion mismatch (documented, not a code defect):** The plan's Task 1 acceptance criteria and the plan-level `<verification>` step 4 both require `grep -c "f_prime = n_air \* h_c" src/aquacal/core/refractive_geometry.py` to return exactly `1`. It returns `2`. Investigation (via `git show HEAD~1:... | grep`) confirmed this is **pre-existing**, not introduced by this plan: `_refractive_project_newton_batch` — which the plan explicitly instructs *not* to touch ("Do NOT touch `_refractive_project_newton_batch`... or any other function in the file") — independently implements the identical `f_prime = n_air * h_c * h_c / (d_air_sq * d_air) + n_water * h_q_v * h_q_v / (...)` expression under a slightly different variable name (`h_q_v` vs `h_q`), which the grep pattern's common prefix still matches. Achieving a literal grep count of 1 would require also refactoring the batch variant, directly contradicting the plan's explicit scope boundary.

The criterion this substitutes for — "the diagnostic shares the loop rather than duplicating it" (T-19.2-10, D-19) — is fully satisfied and independently verified by the plan's own second grep criterion: `grep -c "_solve_newton_r_p(" src/aquacal/core/refractive_geometry.py` returns exactly `3` (1 definition + 2 callers: `_refractive_project_newton` and `refractive_project_newton_diagnostic`). The single-point Newton loop exists in exactly one place; the batch variant's independent implementation is out of this plan's scope and was not touched. Not treated as a Rule 3 blocker or a Rule 4 architectural question because the plan's own explicit "do NOT touch" instruction takes precedence, and the substitute criterion in the same acceptance list already proves the D-19 requirement.

All other acceptance criteria and the plan's `<verification>` steps 1-3 and 5 pass exactly as specified.
