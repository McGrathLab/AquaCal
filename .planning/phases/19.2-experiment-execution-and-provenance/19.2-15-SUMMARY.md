# Phase 19.2 Plan 15: Total `compare_experiment_csv` Summary

Closed CR-04: `compare_experiment_csv` now returns a `ComparisonReport` for every
`(fresh, committed_path, key_columns, rtol)` whose committed file is readable as a CSV,
instead of raising on a row-count mismatch, a key-set mismatch, or a non-numeric cell
inside a column pandas classified as float. This is the fix for the third bug found in
this function this phase (after `ee8af31`, `ac75e35`); this time the fix is a stated
totality contract plus general-shape tests, not a fourth dtype special case.

## What Was Built

### Task 1 (commits `dc51631` test, `c4678ac` feat): key-based alignment

Replaced the prior sort-both-frames-and-compare-positionally step with explicit
key-based alignment, classified into three structural outcomes before any cell-level
comparison:

1. **Key-set mismatch** (`fresh_key_set != committed_key_set`) -- returns a report
   naming both the fresh-only and committed-only keys (truncated at 10, full counts
   stated). This subsumes the plain row-count case: on
   `EXPECTED_BASE`, a row-count mismatch with a differing key set raised
   `ValueError: Can only compare identically-labeled Series objects`; now it returns
   `passed=False` naming the offending key (e.g. `"cam2"`), never raises.
2. **Duplicate key** (equal key sets by unique value, but differing row counts) --
   returns a report stating both sides' row-count-vs-unique-key-count, again without
   raising.
3. **Matched, unique keys on both sides** -- unchanged behavior: sort by
   `key_columns`, compare as before, identical `worst_cell` message for an input that
   already worked (pinned by `test_check_matching_keys_still_names_worst_cell_from_true_counterpart`).

The docstring now states the totality contract explicitly: "returns a
`ComparisonReport` for every `(fresh, committed_path, key_columns, rtol)` whose
committed file is readable as a CSV... The only exceptions it may propagate are I/O
errors reading `committed_path`."

**Observed pre-fix failure (recorded per task 1's acceptance criteria):** the row-count
mismatch test (`test_check_row_count_mismatch_reports_not_raises`) failed on
`EXPECTED_BASE` with `ValueError: Can only compare identically-labeled Series objects`,
reproducing CR-04 case 1 exactly as described in `19.2-GAP-CONTEXT.md`.

### Task 2 (commits `d490f1f` test, `4eb2bc5` feat): non-numeric coercion in the worst-cell loop

In the worst-cell loop, both `fresh_vals` and `committed_vals` are now built via
`pd.to_numeric(..., errors="coerce").to_numpy(dtype=float)` instead of a bare
`to_numpy(dtype=float)`. A cell is only treated as "genuinely missing" (and therefore
not a mismatch) when **both raw, pre-coercion** values are NaN; a cell where coercion
introduced a new NaN on only one side (i.e. a real non-numeric string, such as
`"KeyError: 'cam11'"`, coerced away) is treated as `cell_rtol = inf` and counted as a
mismatch. This distinguishes "genuinely missing on both sides" from "a real value that
happens to be non-numeric," which a naive both-sides-coerced-to-NaN check would have
conflated and silently hidden -- exactly the failure mode the plan warned against.

Added a comment naming this as the third member of the CSV dtype round-trip family,
referencing `ee8af31` and `ac75e35` by commit, and stating the coercion-not-a-fourth-
case rationale.

**Observed pre-fix failure (recorded per task 2's acceptance criteria):**
`test_check_worst_cell_loop_tolerates_nonnumeric_in_float_column` failed on
`EXPECTED_BASE` with `ValueError: could not convert string to float: "KeyError:
'cam11'"`, reproducing CR-04 case 2.

**`worst_rtol` regression anchor:** `test_check_numeric_mismatch_worst_rtol_unchanged_by_coercion`
pins a purely numeric mismatch's `worst_rtol` at `10 * CHECK_RTOL` (`1e-5`), matching the
value produced by the pre-existing `test_check_fails_outside_rtol_and_names_worst_cell`
fixture -- unchanged by the coercion.

## Deviations from Plan

### Auto-fixed Issues (Rule 1/3 -- within task scope, not architectural)

**1. [Task 1 test design] Row-count-mismatch test reassigned to the key-set-mismatch path.**
The plan's task 1 action states the key-set check "subsumes the row-count case." My
first draft of `test_check_row_count_mismatch_reports_not_raises` asserted the message
contained the literal row counts (`"3"`, `"2"`), which does not match the design: a
row-count mismatch that also differs in key set (the only way two frames sharing a
header can differ in row count without a duplicate key) is reported via the key-set
message, naming the offending key rather than a bare count. Fixed the test's assertions
to check for the fresh-only key (`"cam2"`) and the committed path, matching the actual
(and, per the plan text, intended) code path. No production code was affected by this
correction -- it was a test-assertion fix caught before the GREEN commit.
