<objective>
Re-run E4's nine-cell grid on the geometry plans 19.2-17 and 19.2-18 established, and re-commit
`benchmark_grid.csv` and `benchmark_grid.tex` with E2's real rig as the labeled tenth point.

Purpose: EXP-08 and ROADMAP SC2. The committed grid was measured at 0.15 m above the water with a
0.30 m footprint, where the 0.72 × 0.54 m board overfills the frame at a measured 22% mean
visibility — so the residual counts driving its memory and runtime columns describe no rig anyone
would build. D-29 moved the family to real-rig optical geometry; this plan re-measures it.

**This plan runs ALONE on the machine.** Nothing else may run on the box while it does — not another
experiment, not a `--smoke` invocation, not a test suite. E4's headline deliverable is a wall-clock
and peak-memory curve, and a concurrent process makes those numbers measure contention (review H4).
Constraint 11 ("one machine for the whole grid") is about machine identity; this is about quiescence,
and they are different requirements.

**Every `src` and `experiments` change lands before this plan starts.** That is why `depends_on` lists
all six code plans rather than only the ones touching E4's files: the constraint is **temporal**
(the tree must be frozen for the duration of the run), and `files_modified` disjointness is spatial,
so the wave model cannot express it. This exact confusion bit this phase once already.

**Expect 16×200 to fail.** If corners per view rise from 19.5 toward 88, residuals scale 3–4.5× and
peak memory projects to 9.9–14.9 GiB against a ~15.7 GiB box:

<interfaces>
Entry point: `python -u -m experiments.e4_benchmark_grid --force`. Iterates `DECLARED_CELLS` (nine
pairs over {8,12,16} × {50,100,200}), spawning ONE CHILD PROCESS PER CELL via `run_cell_subprocess`,
writing one `benchmark.json` per cell under `<out>/e4_cells/cameras_{n}_frames_{m}/`, then building
`benchmark_grid.csv` and `benchmark_grid.tex`.

Single-cell entry point: `--cell 16x200`. Runs exactly that cell and exits; writes no CSV and no
LaTeX. Exit 0 = ok, 3 = `skipped_existing`, anything else = failed.

Why per-cell processes: `capture_peak_memory()` returns a PROCESS-LIFETIME high-water mark, so nine
cells in one process would make cells 2–9 report "the largest cell so far" — monotone, plausible and
wrong. And a Windows OOM kills the process outright, so an in-process `except Exception` could never
record the `status=failed` row D-04 promises.

**New in this re-run, from plan 19.2-17** — read that plan's summary for exact names:
- an explicit per-cell timeout, with `TimeoutExpired` mapped onto a recorded `status=failed` row;
- commit/virtual memory recorded beside `peak_wset`, plus the machine's physical total;
- a memory-pressure measurement condition (NOT a verdict — D-12 stands);
- a pre-flight ceiling that refuses a cell as a recorded row rather than letting the OS page it.

**New in this re-run, from plan 19.2-18:** grid-family geometry at ~1.031 m above the water,
`depth_range` (1.1, 2.0), spacing ~0.43 m, `xy_extent` derived from the array span, the board volume
centred on the array centroid, and a held-out set built from the cell's own geometry.

`--check` re-aggregates the per-cell records already on disk and compares them against the committed
CSV. It does NOT re-run any cell, so it is **structurally unable to exit 0** — documented, and
deliberately not a CI gate. Do not "fix" this by re-running cells.

Per-cell resumability: re-running WITHOUT `--force` resumes an interrupted sweep, reusing every
completed cell. Plan 19.2-17 fixed the resume path so those cells' metrics survive aggregation
(CR-01); before that fix a resumed run published an all-null CSV.

The hardware spec of record (D-05), already in E2's committed `benchmark.json`: Intel64 Family 6
Model 154, 20 logical cores, 16,857,190,400 bytes RAM, Windows 11, Python 3.12.12, NumPy 2.4.2,
SciPy 1.17.0, OpenCV 4.13.0.
