## What Was Built

### Task 1 — `refractive_project_batch_newton_diagnostic` (new public API)

`src/aquacal/core/refractive_geometry.py`:

- `_refractive_project_newton_batch` gained a `return_diagnostics: bool = False` keyword.
  When `False` (unchanged, the production default used by `refractive_project_batch` ←
  `calibration/_optim_common.py:635`), the function's arithmetic, clipping, iteration
  cap, and termination rule (`np.all(np.abs(delta) < tolerance)`) are byte-for-byte what
  shipped before this plan. When `True`, it additionally returns a diagnostics dict; the
  bookkeeping that builds it (`converged_at_iteration`, `final_abs_delta` tracking) never
  feeds back into `delta`, `r_p_v`, the clip, or the termination check.
- New public function `refractive_project_batch_newton_diagnostic(camera, interface,
  points_3d, max_iterations=10, tolerance=1e-9) -> dict`, exported from `aquacal.core`
  (`__all__` updated in `src/aquacal/core/__init__.py`). Return shape, over only the
  VALID off-axis points (same population `refractive_project_newton_diagnostic` reports
  over — on-axis and above-interface points are excluded):
  - `point_index` (int64 array): index into `points_3d`.
  - `converged_at_iteration` (int64 array): 1-based iteration at which that point's own
    `|delta|` first fell below `tolerance`, or `-1` sentinel if it never did.
  - `converged` (bool array): `converged_at_iteration >= 0`.
  - `final_abs_delta` (float64 array): `|delta|` at the last iteration the batch loop
    executed (not necessarily this point's own convergence iteration — the vectorized
    loop keeps running for slower points under all-points termination).
  - `r_p` (float64 array): converged/clamped interface-crossing radius, metres.
  - `incidence_angle_deg` (float64 array): `degrees(arctan2(r_p, h_c))`.
  - `n_iterations_executed` (int): loop iterations actually executed for the whole batch
    call before the all-points break (or `max_iterations` if it never triggered).
- Corrected two docstrings that misdescribed the code (both grep assertions in the plan's
  acceptance criteria now return 0):
  - `_solve_newton_r_p`'s "cannot drift between two copies" claim now names
    `_refractive_project_newton_batch` as a deliberately un-migrated third copy (D-32
    option (a), rejected and out of scope).
  - `refractive_project_newton_diagnostic`'s "used inside every residual evaluation"
    claim is corrected: it measures the scalar path only; production's residual
    evaluation uses the batch path, measured by the new function.

## Observed Scalar vs. Batch Difference (substance for MF-01, written up in wave 6 by 19.2-25)

On a 3-frame real-rig sweep (`build_newton_iterations_df(n_frames=3, seed=42)`, 3168
points), the scalar and batch loops report **identical** `iter_min`/`iter_median`/
`iter_max`/`n_not_converged` per camera and pooled (both min=3, median=4.0, max≤5,
`n_not_converged=0` everywhere) — because every point converges well under the
`max_iterations=10` cap, so the slowest point in each batch call converges before the cap
regardless of loop. The `residual_max_m` values differ (batch residuals are consistently
smaller, e.g. pooled `9.97e-10` scalar vs `5.64e-10` batch) because the batch loop keeps
refining already-converged points for extra no-op iterations while the batch waits for
its slowest member, driving their `|delta|` further toward zero — this is exactly the
"per-point cost behaves like the tail, not the median" effect D-32 predicted, now visible
in the residual column rather than the iteration columns on this particular sweep. A test
(`test_batch_diagnostic_agrees_with_scalar_diagnostic_rp`) records but does not assert
the per-point iteration-count difference between the two loops, since divergence there is
expected and is the point of this plan, not a defect.
