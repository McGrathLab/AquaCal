## Accomplishments

- **WR-02 (Task 1):** E6's `run_configuration` now builds `SolverDiagnostics()` sinks and passes them via `diagnostics_out=` to `calibrate_synthetic`, surfacing `optimality_stage3_interface_optimization`/`optimality_stage3_intrinsic_pass` as new `E6_COLUMNS` entries. A diverged solve (like the `double_scale` row that published 1536 px RMS under `status="ok"` with nothing to flag it) can no longer hide behind a bare `status="ok"`.
- **WR-03 collision fix (Task 2):** `_config_identity_matches` now compares only `_SCENARIO_IDENTITY_KEYS` (the fields that determine which scene gets built), not the full checkpoint identity. The three `is_baseline` rows -- which deliberately share one scene under three different `axis`/`axis_value` labels -- now match a single recorded identity, while a scenario field mutation (proven with `layout`, distinct from the pre-existing `n_water` test) still degrades the row to `status="failed"`.
- **One-sweep-one-commit (Task 3):** `run_sweep` captures the environment once (before its loop) and threads that same block through every `run_configuration` checkpoint AND the provenance sidecar. `capture_environment()` shells out to `git rev-parse` per call; the measured 2026-07-31 split (`baseline.json` at `3d5c3e6`, the other eleven at `3d0aa3e`) can no longer happen.
- **E5 discard_stats (Task 4):** `run_index_point` forwards `discard_stats_out=` to `calibrate_synthetic`; `run_band` sums each point's counters into one caller-owned dict; `_run_full` threads that summed dict into `e5_provenance.json`'s new `discard_stats` field. Plan 19.2-23's attribution gate (`discard_stats.pnp_guard_rejected > 0` "in the run's own output") is now runnable against real E5 output.
- **Inertness proof (Task 5):** Both new sinks are proven numerically inert by fast exact-equality tests against the package's cheap `"minimal"` preset, matching each experiment's own `calibrate_synthetic` call shape (`normal_fixed`, `refine_intrinsics`).

## Decisions Made

- **E6_COLUMNS grows to 30, not 29.** The plan's interfaces block named only `optimality_stage3_interface_optimization` as E4's precedent, but E4 tracks only one optimization stage's optimality. E6 runs a second stage (`stage3_intrinsic_pass`) whenever `refine_intrinsics=True`, so a second column (`optimality_stage3_intrinsic_pass`, null whenever that pass never runs) was added to avoid silently dropping half the available signal.
- **WR-03 fix scope: `_SCENARIO_IDENTITY_KEYS`** = `n_cameras, layout, n_water, depth_range, xy_extent, spacing, normal_fixed`. Excluded: `axis, axis_value, is_baseline, config_key` (presentational labels only).
- **E5's discard_stats aggregation shape: SUMMED across the band**, not per-point. Rationale in the code and this summary: every point in `N_ASSUMED_BAND` shares the identical rig geometry and calibration frame count -- only `n_assumed` differs -- so the attribution question ("did the PnP guard activate anywhere in this run?") is inherently band-level. A per-point breakdown would imply a granularity the experiment was never designed to distinguish.
- **`None` vs `{}` is preserved everywhere a new sink threads through a provenance artifact.** `discard_stats: None` means "accounting never requested" (e.g. `--smoke`/`--check`, which do not request it); `discard_stats: {}` means "requested, and the run's own output counted zero of every key that ever fired." The two are never coerced into each other.

## WR-03 proof that the guard still trips (Task 2 acceptance criterion)

`test_scenario_field_mutation_still_trips_wr03_after_the_restriction` mutates `layout` (deliberately a DIFFERENT scenario field than the pre-existing `test_reconstitute_row_flags_mismatched_config`, which already covered `n_water`) on a cached checkpoint and asserts the row still degrades to `status="failed"` with the WR-03 reason. This test discriminates a correct restriction from an over-loosened one: if `_SCENARIO_IDENTITY_KEYS` had accidentally dropped `layout` (rather than only the intended presentational fields), this test would fail while `test_baseline_configs_match_despite_differing_axis_labels` would still pass -- the two tests together prove the fix landed at the right boundary, not merely "somewhere that makes both currently-known cases work." A companion test, `test_axis_label_mutation_alone_does_not_trip_wr03`, proves the mirror case: mutating ONLY `axis`/`axis_value` (no scenario field) does NOT degrade the row -- this is the specific behavior the fix adds, and it fails on the pre-fix (full-identity) comparison.

## D-12 statement (Task 1 acceptance criterion)

No `converged`, `diverged`, `verdict`, or pass/fail column exists anywhere in `E6_COLUMNS` or `_METRIC_COLUMNS`. The two new columns record the raw first-order `optimality` FLOAT SciPy reports on the final `OptimizeResult` -- nothing in `e6_generalization_sweep.py` thresholds, compares, or judges that value. Verified by `test_no_optimality_thresholding_in_e6_source` (scans the module source for any comparison operator applied to `optimality`) and `test_no_verdict_column` (scans column names, tokenized).

## `--check` is NOT expected to exit 0 in this plan

Task 1 changes `E6_COLUMNS` from 28 to 30 entries. `experiments/e6_generalization_sweep.py --check` reconstitutes rows from the EXISTING, uncommitted-by-this-plan `e6_configs/*.json` checkpoints and compares them against the OLD, still-28-column committed `generalization_sweep.csv`. That comparison will fail on a header mismatch (`compare_experiment_csv` expects identical columns) until plan 19.2-28 re-runs the sweep and regenerates the CSV with all 30 columns. This is expected, not a regression -- Task 2's WR-03 fix was validated by UNIT TEST ONLY (`_reconstitute_row`/`_config_identity_matches` called directly, never through `--check` end to end), exactly as the plan's `<action>` block for Task 2 specifies.

## Inertness result (Task 5)

Both `diagnostics_out` (E6) and `discard_stats_out` (E5) are output sinks that must not perturb any returned calibration value. Both are proven inert by exact-equality tests (`==` / `np.testing.assert_array_equal`, never `allclose`) run against the package's cheap `"minimal"` preset, calling `calibrate_synthetic` twice -- once with the sink omitted, once with it populated -- using each experiment's own `normal_fixed`/`refine_intrinsics` call shape. Both tests also assert the instrumented sink was actually populated (not vacuously ignored): `diag_stage3.nfev is not None` for E6 (the interface-optimization solve always runs), and `assert stats` for E5 (`pnp_attempts_total` bumps unconditionally on every PnP entry, per `_observability.py`, so even a zero-discard clean run leaves the sink non-empty). **No non-inertness was found; nothing to report as a finding that would change plans 28/29.**
