# Phase 19.2 Plan 17: E4 resume/aggregation/OOM-guard fixes (W1) Summary

**Extended `capture_peak_memory()` with additive commit/virtual/RAM fields, fixed E4's resume-path metric loss and cwd-relative E2 read, and added a per-cell subprocess timeout plus a pre-flight memory ceiling so a thrashing 16-camera cell cannot silently report a paged success as a clean `ok`.**

## Performance

- **Duration:** ~90 min
- **Tasks:** 3/3 completed
- **Files modified:** 5

## Accomplishments

1. **Task 1 — additive memory reading.** `capture_peak_memory()` now returns five keys instead of two: `peak_bytes`/`mode` (unchanged in value and meaning) plus `commit_current_bytes`, `commit_peak_bytes`, `ram_total_bytes` (Windows: `psutil.Process().memory_full_info()`'s `pagefile`/`peak_pagefile` plus `psutil.virtual_memory().total`; `None` — never absent — on every other platform and on any internal failure). Observed on this box: `{'peak_bytes': 113541120, 'mode': 'psutil_peak_wset', 'commit_current_bytes': 1397125120, 'commit_peak_bytes': 1397125120, 'ram_total_bytes': 16857190400}`. The three new fields are threaded through `assemble_benchmark_record`'s per-boundary memory block as `commit_current_bytes_as_of_stage_end`, `commit_peak_bytes_as_of_stage_end`, `ram_total_bytes`, alongside the unchanged `cumulative_peak_bytes_as_of_stage_end`/`delta_bytes_since_previous_boundary`/`mode` — six keys per boundary now, not three.

2. **Task 2 — CR-01/CR-03.** `build_grid_dataframe` now nulls a cell's metric columns only when `status == "failed"` or no record was read at all — a `skipped_existing` cell whose `benchmark.json` was read successfully by `aggregate()` keeps those metrics (verified by a new test that fails on `EXPECTED_BASE`). `E2_BENCHMARK_PATH` is anchored to `__file__` (matching E3's existing `_E2_BENCHMARK_JSON_PATH` pattern) rather than being cwd-relative; the E2 read and the `aggregate(cells_dir)` call are both now guarded, degrading to a null real-rig row with `record_source="missing_e2_benchmark"` and a WARNING instead of raising after all nine cells have solved. Verified `--smoke` exits 0 when invoked from a scratchpad directory outside the repo, proving the cwd-independence fix genuinely works, not just in a test fixture.

   **Correction to CR-01's stated evidence:** a "failed" E4 fixture already existed before this plan (`test_declared_cells_all_emit_rows`) — "every E4 fixture uses `status='ok'`" was overstated. What was actually missing was a `skipped_existing` fixture backed by a real on-disk record; that is the gap this plan closes.

3. **Task 3 — D-33's three gaps.**
   - **Gap 2 (timeout):** `CELL_TIMEOUT_SECONDS = 20 * 60` is now passed at both production call sites (`_run_smoke_cells`, `_run_full`). `subprocess.run` is wrapped inside a new `_invoke_subprocess_with_status_mapping(cmd, timeout)` helper; a `subprocess.TimeoutExpired` maps onto `status="failed"` with `exit_code=None` and a reason distinguishable from a non-zero exit, never raising.
   - **Gap 1 (a real child):** `TestRealChildProcess` spawns genuine `python -c ...` children (no `monkeypatch` of `subprocess.run`) through that same helper: a non-zero exit, a timeout, and a child that dies attempting to allocate. **Finding:** requesting `bytearray(10**20)` makes CPython raise `OverflowError` ("cannot fit 'int' into an index-sized integer"), *not* `MemoryError` — `bytearray()`'s constructor checks the requested size against `Py_ssize_t` before ever asking the allocator for memory, so the child dies in ~15 ms with exit code 1 and places no real memory or pagefile pressure on the machine. This is a deliberately bounded, single-shot observation, not the slow incremental-growth-toward-the-ceiling scenario D-33 describes — that scenario is explicitly deferred to the actual wave-3 production run, per this environment's concurrency-safety rule (other executor agents run in parallel worktrees on this box and must not be destabilized).
   - **Gap 3 (paged success):** a new `memory_pressure` column (34 → 35 `GRID_COLUMNS`) takes one of three values — `MEMORY_PRESSURE_CLEAN` ("clean"), `MEMORY_PRESSURE_NEAR_CEILING` ("near_physical_ceiling"), `MEMORY_PRESSURE_REFUSED_PREFLIGHT` ("refused_preflight") — explicitly a measurement *condition*, never a pass/fail verdict (D-12 stands; no verdict column exists anywhere in this module's output). `_classify_memory_pressure` compares each cell's worst commit/peak reading against `MEMORY_NEAR_CEILING_FRACTION = 0.5` of physical RAM. A new pre-flight guard, `_preflight_ceiling_reason`, projects Stage-3's dense-Jacobian memory from problem shape alone (`n_residuals = 2 * n_cameras * n_frames * MAX_CORNERS_PER_VIEW`, `n_params` from the shared-interface packing layout, scaled by `JACOBIAN_MEMORY_MULTIPLIER = 7.0` — derived from plan 19.2-06's measured 9.78 GiB whole-run against a 1.40 GiB dense Jacobian) and refuses a cell as a recorded `status="failed"` row *before* `calibrate_synthetic` is ever called when the projection exceeds `MEMORY_CEILING_FRACTION = 0.75` of this machine's RAM. Verified via a test that monkeypatches `calibrate_synthetic` to raise if called and drives a fabricated 1000×1000-camera/frame shape through `run_grid_cell`.

## Decisions Made

- `CELL_TIMEOUT_SECONDS = 20 * 60` — see key-decisions above for the full derivation.
- `MEMORY_CEILING_FRACTION = 0.75`, `MEMORY_NEAR_CEILING_FRACTION = 0.5`, `JACOBIAN_MEMORY_MULTIPLIER = 7.0` — all module constants with derivation comments citing plan 19.2-06's measurement.
- The allocating-child test intentionally uses a single-shot, address-space-exceeding allocation request rather than incremental growth toward this box's physical ceiling, because other executor agents run concurrently in parallel worktrees on the same machine and the environment's safety rules explicitly forbid deliberate allocation near the physical limit. The observed failure mode (`OverflowError` at the Python level, not an OS-level `MemoryError` or kill) is recorded honestly as a limitation: the slow-paging scenario D-33 actually cares about has not been directly observed on this machine and remains for the wave-3 production run to surface, guarded now by the pre-flight ceiling and the timeout.
- CR-01's "every E4 fixture uses `status='ok'`" claim is corrected (see Accomplishments #2) rather than re-asserted.
