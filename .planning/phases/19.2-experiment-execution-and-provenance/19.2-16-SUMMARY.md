## Source-level confirmation (CR-02, WR-08)

At EXPECTED_BASE, the skip branch (lines 463-469) read:

```python
if config_path.exists() and not force:
    logger.info(...)
    return {"status": "skipped_existing", "status_reason": "", "metrics": None}
```

This returns a fixed synthetic outcome without ever opening `config_path` — CR-02's substance is confirmed: `metrics` is always `None` and `status_reason` is always `""` on a `force=False` re-entry, regardless of what the checkpoint actually recorded. `_run_check`'s reconstitution (lines 634-646 at EXPECTED_BASE) already does the correct read a few lines away (`cached.get("metrics")`, `cached.get("status_reason", "")`), which is exactly the proof cited in the plan's `<read_first>`.

New tests `test_resume_returns_cached_ok_metrics` and `test_resume_returns_cached_failed_reason` fail against EXPECTED_BASE for exactly this reason (confirmed: 11 new tests failed before the fix, 11 passed after).

## Decision taken: failed checkpoints remain skip candidates

The plan required an explicit choice on whether a checkpoint recorded as `status="failed"` should be retried automatically on the next `force=False` invocation. **Decision: keep it as a skip candidate** (do not auto-retry). Rationale: this keeps `run_configuration`'s skip branch a single uniform read site for every recorded status, rather than adding a second special case; and it makes a resumed sweep's timing predictable (an interrupted run that hit a known-bad configuration doesn't silently re-attempt it and burn calendar time on every resume). The cost, documented explicitly in the docstring, is that a failure is never retried without an explicit `--force`. WR-08's recommended alternative (treat a failed checkpoint as NOT a skip candidate) was read, understood, and rejected here — recorded so it is not silently reopened.
