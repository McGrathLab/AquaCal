**User's choice:** `generate_real_rig_array` geometry.

### Q2 — How do E5 and E6 share runs?

**Initial framing was withdrawn.** The first version of this question recommended a shared
result cache, following the brief's "run them together, not twice." The user asked *"how much
time would a shared results cache actually save?"* — and the arithmetic did not support the
recommendation:

- E5's band (±0.01 at ~0.002 steps ≈ 11 points) and E6's index axis (1.33→1.55 at ~0.03 steps
  ≈ 6–8 points) coincide at **exactly one configuration**, the 1.333 baseline.
- Q1's decision put E5 on real-rig geometry while E6's axes run on `generate_camera_array`
  families, so even that one point has a different cache key and shares nothing.
- At ~2–10 min per run (from 19.1's measured E1/E7 runtimes) across ~29 configurations, the
  cache saves **under 5% of wall-clock, plausibly 0%**.

The recommendation was retracted and the question re-asked:

| Option | Description | Selected |
|--------|-------------|----------|
| Independent scripts, no sharing | Two self-contained scripts, each mapping one-to-one to its requirement; rely on D-24's within-script resumability, which is where the real saving is. | ✓ |
| Share anyway, cheap insurance | A cache-key change to existing machinery; but couples two scripts for <5%, and wrong keys mean silent cross-reuse — a correctness risk for minutes. | |
| Put E6's index axis on real-rig geometry too | Makes the overlap real; but breaks E6's "one-dimensional through a common baseline" design. | |

**User's choice:** Independent scripts, no sharing.
