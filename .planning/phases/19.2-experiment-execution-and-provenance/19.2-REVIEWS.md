# Cross-AI Plan Review — AquaCal Phase 19.2

## 1. Summary

This is a strong plan set — considerably above average in provenance discipline, and the amendment history shows the planners already caught two real defects (the hardcoded `validation_3d_error_*` zeros, the `calibrate_synthetic` index-threading bug) that would have published fabricated or null data. The wave structure is coherent, the CLI contract is uniform, and the "one number, one origin" rule is enforced with grep gates rather than prose in most places. However, I found **five HIGH-severity problems that survive into committed artifacts**, three of which are exactly the failure classes the review brief flagged as fertile ground. The most serious: E4's grid runs a *different solver configuration* than the six `tab:cpr` rows it is supposed to supply, so D-16's split silently orphans four of six rows and would regenerate a supplement aside from the wrong configuration; E4's per-cell peak-memory columns are process-cumulative and therefore meaningless for cells 2–9; and E4's OOM story is structurally unachievable. Separately, EXP-11's `seed` requirement is not actually met by any benchmark record, and plan 12's provenance test is written so that it passes anyway.

## 2. Strengths

- **D-23 and the D-14 amendment are excellent catches.** Both were silent-data-corruption bugs (a null index axis; two fabricated zeros in a published accuracy column), and both are now guarded by grep gates that fail loudly rather than by reviewer attention.
- **The declared-constants table living in `tests/` (D-18) is the right call**, and plan 04's insistence on `read_via ∈ {call, signature_default, source_regex}` with at most one regex row, plus a structural test rejecting `:<digits>` in any `source` field, is a genuinely well-designed anti-rot mechanism.
- **D-19's "share the loop, don't duplicate it"** with a grep gate asserting `f_prime = n_air * h_c` appears exactly once is a precise, checkable formulation of a requirement that is usually left as an aspiration.
- **Plan 06's `git diff 5762d6d..HEAD -- src/` launch gate**, encoded as a hard acceptance criterion rather than relying on wave placement, correctly survives a replan. T-19.2-26 in its threat register is the best-reasoned entry in the whole set.
- **D-04's "every declared cell emits a row"** and P4's "the sweep is data, not control flow" (literal `DECLARED_CELLS` / `N_ASSUMED_BAND` / axis-value lists, with `git diff` gates proving the ranges were not adjusted after seeing results) are the right structural defenses against post-hoc range selection.
- **D-12's refusal to bake a pass/fail column into E6**, with a unit test rejecting any verdict-implying column name, is disciplined and correct.
- **Acceptance criteria are unusually checkable** — mostly `python -c` one-liners and grep counts rather than "the output looks right." The exceptions are noted below.

## 3. Concerns

### HIGH

**H1 — E4's grid cannot supply the four `tab:cpr` rows D-16 assigns to it; the split orphans them.**
*Location: 19.2-07 Task 1/2; 19.2-05 Task 3 (`CPR_CONFIGS`, `test_cpr_rows_exclude_e4_grid`); 19.2-12 Task 2 (README split note) and Task 3 (derived aside).*

All six `tab:cpr` rows are tilt-enabled configurations — the source brief lists them as `(3,3,tilt)`, `(16,200,tilt)`, `(8,100,tilt+intrinsics)`, `(12,100,tilt+intrinsics)`, `(13,200,tilt+intrinsics)`, `(16,200,tilt+intrinsics)`, and `tests/unit/test_optim_common.py:193` confirms "tilt" means `normal_fixed=False`. But:

- `schema.py:333` — `interface_normal_fixed: bool = False`, so E2's real-rig run is tilt-enabled. Consistent with `tab:cpr`.
- `interface_estimation.py:142` and `refinement.py:57` — `normal_fixed: bool = True`, and `calibrate_synthetic` (`pipelines.py:109-127, 141-156`) never passes it. **E4's nine cells therefore run tilt-FIXED.**

So E4's `n_params_*` columns are the `normal_fixed=True` variants, differing from the published `tab:cpr` values by exactly the 2 tilt parameters. Consequences, all live:
- ROADMAP SC1's "`cpr_grouping.csv` covering the six existing `tab:cpr` rows" is **not met** — plan 05 emits only 2 configurations, and `test_cpr_rows_exclude_e4_grid` actively *enforces* that the other four are absent.
- Plan 12 Task 2 will write a README subsection documenting a split that does not hold, and its stated purpose is precisely "so the omission cannot be mistaken for an oversight."
- Plan 12 Task 3 regenerates D-22's "40 to 42× from eight to twelve cameras" aside from `benchmark_grid.csv`'s 8- and 12-camera rows — i.e. from the wrong configuration. That is a hand-carried number replaced by a *machine*-carried wrong number, which is worse.
- `solver_config` in the record carries `refine_intrinsics` and `shared_interface` but **not** `normal_fixed` (verified in `experiments/results/e1_benchmark_refractive.json:24-34`), so nothing in the committed artifact would reveal the mismatch.

**H2 — E4's per-cell peak-memory columns are process-cumulative, not per-cell.**
*Location: 19.2-07 Task 1 (`run_grid_cell`), Task 2 (`peak_bytes_*` columns); 19.2-09 Task 1.*

`capture_peak_memory()` (`io/benchmark.py:172-243`) returns `psutil.Process().memory_full_info().peak_wset` on Windows — a **process-lifetime** high-water mark, and its docstring says so explicitly ("monotonically non-decreasing across calls within one process"). Plan 09 runs all nine cells in one process. Therefore for cells 2–9, `_baseline` already carries the running maximum of every prior cell, `peak_bytes_stage3_*` is contaminated, and `delta_bytes_since_previous_boundary` (`io/benchmark.py:396`) degenerates to "growth beyond the largest previous cell" — near zero for any cell that isn't a new maximum. Worse, plan 09 explicitly encourages resumption without `--force`, so which cells contributed to a given cell's baseline depends on the interruption history, making the column non-reproducible.

Meanwhile E2's tenth row *is* a genuine single-run peak. This is precisely the comparability problem D-06 was introduced to fix, reintroduced in the same column. And it is a **silent null**: because the grid iterates in ascending cost order, the contaminated numbers will look monotone and plausible. Nothing in plans 07, 09, or 12 would catch it.

**H3 — E4's OOM failure path is unachievable as designed.**
*Location: 19.2-07 Task 1 (`try/except Exception`, `status="failed"`); 19.2-09 Task 1 (resume instructions).*

D-04's guarantee is that the 16×200 cell, identified as the memory risk on a 16.9 GB box, records `status=failed` with a `status_reason` rather than vanishing. But a Windows OOM or allocation failure in a NumPy `.toarray()` of a ~3.6 GB-class dense Jacobian typically kills the process; `except Exception` cannot observe it. Plan 09 Task 1 concedes this ("If the process dies partway through — an OOM on the 16×200 cell is the anticipated failure — re-launch the SAME command WITHOUT `--force`"), but on resume the cell is retried and dies the same way. There is no state in which the OOM cell ever produces a `failed` row, and plan 09's automated verify asserts all nine declared pairs are present — so the anticipated failure mode deadlocks the plan rather than being recorded.

**H4 — Wave 3 runs two long production benchmarks concurrently on one machine.**
*Location: wave 3 = 19.2-08 (Task 3 runs the full E5 band), 19.2-09 (the nine-cell grid), 19.2-10 (`--smoke`).*

E4 is a *wall-clock and peak-memory* benchmark. Nothing in plans 08, 09, or 10 forbids concurrent execution, and GSD's default is to run a wave's plans in parallel. Constraint 11 ("one machine for the whole E4 grid") is about machine *identity*, not quiescence — it is satisfied by, and provides no protection against, running E5's eleven calibrations alongside E4's grid on the same 20-core / 16.9 GB box. That contaminates every timing in `benchmark_grid.csv` (the headline R1.5/R3.2 answer) and materially raises the odds of H3's OOM. Plan 09's "do not modify any file under `src/` or `experiments/`" mid-run shows the authors thought about run isolation but only for code, not for load.

**H5 — EXP-11's `seed` requirement is not met, and plan 12's test is calibrated to pass anyway.**
*Location: 19.2-12 Task 1 (`REQUIRED_ENVIRONMENT_KEYS`, the six behaviors).*

ROADMAP SC5 and EXP-11 require every committed result to carry "its seed, AquaCal version, git SHA, and environment." Verified against the real artifact: `experiments/results/e1_benchmark_refractive.json` contains no `seed` key anywhere — `assemble_benchmark_record` emits `schema_version`, `problem_shape`, `stages`, `solver_config`, `accuracy`, `environment`, `memory`, and none carries it. Nor do `GRID_COLUMNS` (19.2-07), `E5_COLUMNS` (19.2-08), or `E6_COLUMNS` (19.2-10). The only artifact in the phase that records a seed is `e3_provenance.json`.

Plan 12's behavior list asserts `environment` key-presence for benchmark records and `seed` only for the E3 sidecar — so the test passes without the requirement being satisfied. This is the review brief's "guards that only test the paths that were already going to pass," applied to the phase's own headline deliverable. Note also that plan 12 forbids re-running E1/E7, and constraint 10 declares the schema settled, so the fix has to be deliberate (an additive `seed` in `solver_config` for new records, plus an explicit recorded carve-out for E1/E7's existing ones).

### MEDIUM

**M1 — Plan 05's 13/200 `cpr_grouping.csv` rows are arithmetically inconsistent and one reading fabricates a value.**
*Location: 19.2-05 Task 3.* The action declares two `CPR_CONFIGS`, each "emitted twice — once with `shared_interface=True` and once with `shared_interface=False`," and acceptance requires 4 rows with "exactly 2 rows [having] `record_source` equal to `copied_from_e2_benchmark`." Under that reading, the **per-camera** 13/200 row is also copied from E2's record — but E2 ran shared-interface only, so the per-camera row would carry the shared-interface numbers. That is a fabricated value in a published table. Separately, E2's record has two stages with different counts (`stage3_interface_optimization` vs `stage3_intrinsic_pass`); the plan never says which supplies the 13/200 row, and only the intrinsic pass matches `tab:cpr`'s "tilt+intrinsics" descriptor.

**M2 — E6's "scale" axis is neither one-dimensional nor a scale change.**
*Location: 19.2-10 Task 1 (`SCALE_AXIS_VALUES`); 19.2-07 Task 1 (`build_grid_scenario`'s signature).* The axis varies `depth_range` and `xy_extent` together while camera `spacing` (0.1 m), `height_above_water` (0.15 m), and the board's `square_size` (0.060 m) stay fixed — `build_grid_scenario` exposes no keyword for any of them. So the axis changes the *ratio* of working volume to camera baseline and to board size, not scale. D-11 calls it "tank size / working distance"; a reviewer asking "does the method generalize to a larger tank" would reasonably expect the rig to scale with it. Either rename the axis to what it measures (working-volume-to-baseline ratio) or add `spacing`/`height_above_water` to `build_grid_scenario` in plan 07.

**M3 — E4 records no observation count, and the grid family's geometry changes with `n_cameras` in ways the plan does not acknowledge.**
*Location: 19.2-07 Task 2 (`GRID_COLUMNS`).* Verified in `synthetic.py:165-190`: the grid layout is `side = ceil(sqrt(n_cameras))` at fixed 0.1 m spacing, then re-centered so **cam0 (a corner camera) sits at the origin**. Footprint therefore grows from ~0.2 m (8 cameras) to ~0.3 m (16), while `generate_board_trajectory`'s `xy_extent=0.15` keeps the board near cam0 — so the *fraction of cameras that observe the board* changes across cells, and asymmetrically. D-03's "only the two swept variables change" is not true in the way that matters for a scaling curve. The source brief explicitly lists `n_observations` in the per-run metric list; `GRID_COLUMNS` omits it. Without it, a cell in which half the array saw nothing is indistinguishable from a healthy point. (`n_residuals` helps but is not decomposed per camera.) Also: `generate_camera_array`'s own docstring says "Number of cameras (2-14)" — 16 is outside the documented range, and no plan notes it.

**M4 — E4's 12-camera cell and E6's baseline are the same scene, run twice, with both accuracy numbers published.**
*Location: 19.2-07 Task 1 (`build_grid_scenario`), 19.2-10 Task 1 (`BASELINE_N_CAMERAS=12, BASELINE_N_FRAMES=100`).* Sharing the *builder* is good, but the consequence is that `benchmark_grid.csv` and `generalization_sweep.csv` will both carry a `reprojection_rms` for the identical configuration. If they differ (different held-out sets, `evaluate_calibration` vs the record's `accuracy` block), a reader sees two numbers for one configuration — the D-16 violation, applied to accuracy instead of CPR. No plan cross-checks them. Cheap fix: have plan 11 assert the baseline row agrees with `benchmark_grid.csv`'s 12/100 cell, or drop accuracy from one of the two.

**M5 — `water_z_error_mm_mean` has no specified source.** *Location: 19.2-10 Task 2 (`E6_COLUMNS`).* `compute_per_camera_errors` returns `focal_length_error_pct`, `z_position_error_mm`, `xy_position_error_mm`, `k1_error`, `k2_error`, the gt/est positions, and `reprojection_rms_px` — no water_z error. The column must be computed in the script from `result` vs `scenario.water_zs`, and the plan never says so. It is the single most diagnostic metric for the index axis (index error couples directly into recovered interface depth), so leaving it under-specified risks it landing as null or as an inconsistent hand-rolled quantity.

**M6 — E5's yardstick mixes two experiments' error scales.** *Location: 19.2-08 Task 2 (`load_holdout_floor_pct`, `scale_bias_over_floor`).* The numerator is a *bias* from a **synthetic** 12-camera run at `noise_std=0.5 px`; the denominator is E2's **real-rig** held-out **RMSE**. Reading the live value rather than hardcoding 0.674 is right, but the ratio compares a signed bias on one dataset to a noise magnitude on another. The band's Δn = 0 row is the correct internal control and it is present — but no column expresses the bias relative to *it*, which is the comparison that actually isolates the index effect.

**M7 — E6 has no per-configuration resumability, despite being the longest sweep.** *Location: 19.2-11 interfaces block, which concedes "FILE-level, not row-level — an interrupted E6 run has no per-row resume, so a full restart is the recovery path."* E4 got per-cell `benchmark.json` files precisely for this. E6 is both the largest sweep and the designated calendar-fallback casualty, so it is the one that most needs to survive an interruption.

**M8 — Runtime estimates have no measured basis and look optimistic.** *Location: 19.2-09 objective ("minutes each"); 19.2-08 Task 3 ("a few minutes each").* The project's own record (`CLAUDE.md`, memory) is 48–87 min for a 13-camera × 200-frame calibration with **Stage 3 dominating** — and E4's 16×200 cell is a comparable Stage-3 problem. Skipping detection removes the smaller half. Nine cells plus eleven E5 points plus ~17 E6 configurations could plausibly be 15–30 hours of compute, not "a day." No plan runs a single representative cell first to calibrate the estimate before committing to the full sweep. Feasible in 24 days, but not with a re-run.

**M9 — E4's `--check` semantics are ambiguous.** *Location: 19.2-07 Task 3 ("compares a freshly built frame against the committed `benchmark_grid.csv`"); 19.2-09 Task 2 runs it.* If "freshly built" re-runs the nine cells, `--check` is a multi-hour operation and unusable in the pattern the other scripts establish; if it re-aggregates the existing per-cell records, it verifies the aggregation but not the run, and will trivially pass. Say which.

**M10 — Only one of three `f_scale = 1.0` sites is asserted.** *Location: 19.2-04 Task 1, `huber_f_scale_px` row.* The row reads `inspect.signature(optimize_interface).parameters["loss_scale"].default`. Verified live, there are three: `interface_estimation.py:140` (that default), `interface_estimation.py:720` (a hardcoded `f_scale=1.0` in auxiliary registration), and `refinement.py:53`. D-18 itself names two sites. CI would not break if the hardcoded one changed.

### LOW

**L1 — `scenario.name` is load-bearing and unpinned.** `calibrate_synthetic` (`pipelines.py:115-119`) branches on `scenario.name != "calibration"` to choose `initial_water_zs` between ground truth and a flat 1.0. `build_grid_scenario` takes `name: str | None = None` (19.2-07 Task 1) with no pinned value and no warning. A future scene named "calibration" silently changes Stage-3 initialization for every E4 and E6 cell.

**L2 — `from tests.unit....` is fragile.** `tests/__init__.py` exists but `tests/unit/__init__.py` does not; the import resolves via PEP 420 namespace-portion semantics and depends on the repo root being on `sys.path`. Both plan 04's acceptance criteria and plan 05's E3 script rely on it, including inside CI's `experiments-smoke` job. It will work from the repo root, but nothing asserts that precondition and the failure mode is an `ImportError` in CI rather than a clear message.

**L3 — Plan 08 edits E1 but never re-proves E1 reproduces.** *19.2-08 Task 1 Step 1* extracts `compute_scale_bias` out of `e1_refractive_comparison.py`. The guard is a unit test cross-checking three values against the committed CSV — good, but the natural full check, `python -m experiments.e1_refractive_comparison --check`, is never run.

**L4 — VALIDATION.md claims coverage it does not have.** The EXP-07 row "Tier-3 P / group counts for the six `tab:cpr` rows → ✅ existing (`test_optim_common.py:189-276`)" is wrong: `_DOCUMENTED_CONFIGS` is three configurations at 13 cameras × 100 frames, pinning `docs/guide/optimizer.md`'s numbers, not the six `tab:cpr` configurations. This is the same gap as H1, showing up as a green checkmark.

**L5 — D-08's premise is checked against the wrong base.** *19.2-06 Task 1/2.* The decision's argument rests on `git diff f193d60..HEAD -- src/` being empty; the mechanically enforced gate is `git diff 5762d6d..HEAD -- src/`. Those coincide only if nothing between `f193d60` and `5762d6d` touched `src/` — asserted in CONTEXT but never re-verified at launch. Have Task 1 check both. Also, Task 2 says "if ANY value has moved — including a value that moved by a fraction of a percent" but the acceptance criterion says "Every delta_pct in that table is `0.000%`," which is a *rounded display*. A 1e-14 relative move would display as 0.000% and pass, while the prose says halt. Decide which, and say so — a BLAS-reduction-order difference at that magnitude is a plausible false positive that would otherwise halt the phase.

**L6 — `GRID_COLUMNS` asymmetry.** `n_residuals_*` and `jacobian_elements_*` exist for `stage3_interface_optimization` only, not for `stage3_intrinsic_pass`, even though the intrinsic pass is the larger problem and the one `tab:cpr`'s "tilt+intrinsics" rows describe. And no column records `normal_fixed`/`shared_interface`, so the CSV does not self-describe its own configuration (see H1).

## 4. Suggestions

1. **Fix H1 before wave 2.** Either (a) add a `normal_fixed` parameter to `calibrate_synthetic` and run E4 with `normal_fixed=False` so its cells match `tab:cpr` and the real pipeline's default — this is a small, guardable additive change of exactly the kind plans 01–03 already make; or (b) accept the mismatch, extend `CPR_CONFIGS` in plan 05 to cover all four orphaned rows (tier 3 builds sparsity patterns, it does not calibrate — this costs seconds), and rewrite D-16's split as "E3 owns every `tab:cpr` row; E4's CPR columns describe E4's own tilt-fixed configuration and are labeled as such." (b) is cheaper and lower-risk this close to the deadline. Either way, add `normal_fixed` and `shared_interface` to `GRID_COLUMNS` and to `solver_config`.
2. **Fix H2 and H3 together by running each E4 cell in a subprocess.** `python -m experiments.e4_benchmark_grid --cell 16x200` invoked from the parent gives a true per-run `peak_wset`, makes an OOM a non-zero exit code the parent *can* record as `status=failed` with a reason, and preserves the existing per-cell resumability. This is the single highest-value change in the review.
3. **Fix H4 by making the production runs sequential and explicit.** Move 19.2-08 Task 3 (E5's band) and 19.2-11 (E6's sweep) into waves strictly after 19.2-09 completes, and add an acceptance criterion to plan 09 Task 1: no other AquaCal experiment process is running during the grid, verified before launch and at completion.
4. **Fix H5 by adding `seed` to `solver_config` in `assemble_benchmark_record`** (additive, does not break `_render.aggregate`'s schema check), threading it from `write_direct_call_benchmark`, and adding a `seed` column to all three new CSVs. Then strengthen plan 12's `REQUIRED_ENVIRONMENT_KEYS` test to assert seed presence, with E1's and E7's pre-existing records listed in an explicit, commented carve-out set rather than passing by omission.
5. **Add `n_observations` and a per-camera coverage figure to `GRID_COLUMNS`** (M3), and have plan 09 Task 2 record min/median observing-cameras-per-frame per cell. If a 16-camera cell turns out to have half its array blind, that is a finding the manuscript needs, not a curve point.
6. **Smoke-test one real 16-camera cell before committing to the full grid.** Add a task to plan 07 that runs `build_grid_scenario(16, 50, 42)` through `calibrate_synthetic` once, records wall-clock and peak memory, and reports both. It de-risks H3, M3, and M8 in under an hour and calibrates every downstream estimate.
7. **Pin `scenario.name`** in `build_grid_scenario` and `build_real_rig_scenario` to a value that is provably not `"calibration"`, with a comment naming `pipelines.py`'s branch (L1).
8. **Resolve M1 explicitly** in plan 05: state which E2 stage supplies the 13/200 row, and require the per-camera 13/200 row to be `computed` (E3 can build that sparsity pattern in seconds) with `record_source` reflecting it. Add an acceptance criterion that no row is `copied_from_e2_benchmark` unless E2's record actually ran that configuration.
9. **Give E6 per-configuration resumability** — one small JSON per configuration under `results/e6_configs/`, mirroring E4's mechanism (M7).
10. **State E5's Δn = 0 control as an explicit column** (`scale_bias_pct_at_zero_delta`, or a `bias_over_control` ratio) alongside the real-rig floor, so the argument does not rest solely on a cross-dataset comparison (M6).

## 5. Risk Assessment

**HIGH.**

Not because the plan is poorly built — it is well above average, and most of the machinery for catching this class of problem is already in place. The rating reflects three things. First, H1, H2, and H5 each produce a *committed, publishable artifact that is wrong or unverified while looking correct*, which is the exact failure mode the phase exists to eliminate, and none of the twelve plans' gates would catch any of them. Second, H3 and H4 threaten the E4 production run specifically, and E4 is both the longest run and the input to plan 12's close-out, so a defect discovered after the grid completes costs a re-run the calendar cannot absorb. Third, the compute estimates (M8) have no measured basis and the project's own history says a comparable calibration takes 48–87 minutes, so the schedule has less slack than the plans assume.

The mitigating factor is that all five HIGH items are fixable at the *planning* level, mostly in wave-1 or wave-2 plans that have not executed yet, and suggestions 1, 2, 3, 4, and 6 together would drop this to LOW–MEDIUM for perhaps a day of replanning plus one hour of smoke compute. Doing that before wave 2 starts is, on my reading, clearly cheaper than discovering H1 or H2 during manuscript assembly in August.
