<objective>
Make every silent discard in the calibration path countable, and surface the totals in
`diagnostics.json`.

**Why now, and why this blocks plan 19.2-06.** Plan 06's amended D-34 gate requires the executor to
confirm the degenerate-PnP guard rejected **exactly 10 of 3538 poses** before accepting any moved
section-3 number. That gate is currently **unrunnable**: the guard is completely silent. It
`return None` at `extrinsics.py:203` and `:214`, and all four call sites (`441`, `498`, `665`,
`721`) do a bare `if result is None: continue`. Verified live 2026-07-31: `grep 'logger\.'
src/aquacal/calibration/extrinsics.py` returns **zero hits**, and so does the same grep over
`pipeline.py`, `frame_rejection.py`, `_optim_common.py`, `intrinsics.py`, and all of `core/`. The
"10 of 3538" figure in `.continue-here.md` came from ad-hoc instrumentation during the 2026-07-30
debugging session and **cannot be reproduced from any committed artifact or run log**.

So plan 06 as amended would halt 100% of the time — it fails closed, which is safe, but it does not
run. This plan is the minimum change that makes the mechanism observable.

**The general defect, stated once.** A discard that no artifact records cannot be audited after the
fact. The calibration path currently drops observations, poses, and video frames at nine sites
without recording a single count anywhere. Every one of those is a silent change to what the solve
sees, and therefore a silent change to a published number. This plan closes the ones outside the
hot numeric path.

**Scope discipline — what is deliberately NOT in this plan.** The three total-internal-reflection
branches in `core/refractive_geometry.py` (lines 122, 225, 307) are also silent, and are also worth
counting. They are **excluded** because they sit in the per-point projection path, which runs
~10^5 points x tens of iterations per solve. A counter there risks moving `benchmark.json`'s
wall-clock — and E4's nine-cell grid (`5b17cd4`) and E2's timings are already committed and
published. Recorded as a follow-up, not silently dropped. If a future plan adds them, it must
either vectorise the count or re-run every timing artifact.

**`frame_rejection` is likewise NOT in scope, because it is already solved.** `FrameRejectionResult
.to_diagnostics_dict()` reaches `diagnostics.json` through `save_diagnostic_report(frame_rejection=
...)` at `pipeline.py:1659`. The pre-guard baseline survives in
`C:/Users/tucke/Desktop/Aqua/AquaCal/release_calibration/diagnostics.json`, which plan 06 already
protects with an mtime assertion. Do not duplicate it.

**Re-deriving the real-rig "10 of 3538" is NOT in this plan — and this is a deliberate, flagged
trade.** An earlier draft carried a third task that would have measured the pair against the local
release frameset. It was removed on review: `discard_stats` only reaches `diagnostics.json` after a
COMPLETE pipeline run (see `<interfaces>`), so that task was a second 48-87 min box-exclusive
production run in disguise — unmarked as such, and carrying none of the protocol this phase learned
the hard way (detached launch, quiescence checks, duplicate-process scan). It would have doubled the
critical path ahead of E2.

The confirmation therefore happens inside **plan 19.2-06's own run**, where `diagnostics.json` is
produced anyway. **State the residual risk plainly rather than letting it pass unnoticed:** the
*expected* value 10/3538 still rests on prose in `.continue-here.md`, written from instrumentation
that no longer exists. That is a real check — the expected value is independent of the run being
gated, so a disagreement is still informative — but it is weaker than a measurement with recorded
provenance. If plan 06's run reports a different pair, **the handoff figure is a candidate for being
wrong, on equal footing with the run**; adjudicate, do not assume the run is at fault.

This plan's own counter-correctness evidence comes from synthetic fixtures with KNOWN degenerate
poses (Task 2B), which is cheap, deterministic, and does not depend on the real frameset at all.

threaded to the functions that own the sites in `<interfaces>`. When `None` (the default), behaviour

**Counter names must distinguish failure modes, not merge them.** `extrinsics.py:203` (non-finite LM
result) and `:214` (the projection self-check) are different defects with different diagnoses;
collapsing them into one "pnp_failed" counter would make plan 06's gate unable to tell which

  pnp_solve_failed                    -- solvePnP returned success=False (extrinsics.py:155 path)

  pnp_guard_rejected                  -- extrinsics.py:214  <-- the one plan 19.2-06 reads

  observation_absent                  -- the four `obs_maybe is None` sites (denominator, not anomaly)

                                         wrong in a published artifact.
  interface_pnp_failed                -- interface_estimation.py:495
  video_frame_unreadable              -- intrinsics.py:308

**`pnp_attempts_total` — count BOTH branches, and say so.** Each of the four call sites branches
between `estimate_board_pose_refractive` and the non-refractive `estimate_board_pose`. The
denominator must count **every** pose attempt across both branches. If it counted only the
refractive branch, it would not read 3538 on a run that uses both — and plan 19.2-06 routes a
differing denominator to an *input* diagnosis (wrong frameset), sending the investigation in
entirely the wrong direction for what would actually be a counter-scoping bug. Record
`pnp_attempts_refractive` and `pnp_attempts_nonrefractive` separately as well, so the split is
visible rather than inferred.

**State and test the producer/consumer invariant.** `pnp_guard_rejected` and friends count
rejections where they are *produced*; `pose_discarded_by_consumer` counts them where they are
*consumed*. Every produced rejection is consumed exactly once, so:

    pose_discarded_by_consumer == pnp_solve_failed + pnp_nonfinite_refinement + pnp_guard_rejected

This redundancy is deliberate — it is a cross-check, not duplication. Without the stated invariant
an executor could ship two numbers that disagree and nobody would know which one the gate should
read. Assert it in Task 2.

**Hard constraints on the implementation.**

1. **No control-flow change.** A counter increments; nothing else moves. No branch is added,
   removed, or reordered. No pose, residual, or projection is altered.
2. **No counter inside a per-point or per-residual loop.** Every site listed is per-(camera, frame)
   or per-video-frame, which is safe. If instrumenting a site would require entering a per-point
   loop, **stop and report** rather than doing it — published wall-clock must not move.
3. **No module-level or global mutable state.** The out-parameter is the mechanism. A module-level
   counter would leak across calls, break under any future parallelism, and make test isolation
   impossible.
4. **`None` default everywhere.** Any caller that does not opt in sees today's exact behaviour.

Then surface it: `pipeline.py` allocates the dict, passes it down, and hands the populated result to
`save_diagnostic_report(..., discard_stats=...)` alongside the existing `frame_rejection`. Add the
parameter to `save_diagnostic_report` with a `None` default so existing callers are unaffected.

Emit **one** summary log line per run — not per event — after the counts are final. Per-event
logging at these sites would produce thousands of lines on a real rig and would itself cost
wall-clock. The log line is a convenience; **`diagnostics.json` is the load-bearing artifact**,
because a gate can assert on a field and cannot assert on a log.

Two independent obligations. **Do not let the second substitute for the first** — a test that the
counters are right says nothing about whether the numbers moved.

**A. Inertness, by exact equality.** Run a full deterministic calibration twice on the same seeded
synthetic scenario: once without `discard_stats_out`, once with it supplied. Assert **exact
equality** — `==` or `assert_array_equal`, never `allclose` — on every extrinsic, every board pose,
every `water_z`, and the final residual vector. A tolerance-based comparison would pass on a change
that genuinely moved a number in the last bits, which is exactly the claim under test.

Additionally assert exact equality against a **frozen anchor**, so the guarantee survives a future
refactor that changes both branches together.

**The anchor must be captured from code that does not contain this plan's edit — and the plan is
the thing making that edit, so the ordering is not optional.** An anchor captured after editing is
self-confirming and passes trivially against any change, including a wrong one. Use ONE of:

- **Preferred:** before touching any source file, generate the anchor from the clean base checkout
  and commit it as a fixture in its own commit. The commit ordering is then the evidence — `git log
  --follow` shows the anchor predates the source edit.
- Or generate it from a separate worktree pinned at the base sha (`git worktree add <dir>
  <base-sha>`), with `PYTHONPATH` exported to that worktree — verify with
  `python -c "import aquacal; print(aquacal.__file__)"`, because the editable install otherwise
