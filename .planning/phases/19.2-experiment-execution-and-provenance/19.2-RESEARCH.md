# Phase 19.2: Experiment Execution and Provenance - Research

**Researched:** 2026-07-28
**Domain:** Scientific experiment scripting over an already-instrumented calibration library (synthetic sweeps, code-constant assertions, provenance)
**Confidence:** HIGH for existing-API shapes (all read from live source); MEDIUM-LOW for two load-bearing gaps flagged below that CONTEXT.md did not anticipate

## Summary

Phase 19.2 writes four new experiment scripts (E3, E4, E5, E6) on top of the `experiments/`
scaffold Phase 19.1 shipped, following the exact CLI/CSV/benchmark-json conventions E1/E7
already established. Most of the plumbing CONTEXT.md assumes is real and verified in this
session: `assemble_benchmark_record`, `capture_solver_diagnostics`'s `n_params`/`n_groups`
threading, `build_structural_column_groups`, `pack_params`, and the Newton root-finder's
tolerance/iteration-count constants all exist exactly as described, with a test helper
(`tests/unit/test_optim_common.py::_make_pattern`) that already builds an arbitrary sparsity
pattern without running a calibration — this is the direct precedent E3 tier 3 should copy.

Two findings are **not** covered by CONTEXT.md and are load-bearing for planning:

1. **D-03's claim that a `generate_camera_array(layout="grid", n_cameras=12)` cell can match
   `create_scenario("realistic")` "exactly" is false by inspection.** `create_scenario("realistic")`
   calls `generate_real_rig_array()`, a completely different generator (fixed real-rig XY
   positions, averaged real intrinsics, image size 1600x1200) — not `generate_camera_array` at
   all. These two generators cannot produce the same scene under any parameterization. See
   Contradictions Found.
2. **`calibrate_synthetic` cannot generate ground truth at one refractive index and calibrate
   at another** — its internal call to `generate_synthetic_detections` omits `n_air`/`n_water`
   entirely (always uses the function's default `n_water=1.333`), while the `n_water` parameter
   of `calibrate_synthetic` only ever reaches the *calibration* (Stage 2/3) side. E5's stated
   procedure ("generate ground truth at `n_true`, calibrate assuming `n_assumed`") cannot be
   built by calling `calibrate_synthetic` as-is. E5 must be a direct-call script (like E7),
   not a `calibrate_synthetic` wrapper, or `calibrate_synthetic` needs a new parameter.

**Primary recommendation:** Build E4 as direct calls to `generate_real_rig_array` /
`generate_camera_array` + `calibrate_synthetic` + `assemble_benchmark_record`, matching E1's
pattern, but resolve the D-03 contradiction with the user/planner before coding: either the
12-camera cell uses `generate_camera_array(n_cameras=12, layout="grid")` on its own terms (not
"matching realistic exactly"), or E4's 12-camera cell literally *becomes* `generate_real_rig_array()`
(abandoning "grid" for that one cell only). Build E5 as a direct-call script bypassing
`calibrate_synthetic`, following E7's pattern of calling `generate_synthetic_detections`,
`estimate_extrinsics`, `optimize_interface`/`joint_refinement`, and `evaluate_calibration`
directly with independently-controlled true/assumed indices.

## A. E5's evaluation path (EXP-09)

### A.1 `evaluate_calibration` — signature, contract, existing caller

`src/aquacal/validation/evaluation.py:88-151`:

```python
def evaluate_calibration(
    calibration: CalibrationResult,
    detections: DetectionResult,
    board: BoardGeometry,
    min_corners: int = 8,
    cameras: set[str] | None = None,
    board_poses: dict[int, BoardPose] | None = None,
    include_reconstruction: bool = True,
) -> HeldOutEvaluation
```

`HeldOutEvaluation` (`:36-54`) has fields `reprojection: ReprojectionErrors`,
`reconstruction: DistanceErrors | None`, `board_poses: dict[int, BoardPose]`,
`num_frames: int`.

**Confirmed by the module's own docstring (`:1-12`, `:105-111`)**: there is **no**
`n_water` override parameter. `n_air`, `n_water`, and `interface_normal` always come
from `calibration.interface` (i.e., whatever the calibration itself assumed). "The
different assumption is encoded in the held-out `detections` instead" — meaning the
caller must generate the held-out `DetectionResult` at the *true* index and pass it in;
`evaluate_calibration` estimates board poses via refractive PnP + per-frame refinement
using the calibration's own (possibly wrong) `n_water`, then scores reprojection/3D
reconstruction error. This IS the E5 evaluation mechanism, confirmed [VERIFIED: read
source + docstring's explicit example]. There is a runnable docstring example at
`:135-147` using `create_scenario("minimal", n_water=1.45)` — this is the closest
existing "different index" caller, though it is illustrative code in a docstring, not
a script.

### A.2 `evaluate_reconstruction` (pipelines.py) vs `evaluate_calibration` — which is right for E5

`aquacal.datasets.pipelines.evaluate_reconstruction` (`pipelines.py:206-227`):

```python
def evaluate_reconstruction(
    calibration: CalibrationResult,
    board: BoardGeometry,
    test_detections: DetectionResult,
) -> DistanceErrors
```

This is a **thin wrapper** around `compute_3d_distance_errors(..., include_per_pair=False,
include_spatial=True)` — it does NOT estimate board poses itself; it assumes the caller
already has board poses embedded appropriately (in practice E1 uses dense XY-grid poses
generated with known ground truth, not PnP-estimated poses). It returns only
`DistanceErrors`, no reprojection metrics, and has no `min_corners`/`cameras` filtering.

`evaluate_calibration` is strictly the richer, more general function: it estimates board
poses via PnP+refinement (needed because E5's held-out detections at `n_true` do not come
with known poses the calibration/optimizer already solved for), and returns BOTH
reprojection and reconstruction metrics plus the poses used. **`evaluate_calibration` is
the correct choice for E5** — it is also literally what Phase 16's roadmap entry and
`19.2-SOURCE-BRIEF.md` cite as E5's dependency ("`evaluate_calibration` as a standalone
callable ... the experiment calibrates at one index and evaluates against ground truth
generated at another"). `evaluate_reconstruction` is E1's tool (dense XY grids at known
poses), not E5's.

**Depth/scale bias**: `HeldOutEvaluation.reconstruction` (a `DistanceErrors`) is not
inspected in this session (module not read in full), but `compute_3d_distance_errors`
is called with `include_spatial=True`, matching E1's usage pattern which the pipeline
CSVs (`exp2_spatial_errors.csv`) turn into per-point signed errors with positions — this
is exactly the substrate a depth/scale-bias computation needs. **Recommend**: read
`aquacal/validation/reconstruction.py`'s `DistanceErrors` dataclass fields during planning
(not done in this research pass — flagged as an Open Question) to confirm whether a
"scale factor" or "signed mean depth error" is already a field (E1's
`exp2_depth_generalization.csv` schema has a `scale_factor` column, suggesting the
computation already exists somewhere reusable — check before hand-rolling it in E5,
per P2).

### A.3 GT-at-`n_true` vs calibrate-at-`n_assumed`: `calibrate_synthetic`'s gap

**This is the load-bearing finding for E5.** `calibrate_synthetic`
(`src/aquacal/datasets/pipelines.py:27-203`) calls `generate_synthetic_detections` at
lines 69-77:

```python
detections = generate_synthetic_detections(
    intrinsics=scenario.intrinsics,
    extrinsics=scenario.extrinsics,
    water_zs=scenario.water_zs,
    board=board,
    board_poses=scenario.board_poses,
    noise_std=scenario.noise_std,
    seed=seed,
)
```

Note: **no `n_air`/`n_water` kwargs passed.** `generate_synthetic_detections`'s defaults
(`synthetic.py:472-473`) are `n_air: float = 1.0, n_water: float = 1.333` — so detections
are *always* generated at 1.333 regardless of `calibrate_synthetic`'s own `n_water`
parameter, which is only threaded into `estimate_extrinsics` (Stage 2) and
`optimize_interface`/`joint_refinement` (Stage 3) — the *calibration* side. This is
intentional and correct for E1 (both the refractive and non-refractive models must
calibrate against the identical ground truth), but it means **`calibrate_synthetic` has
no way to vary the ground-truth index independently of the calibration's assumed index.**

E5 needs exactly that: GT at `n_true` (swept ±0.01 around 1.333), calibrated assuming
`n_assumed` (also swept, coincident with `n_true` at one point per D-10's arithmetic).
Two options, to be decided during planning:

1. **Add a new parameter to `calibrate_synthetic`** (e.g., `n_water_true: float | None
   = None`, defaulting to `n_water` when unset — preserving bit-identical behavior for
   every existing caller) that is threaded into the internal
   `generate_synthetic_detections` call instead of relying on its default. This keeps
   E5 inside the shared-verb pattern P2 prefers.
2. **Write E5 as a direct-call script**, following E7's `_build_shared_data`/`_run_arm`
   pattern exactly: call `generate_synthetic_detections(..., n_air=1.0, n_water=n_true)`
   directly, then `build_pose_graph`/`estimate_extrinsics`/`optimize_interface`/
   `joint_refinement` directly with `n_water=n_assumed`, bypassing `calibrate_synthetic`
   entirely.

Option 1 is smaller in surface area and keeps `calibrate_synthetic` more broadly useful
(E6 might want the same knob for its index axis, since E6's index sweep is `n_water`
varying with GT presumably matching the assumption — verify this too during E6 planning,
since if E6 wants a *mismatched* index test at any point it hits the identical gap).
Option 2 costs more code but requires no library change. **Recommend Option 1** given P2
("library computes, script orchestrates") and given D-06 is already adding one new
optional parameter (`memory_out`) to this same function — a second optional out-parameter
in the same phase is a small, consistent addition, not scope creep.

### A.4 `generate_real_rig_array` / `generate_real_rig_trajectory` — signatures

`synthetic.py:226-299`:

```python
def generate_real_rig_array() -> tuple[
    dict[str, CameraIntrinsics], dict[str, CameraExtrinsics], dict[str, float]
]
```

No parameters at all — fixed 12 cameras (`cam0`..`cam11`) at hardcoded XY positions
derived from an actual rig calibration, common averaged intrinsics (`K` fx=1587.79,
fy=1588.34, image_size=(1600,1200)), common `water_z = 1.031`, all at world Z=0, all
identity rotation (cameras looking straight down). This is the "realistic" scenario's
camera generator — see D-03 contradiction below.

`generate_real_rig_trajectory` (`:355-405`):

```python
def generate_real_rig_trajectory(
    n_frames: int = 100,
    depth_range: tuple[float, float] = (1.1, 2.0),
    seed: int = 42,
) -> list[BoardPose]
```

Board positions sweep a fixed footprint centered at `(X_CENTER, Y_CENTER) = (-0.34, 0.55)`
with `XY_EXTENT = 0.7`, `ROTATION_RANGE_DEG = 20.0` — these are **not** parameters, they
are hardcoded module constants inside the function body (`:384-386`). Only `n_frames`,
`depth_range`, `seed` are externally controllable. `create_scenario("realistic")` calls
this with `n_frames=30, depth_range=(1.1, 2.0)` (`synthetic.py:762-766`).

**Assembling a `SyntheticScenario` from these two functions** (rather than
`create_scenario`, which only offers 3 fixed presets): call
`generate_real_rig_array()` to get `(intrinsics, extrinsics, water_zs)`, call
`generate_real_rig_trajectory(n_frames=..., depth_range=..., seed=...)` for
`board_poses`, then construct `SyntheticScenario(name=..., board_config=<same
default_board as create_scenario, defined inline at synthetic.py:687-694>,
intrinsics=..., extrinsics=..., water_zs=..., board_poses=..., noise_std=0.5,
description=..., n_air=1.0, n_water=<n_true>, seed=...)`. The `default_board`
(`BoardConfig(squares_x=12, squares_y=9, square_size=0.060, marker_size=0.045,
dictionary="DICT_5X5_100")`) is not itself exported as a constant — it is redefined
inline inside `create_scenario`. E5/E3-tier-2/E6 scripts that need it without calling
`create_scenario` must either duplicate this literal or (cleaner) the library should
export a small helper/constant. **Flag for planning**: consider whether `default_board`
should be promoted to a module-level constant in `synthetic.py` to avoid a fourth
hand-copy of this literal (E5, E3 tier 2, and E6 would each otherwise need to redefine
the same `BoardConfig`).

## B. E4's synthetic grid construction (EXP-08)

### B.5 `generate_camera_array` — full signature

`synthetic.py:132-141`:

```python
def generate_camera_array(
    n_cameras: int,
    layout: str = "grid",
    spacing: float = 0.1,
    height_above_water: float = 0.15,
    height_variation: float = 0.005,
    image_size: tuple[int, int] = (1920, 1080),
    fov_deg: float = 60.0,
    seed: int = 42,
) -> tuple[dict[str, CameraIntrinsics], dict[str, CameraExtrinsics], dict[str, float]]
```

`layout` accepts `"grid"`, `"line"`, `"ring"` (`:168-189`) — this is E6's layout axis and
E4's/E6's shared substrate. Cam0 is always the reference at the origin with identity
rotation; other cameras get a small random roll (`rng.uniform(-0.1, 0.1)` rad) and a
per-camera height variation (`rng.normal(0, height_variation)`), so **this generator is
inherently stochastic per-camera even at fixed `n_cameras`/`layout`** — reruns with the
same seed reproduce identically (an `np.random.default_rng(seed)` is created fresh each
call), but two *different* `n_cameras` values do not share camera 0..k-1's exact poses
(the RNG draw sequence differs based on loop structure — verify if determinism across
grid cells at different `n_cameras` matters for any E4/E6 comparison; not flagged as a
blocker, just an implementation note).

### B.7 `generate_board_trajectory` — full signature

`synthetic.py:302-311`:

```python
def generate_board_trajectory(
    n_frames: int,
    camera_positions: dict[str, NDArray[np.float64]],
    water_zs: dict[str, float],
    depth_range: tuple[float, float] = (0.3, 0.6),

```

`n_frames` controls E4's frame axis directly. `depth_range`/`xy_extent` control tank size

connectivity for an 8- or 16-camera grid cell with wide baseline; if a synthetic run in
E4 fails to build a connected pose graph, this is why. `min_cameras_per_frame` accepting
the argument silently without using it should be flagged to the planner as a possible
silent-no-op footgun for E4's 16-camera cells specifically.

### B.8 `assemble_benchmark_record` — full signature and block shapes

Already quoted above under `io/benchmark.py:310-320`; keyword-only:
`schema_version: int = 1`, `problem_shape: dict`, `timings: dict`,
`diagnostics: dict[str, SolverDiagnostics]`, `solver_config: dict`, `accuracy: dict`,
`environment: dict`, `memory_readings: dict | None = None`. Returns a dict with keys

`write_direct_call_benchmark` (`experiments/_io.py:358-430`) wraps this for E1/E7's
pattern, but **hard-restricts `timings`/`diagnostics` keys to exactly
`{"stage3_interface_optimization", "stage3_intrinsic_pass"}`** (`_io.py:37-39,403-409`)
and **always passes `memory_readings=None`** (`:427`, docstring `:374-377`, citing 19.1
D-11's deliberate psutil deferral). **This is a real constraint E4 collides with**: D-06/
D-07 need memory readings threaded for E4's synthetic cells, but the existing
`write_direct_call_benchmark` wrapper cannot pass them through — it was written before

### B.10-11 `n_params`/`n_groups` threading — CONFIRMED, and Jacobian element count

**Confirmed, not assumed** (direct grep of both call sites): `n_params`/`n_groups` ARE
populated by `optimize_interface` (`interface_estimation.py:373-374`) and
`joint_refinement` (`refinement.py:280-281`) regardless of caller — both compute
`jac_sparsity.shape[1]` and `int(groups.max()) + 1` internally whenever
`use_sparse_jacobian=True` (the default) and pass them to `capture_solver_diagnostics`.
Since `calibrate_synthetic` calls these two functions directly with `diagnostics_out`
threaded through, **the direct-call path (E1/E7/E4) populates `n_params`/`n_groups`
identically to the pipeline path** — D-16's assumption that E4 can copy CPR columns
from its own `benchmark.json` is CONFIRMED true, not merely assumed.

**Jacobian element count (D-15)**: `n_residuals x n_params`. `n_params` is
`stage3_interface_optimization.n_params` (or `.n_groups`) already in the record.
`n_residuals` is **not currently in any block** — `jac_sparsity.shape[0]` is computed
inside `build_jacobian_sparsity` but never surfaced to `SolverDiagnostics` or
`problem_shape`. Per P2 ("the library computes; the experiment orchestrates"), this is
technically a new library-side field the experiment cannot compute itself without
re-deriving it (which the source brief also identified as the exact anti-pattern E3
tier 3 exists to avoid for grouping). **Options**: (a) add `n_residuals` to
`SolverDiagnostics` alongside `n_params`/`n_groups` (small, consistent addition,
populated the same way at the same two call sites), or (b) `n_residuals` can be derived
honestly from data already in the record without re-deriving library logic: each
observation contributes exactly 2 residuals (x, y) per corner, and
`problem_shape` (a caller-supplied dict, not derived) could simply include
`n_corner_observations * 2` if the caller (E4's script) already knows
`n_corner_observations` from the detections it generated — this is a script-level
aggregation of a quantity the script itself produced (the synthetic detections), not a
recomputation of library-internal state, so it does not violate P2. **Recommend (a)**
for symmetry with `n_params`/`n_groups` and because it is directly available inside
`optimize_interface`/`joint_refinement` at zero extra cost (`jac_sparsity.shape[0]`).
Flag for planning: this is a new `SolverDiagnostics` field, another small library change
this phase should plan for.

## Common Pitfalls

### Pitfall 1: Trusting CONTEXT.md's exact line-number citations verbatim
**What goes wrong:** A test or docstring comment cites `interface_estimation.py:343` when
the current line is actually 140 or 720, because the file grew ~43 lines since the
citation was verified (2026-07-24, before this session).
**Why it happens:** BENCH-06's tolerance-explicit additions (and possibly other commits)
shifted line numbers without changing the *values* CONTEXT.md describes.
**How to avoid:** Any plan/test that must cite a specific source line should re-grep at
execution time rather than copy CONTEXT.md's line number directly. Values are all
confirmed correct; only line numbers drifted.
**Warning signs:** A new test asserting on a hardcoded line number (rather than by
importing and calling the actual function/reading its default) is inherently fragile —
prefer asserting on live values (e.g. `inspect.signature(...).parameters[...].default`
or simply calling the function and checking its bound/behavior) over line-number
comments.

### Pitfall 2: Assuming `generate_camera_array` and `generate_real_rig_array` are interchangeable
**What goes wrong:** D-03 assumes a `generate_camera_array(layout="grid", n_cameras=12)`
cell can be parameterized to match `create_scenario("realistic")` (which uses
`generate_real_rig_array`) "exactly." These are two independent code paths with
different camera counts' worth of hardcoded geometry, different intrinsics-generation
logic, and different image sizes — no parameter choice unifies them.
**Why it happens:** The source brief and CONTEXT.md were written with the intent that
"the 12-camera grid cell = the realistic scenario," without re-verifying against the
generator source at decision time.
**How to avoid:** Planner must resolve this explicitly (see Contradictions Found) before
writing E4's task list — the resolution changes which function E4's 12-camera cell calls.
**Warning signs:** Any acceptance criterion phrased as "E4's 12-camera/30-frame cell
matches E1/E6's baseline scenario" needs verification against actual generated
intrinsics/extrinsics, not just camera count.

### Pitfall 3: `write_direct_call_benchmark`'s stage-key allowlist silently rejecting new stage names
**What goes wrong:** `write_direct_call_benchmark` raises `ValueError` if `timings`/
`diagnostics` contain any key outside `{"stage3_interface_optimization",
"stage3_intrinsic_pass"}`. If E4/E5's direct-call scripts introduce a new logical stage
name in their own `timings` dict, this call fails loudly (a good thing — but must be
anticipated in the plan, not discovered mid-execution).
**Why it happens:** The allowlist was deliberately narrow when E1/E7 only used these
two Phase-18 stage keys.
**How to avoid:** Keep every new script's stage vocabulary limited to these same two
keys (both E4 and E5 only run Stage 2 + Stage 3, matching E1/E7's usage) — do not invent
a third key without also updating `_SETTLED_STAGE_KEYS` in `_io.py`.

### Pitfall 4: `generate_board_trajectory`'s unused `camera_positions`/`min_cameras_per_frame` parameters
**What goes wrong:** The function signature accepts `camera_positions` and
`min_cameras_per_frame` (implying connectivity is checked/enforced), but the function
body never reads or uses either — poses are drawn uniformly at random with no
connectivity guarantee.
**Why it happens:** Likely a documented-but-unimplemented safety net, or a param that
became vestigial after a refactor.
**How to avoid:** For E4's 16-camera/wide-baseline cells (and E6's ring/line layouts at
varied camera count), do not assume connectivity is guaranteed — a run may produce a
disconnected pose graph and fail Stage 2's `build_pose_graph`/`estimate_extrinsics`.
D-04 already requires every declared cell to emit a row with `status`/`status_reason`,
which is the correct mitigation (catch the failure, record it, move on) — but the
planner should not assume this failure mode is rare without empirical check.
**Warning signs:** A grid cell reporting `status=failed` with a pose-graph
connectivity error is expected behavior to handle gracefully, not a bug to chase.

### Building a sparsity pattern without running a calibration (E3 tier 3's exact model)

```python
# Source: tests/unit/test_optim_common.py:33-88 (existing test helper, not shipped code —
# E3's script should adapt this pattern, not import test code directly per P3's intent
# that experiments/ imports from src/aquacal, not from tests/)
def _make_detections(n_cams, n_frames, visibility, corners_per_view=4, seed=0):
    rng = np.random.default_rng(seed)
    camera_names = [f"cam{i}" for i in range(n_cams)]
    corner_ids = np.arange(corners_per_view, dtype=np.int32)
    frames = {}
    for frame_idx in range(n_frames):
        visible = [c for c in camera_names if rng.random() < visibility]
        if not visible:
            visible = [camera_names[rng.integers(n_cams)]]
        detections = {
            cam: Detection(
                corner_ids=corner_ids.copy(),
                corners_2d=rng.uniform(0.0, 1000.0, size=(corners_per_view, 2)),
            )
            for cam in visible
        }
        frames[frame_idx] = FrameDetections(frame_idx=frame_idx, detections=detections)
    return DetectionResult(frames=frames, camera_names=camera_names, total_frames=n_frames)
```

## Contradictions Found

### Contradiction 1 (major): D-03's "12-camera cell matches `create_scenario("realistic")` exactly" is not achievable

**CONTEXT.md D-03** states: "All nine cells use `generate_camera_array(layout="grid")` at
fixed noise (0.5 px), fixed board, fixed working distance, varying only `n_cameras` in
{8, 12, 16} and `n_frames` in {50, 100, 200}. **The 12-camera cell is parameterized to
match `create_scenario("realistic")` exactly**, so the grid's midpoint is the same scene
E1 calibrates and E6 baselines on."

**Verified by reading `synthetic.py:760-779`**: `create_scenario("realistic")` calls
`generate_real_rig_array()` (zero layout/spacing parameters; fixed real-rig XY positions
derived from an actual calibration; common averaged intrinsics with `image_size=(1600,
1200)`, `fx=1587.79`) and `generate_real_rig_trajectory(n_frames=30, depth_range=(1.1,
2.0), seed=seed)` (fixed footprint centered at `(-0.34, 0.55)`, extent `0.7`, rotation
range `20`deg) — **not** `generate_camera_array` and **not** `generate_board_trajectory`
at all. `generate_camera_array(layout="grid")` uses a completely different camera
placement algorithm (`side = ceil(sqrt(n_cameras))` grid spacing, default
`image_size=(1920,1080)`, computed intrinsics from `fov_deg`, per-camera random roll and
height variation) that cannot reproduce the real rig's specific XY layout, intrinsics, or
image size under any parameter choice — the two functions have disjoint parameter
spaces and different camera-count-to-position mappings by construction.

**This must be resolved before E4 is planned**, since it determines what E4's 12-camera
cell literally is:
- **Option A**: Drop the "matches realistic exactly" requirement; the 12-camera cell is
  simply `generate_camera_array(n_cameras=12, layout="grid")` on its own terms, an
  internally-consistent point on E4's cost-scaling curve but *not* the same scene as
  E1/E6's baseline. E4's LaTeX prose must not claim it is the same scene.
- **Option B**: The 12-camera cell literally calls `generate_real_rig_array()` +
  `generate_real_rig_trajectory(n_frames=<axis value>)` instead of
  `generate_camera_array`/`generate_board_trajectory` — i.e., E4's scene-family is NOT
  uniform across all nine cells; the 8/16-camera cells use `generate_camera_array`
  (since `generate_real_rig_array` has no camera-count parameter — it is hardcoded to
  12), while the 12-camera cell alone uses the real-rig generator. This achieves "exactly
  matches realistic" for that one cell at the cost of D-03's "one scene family" premise.

Report this to the user/planner rather than silently picking one — it changes what "one
scene family" means for D-03 and D-14 (accuracy-vs-camera-count), and affects whether
E4's cost-scaling curve is monotonically comparable across all nine points.

### Contradiction 2 (moderate): `calibrate_synthetic` cannot separate ground-truth index from calibration-assumed index

Detailed in Finding A.3. CONTEXT.md's E5 procedure ("generate ground truth at index
`n_true`, calibrate assuming `n_assumed`") is not achievable by calling
`calibrate_synthetic` as currently written, because its internal
`generate_synthetic_detections` call omits `n_air`/`n_water` and therefore always
generates at the hard-coded default `n_water=1.333`, decoupled from the function's own
`n_water` parameter (which only reaches the calibration side). Not flagged anywhere in
CONTEXT.md or the source brief — both assume `calibrate_synthetic` already supports this
without checking. Requires either a small library addition (a new optional parameter) or
writing E5 as a fully direct-call script bypassing `calibrate_synthetic` (E7's pattern).
