Execute E4's nine-cell synthetic grid and emit the committed `benchmark_grid.csv` and
`benchmark_grid.tex`, with E2's real rig as the labeled tenth point.

Purpose: EXP-08 and ROADMAP SC2. This is the production run for the module plan 19.2-07 wrote and
unit-tested. It answers R1.5 (runtime and memory at 8/12/16 cameras across frame counts), R3.2
(hardware, stopping criteria, 13-camera wall-clock), the cost half of R1.2, and — via D-14's
accuracy columns — the empirical leg of R1.3.

**This is a production run, not a test step.** Nine synthetic calibrations, each in its own child
process. Launch with `python -u` in the background per `CLAUDE.md`; without `-u` the log stays empty
for the entire run and a stall is indistinguishable from progress.

**Runtime is unknown until Task 1 measures it — do not trust "minutes each".** The project's own
record is 48-87 minutes for a 13-camera x 200-frame calibration with Stage 3 dominating, and E4's
16x200 cell is a comparable Stage-3 problem. Skipping detection removes the smaller half, not the
dominant one. Nine cells could plausibly be many hours. Task 1 measures one representative cell
first and extrapolates before the full grid is launched (review M8).

**This plan runs ALONE on the machine.** It moved to its own wave because E4 is a wall-clock and
peak-memory benchmark: a concurrent E5 band, E6 sweep, or even another script's `--smoke` would
contaminate every timing it publishes and raise the odds of the 16x200 cell OOMing (review H4).
Constraint 11 ("one machine for the whole grid") is about machine identity; this is about
quiescence, and they are different requirements.
</objective>

Entry point: `python -u -m experiments.e4_benchmark_grid --force`
  Iterates DECLARED_CELLS = the nine (n_cameras, n_frames) pairs over {8,12,16} x {50,100,200},
  spawning ONE CHILD PROCESS PER CELL via `run_cell_subprocess`
  (`python -u -m experiments.e4_benchmark_grid --cell {n}x{m} ...`), writes one benchmark.json per
  cell under <out>/e4_cells/cameras_{n}_frames_{m}/, then builds benchmark_grid.csv and
  benchmark_grid.tex.

Single-cell entry point (the child, also usable by hand): `--cell 16x200`. It runs exactly that one
declared cell and exits; it writes no CSV and no LaTeX. Exit code 0 = ok, 3 = skipped_existing,
anything else = failed.

Why per-cell processes (review H2, H3): `capture_peak_memory()` returns a PROCESS-LIFETIME
high-water mark, so nine cells in one process would make cells 2-9 report "the largest cell so far"
— monotone, plausible, and wrong. And a Windows OOM kills the process outright, so an in-process
`except Exception` could never record the `status=failed` row D-04 promises for the 16x200 cell.
A child process makes the peak per-run and turns the kill into an exit code the parent records.

`--check` re-aggregates the per-cell records already on disk and compares them against the
committed CSV. It does NOT re-run any cell (review M9). A green `--check` is evidence the
aggregation and the committed CSV agree with the records, not that the nine solves reproduce.

Per-cell resumability: `write_direct_call_benchmark` skips a write when the file exists and
`force` is False. Re-running WITHOUT `--force` therefore resumes an interrupted sweep, reusing
every completed cell. That is the intended recovery path if the machine is interrupted.

The hardware spec of record (D-05), already captured in E2's committed benchmark.json:
  Intel64 Family 6 Model 154, 20 logical cores, 16,857,190,400 bytes RAM, Windows 11,
  Python 3.12.12, NumPy 2.4.2, SciPy 1.17.0, OpenCV 4.13.0.
  Constraint 11 (one machine for the whole grid) is satisfied by running the nine synthetic cells
  on THIS machine. Do not run any cell elsewhere.

Known risk: the 16-camera / 200-frame cell is the memory risk on a 16.9 GB box (D-04). A cell that
OOMs or fails a pose-graph connectivity check records `status=failed` with a reason and the sweep
continues (`generate_board_trajectory` accepts `camera_positions` and `min_cameras_per_frame` but
its body uses neither, so connectivity is not guaranteed for wide-baseline cells).
