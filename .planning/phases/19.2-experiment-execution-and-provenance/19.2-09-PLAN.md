<!-- Contracts the executor needs. -->

Entry point: `python -u -m experiments.e4_benchmark_grid --force`
  Iterates DECLARED_CELLS = the nine (n_cameras, n_frames) pairs over {8,12,16} x {50,100,200},
  writes one benchmark.json per cell under <out>/e4_cells/cameras_{n}_frames_{m}/, then builds
  benchmark_grid.csv and benchmark_grid.tex.

Per-cell resumability: `write_direct_call_benchmark` skips a write when the file exists and
`force` is False. Re-running WITHOUT `--force` therefore resumes an interrupted sweep, reusing
every completed cell. That is the intended recovery path if the machine is interrupted.

The hardware spec of record (D-05), already captured in E2's committed benchmark.json:
  Intel64 Family 6 Model 154, 20 logical cores, 16,857,190,400 bytes RAM, Windows 11,
  Python 3.12.12, NumPy 2.4.2, SciPy 1.17.0, OpenCV 4.13.0.
  Constraint 11 (one machine for the whole grid) is satisfied by running the nine synthetic cells
  on THIS machine. Do not run any cell elsewhere.

Known risk: the 16-camera / 200-frame cell is the memory risk on a 16.9 GB box (D-04). A cell that
OOMs or fails a pose-graph connectivity check records `status=failed` with a reason and the sweep
continues (`generate_board_trajectory` accepts `camera_positions` and `min_cameras_per_frame` but
its body uses neither, so connectivity is not guaranteed for wide-baseline cells).
