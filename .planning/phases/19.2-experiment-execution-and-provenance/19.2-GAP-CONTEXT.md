## D-27 — `generate_board_trajectory` centres the volume on the array centroid, by default

**Decision.** Add a `center` parameter to `generate_board_trajectory`
(`src/aquacal/datasets/synthetic.py`). It defaults to **the centroid of
`camera_positions`**, NOT to the origin and NOT to today's behaviour.

**This is a deliberate NON-INERT library change.** It is the one place in this phase
where inertness is explicitly not the goal.

**Why.** Today the function samples `x = uniform(-xy_extent, +xy_extent)` about the
**origin**, while `generate_camera_array` recentres the array so **cam0** sits at the
origin. cam0 is a *corner* camera under `grid` and an *end* camera under `line` — never
the middle. The calibration volume is therefore pinned to a corner of the rig, by an
amount that differs per layout:

| layout (12 cams) | array span | centroid | offset from board volume |
|---|---|---|---|
| grid | +0.00…+0.30 | (+0.15, +0.10) | 0.18 m |
| ring | −0.38…+0.00 | (−0.19, 0.00) | 0.19 m |
| line | +0.00…+1.10 | (+0.55, 0.00) | **0.55 m** |

The board volume is (0,0) ± 0.15 m in all three cases. Under `grid`, half that volume
lies at negative x where no camera exists. Under `line`, the board never leaves the first
~14% of the rig, which is the actual cause of the `KeyError: 'cam11'` recorded in the
committed `generalization_sweep.csv`.

**The function already receives `camera_positions` as a required argument** and simply
does not use it for centring. `generate_real_rig_trajectory` — the realistic path — solves
this correctly and explicitly (`X_CENTER, Y_CENTER = -0.34, 0.55`, commented "Center of the
rig footprint... Board should move throughout this area to ensure all cameras see it").
The grid-family generator never received that fix. There is no scenario in which centring
the calibration volume on an arbitrary corner camera is the desired behaviour, so the
default is corrected rather than preserved.

**Consequence accepted by the user:** some experiments are pre-update and some post-update.
That is acceptable **only** because the containment audit below shows no committed result
depends on the changed path.

## D-28 — `xy_extent` scales with the array footprint

**Decision.** The grid family derives `xy_extent` from the array's span rather than using
a fixed 0.15 m, with a floor so small arrays still get a usable volume.

**Why.** `xy_extent` is fixed at 0.15 m whether the array spans 0.20 m or 1.10 m. The
realistic generator uses ±0.7 m against a ~1.3 m footprint — about **±0.54× the span**.
The grid family ranges from ±0.75× down to ±0.14×, so each layout exercises a different
fraction of its own footprint.

**Why this matters beyond the `line` crash.** Together with D-27, this means E6's layout
axis is currently **confounded**: `grid`, `ring` and `line` each get a different
board-to-array alignment and a different fraction of footprint covered. A `ring` row that
reads slightly worse than `grid` may be measuring a 0.19 m centroid offset rather than
anything about ring geometry. The committed layout rows are therefore not trustworthy as a
layout comparison — a separate and more serious problem than board overfill, which at
least applies uniformly across cells.

## D-29 — The grid family moves to realistic optical geometry

**Decision.** `build_grid_scenario`'s defaults become approximately
`height_above_water = 1.031`, `depth_range = (1.1, 2.0)`, `spacing ≈ 0.43`.
Exact values are the planner's to finalise; the acceptance property is that
**the board fits within the frame at every depth in the range**.

**Why.** Today the grid family sits **0.15 m** above the water with a 0.30 m footprint,
while the real rig and the `realistic` preset both sit at **~1.03 m** with a ~1.34 m
footprint. The 0.72 × 0.54 m board — the same physical board in both cases, deliberately
not scaled — **overfills the frame** in the grid family:

| geometry | view at working depth | board visible |
|---|---|---|
| grid family (0.15 m) | 0.29 × 0.17 → 0.54 × 0.31 m | **12.8% → 43.1%** (measured 22% mean) |
| real rig (1.031 m) | 1.09 × 1.73 m | **100%** |

Verified proposal at `height=1.031`, `depth=(1.1, 2.0)`:

| depth | view | board fits | adjacent overlap @ spacing 0.43 |
|---|---|---|---|
| 1.1 m | 1.25 × 0.70 m | ✓ | 25% |
| 1.5 m | 1.57 × 0.89 m | ✓ | 38% |
| 2.0 m | 1.97 × 1.13 m | ✓ | 49% |

Overlap stays in the same band as today's 27–55%, so redundancy is preserved.

**What was checked and found NOT to be wrong.** The current array is not degenerate: 40–52%
of cameras see the board each frame (5.4–7.0 cameras, not the bare minimum of 2), adjacent
overlap is 27–55% by area, and `validation_3d_error_mean` is ~1e-6 m with ~0.17 mm std at
0.70 px reprojection against 0.5 px noise. The justification for the change is
**representativeness**, not infeasibility: E4 and E6 exist to characterise cost and
generalisation for deployments like the real rig, and at 22% corner visibility the residual
counts that drive memory and runtime describe no rig anyone would build.

**Nothing published moves.** E4/E6 feed reviewer responses R1.4/R1.5/R3.2, not §3. E1, E5
and E7 already run at real-rig geometry. See `MANUSCRIPT-FINDINGS.md` MF-02.

### Expect the 16×200 cell to OOM

If corners per view rise from 19.5 toward 88, residuals scale 3–4.5× and peak memory
projects to **9.9–14.9 GiB** against a ~15.7 GiB box:

| corner-density rise | residuals | projected peak | projected stage 3 |
|---|---|---|---|
| 2.0× | 108,920 | ~6.6 GiB | ~5 min |
| 3.0× | 163,380 | ~9.9 GiB | ~8 min |
| 4.5× | 245,070 | ~14.9 GiB | ~12 min |

16×200 is **pre-authorised to fail** as a recorded row, exactly as in plan 19.2-09.
Escalate only if a 16-camera cell **other than** 16×200 fails, since the curve needs at
least one successful 16-camera point. Note the irony worth recording in the summary: the
cell only fit at 3.31 GiB *because* the geometry was unrealistic; the original ~14.4 GiB
projection was closer to correct than the measurement that appeared to refute it.

## D-32 — CR-05: the Newton diagnostic measures a loop production never runs

`refractive_project_newton_diagnostic` (`core/refractive_geometry.py:467`) documents itself
as performing "the identical root-find as `_refractive_project_newton` — the shipped
projection path used inside every residual evaluation", via the shared `_solve_newton_r_p`.
Confirmed false in source: `calibration/_optim_common.py:635` projects through
`refractive_project_batch` (`:718`) → `_refractive_project_newton_batch` (`:546`), which
contains its own hand-inlined Newton loop, never calls `_solve_newton_r_p` (grep count 0),
and terminates on `np.all(np.abs(delta) < tolerance)` — all points at once, with no
per-point convergence flag.

So `newton_iterations.csv`'s published `n_not_converged = 0` is a property of a loop the
optimizer never runs, and its per-point iteration counts do not transfer: under all-points
termination every point iterates until the slowest converges.

**This is the sharpest form of the goal's traceability clause failing** — provenance
pointing at the wrong implementation is worse than absent provenance, because it is citable.
It also bears on `MANUSCRIPT-FINDINGS.md` MF-01, which now carries a resolve-before-citing
caveat.

### There are three Newton loops, not two

| function | vectorized? | termination | called by |
|---|---|---|---|
| `_solve_newton_r_p` (`:325`) | **no — scalar** (`r_p: float`) | per-point: `if final_abs_delta < tolerance: break` | `_refractive_project_newton` (`:454`), the diagnostic (`:533`) |
| `_refractive_project_newton_batch` (`:546`) | yes | all-points: `if np.all(np.abs(delta) < tolerance): break`, **no per-point convergence flag** | `refractive_project_batch` (`:718`) ← the production residual path |

`_solve_newton_r_p`'s own docstring says it is "shared by `_refractive_project_newton` and
`refractive_project_newton_diagnostic`, so a change to the convergence logic cannot drift
between **two copies**." It says *two*. The batch loop is a third, sitting outside the
guarantee the helper was written to provide.

### What is NOT at risk (do not overstate this finding)

The computed **positions are almost certainly correct**. Once a point converges its `delta`
is ~0 and further Newton steps are no-ops, so running to the batch maximum reaches the same
root; the observed max of 7 iterations sits under the cap of 10, so the batch converges
every point too. This is a **provenance defect, not a numerical one** — which is exactly
what makes it citable and wrong. A plan must not "fix" it by asserting the numbers are bad.

### DECISION (user, 2026-07-29): option (c) — instrument the batch path

**Recommended and chosen.** Add per-point iteration and convergence tracking to a
diagnostic twin of `_refractive_project_newton_batch` (or an opt-in flag on it that is OFF
in production), and regenerate `newton_iterations.csv` from **that**.

**Why (c).** It makes the published number actually describe the loop production runs,
while touching production numerics **not at all** — so there is no §3 exposure and no D-08
hard-stop risk. It also yields the one quantity the batch currently cannot report
(per-point convergence), which is precisely what the supplement's claim is about.

**Acceptance:**
- `newton_iterations.csv` is regenerated from the batch path and its provenance states so.
- Production projection output is proven **bit-identical** pre/post (the flag defaults off).
- The `refractive_project_newton_diagnostic` docstring's "used inside every residual
  evaluation" claim is corrected, whichever path the diagnostic ends up describing.
- `MANUSCRIPT-FINDINGS.md` MF-01's resolve-before-citing caveat is updated with the new
  measurement, and the median/max framing is restated against the batch loop's semantics
  (under all-points termination, per-point cost behaves like the tail, not the median).

### Rejected alternatives (recorded so they are not silently reopened)

- **(a) Migrate the batch onto `_solve_newton_r_p`.** More expensive than it appears: the
  helper is **scalar**, so calling it per-point would destroy vectorization in the hottest
  loop of every residual evaluation, and making it array-aware changes the scalar path too.
  Switching the batch to per-point termination stops iterating earlier, shifting results at
  ~1e-16 and propagating through the bundle adjustment — which risks moving §3 numbers, a
  D-08 hard stop. **Retained as a desirable follow-up** for code quality (it would remove
  the duplicate loop the helper exists to prevent), but explicitly OUT of scope here.
- **(b) Correct the docstring and restate the CSV's scope** as the scalar path. Zero risk
  and cheap, but it documents the problem rather than fixing it: the published convergence
  number would still not describe production.

## D-33 — The OOM path must be guarded and *observed* before the re-run

D-29 pre-authorises 16×200 to fail, but the failure path has never actually run. Before
relying on it, the plan must close three gaps. **The third is the important one.**

### What is already covered (do not re-do)

`tests/unit/test_experiments_e4.py::test_subprocess_status_mapping` monkeypatches
`subprocess.run` and asserts exit 1 → `status="failed"` with a populated `status_reason`,
and `build_grid_dataframe` is tested to emit a failed cell as a row with NaN metrics and a
preserved reason. **CR-01's claim that "every E4 fixture uses `status='ok'`" is overstated**
— failed and `skipped_existing` fixtures both exist. CR-01's substance (metrics discarded
on the *resume* path) may still stand, but its stated evidence does not.

### Gap 1 — no real child process is ever spawned in tests

The test module states this explicitly. The status *mapping* is proven; the behaviour of a
child actually dying under memory pressure on this OS has never been observed. Add one test
that spawns a real child which exits non-zero (and, separately, one that allocates until it
dies), asserting the row is recorded rather than raised, hung, or dropped.

### Gap 2 — no timeout is passed in production

`run_cell_subprocess(timeout=None)` at both call sites (`e4_benchmark_grid.py:1010`,
`:1048`) means `subprocess.run` waits indefinitely. A thrashing cell runs unbounded. Pass an
explicit per-cell timeout, sized from the measured probe, and map `TimeoutExpired` onto a
recorded row (`status="failed"`, a distinct reason) rather than an exception — same contract
as a non-zero exit (D-04).

### Gap 3 — degraded success via paging silently corrupts the two columns E4 exists to publish

**This box has 15.7 GB physical and 30.7 GB virtual** — roughly 15 GB of pagefile. Windows
has no OOM killer, so the `run_cell_subprocess` docstring's "turns an OS-level OOM kill into
a recordable exit code" is Linux-shaped reasoning that does not describe this machine. The
realistic outcomes for a ~15 GiB cell, in order of likelihood:

| outcome | what gets recorded | handled today? |
|---|---|---|
| **succeeds via pagefile** | `status=ok`, exit 0, **inflated wall-clock**, **understated peak** | **NO — silently wrong** |
| `MemoryError` in the child | exit 1 → `status=failed` | yes |
| OS kills the process | negative/large exit code → `status=failed` | yes |

The understatement is structural: the Windows metric is `psutil`'s **`peak_wset`** —
*resident* working set, which paging caps near the physical limit while true commit runs
higher. So a thrashing cell can report a peak *lower* than a healthy one while taking
several times the wall clock, which would bend the scaling curve in a direction that looks
like a good result.

**Required.** A cell must not be able to report `status=ok` with silently degraded timings:

- Record committed/virtual memory alongside `peak_wset`, so paging is visible in the record
  rather than inferred. (`peak_wset` alone cannot distinguish the two cases.)
- Flag any cell whose peak approaches the physical limit — a `memory_pressure` field or an
  explicit reason string — so a reader can tell a clean measurement from a paged one.
  This is **not** a pass/fail verdict column (D-12 stands); it is a measurement condition.
- Prefer an explicit pre-flight ceiling: if projected or observed memory exceeds a declared
  fraction of physical RAM, fail the cell deliberately as a recorded row rather than letting
  the OS page it. A deliberate recorded failure is a better datum than a paged success.
- State in the summary which cells, if any, ran under memory pressure.

**Rationale.** A crash is self-announcing; a paged success is not. Publishing "16 cameras ×
200 frames: N GiB, M minutes" when M measures pagefile thrash is the same class of defect as
MF-01 and CR-05 — a plausible number whose stated meaning is wrong. Given D-29 deliberately
pushes this cell to the edge of the box, this guard is a precondition for the re-run, not a
follow-up.
