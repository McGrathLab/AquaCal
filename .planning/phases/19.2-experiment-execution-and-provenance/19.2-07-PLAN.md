**Three cross-AI review findings are folded into this plan and are settled, not open.**
1. **H1 — the grid runs tilt-ENABLED.** Every cell passes `normal_fixed=False` through
   `calibrate_synthetic`'s new passthrough (plan 19.2-01). `interface_estimation.py` and
   `refinement.py` both default `normal_fixed=True`, but `schema.py`'s
   `interface_normal_fixed=False` is the PIPELINE default, so E2's real-rig point and every
   `tab:cpr` row are tilt-enabled. A tilt-fixed grid would differ by exactly the 2 interface-tilt
   DOF and nothing in the committed record would reveal it. `normal_fixed` and `shared_interface`
   are therefore both columns AND `solver_config` keys.
2. **H2/H3 — each cell runs in its own subprocess.** `capture_peak_memory()` returns a
   process-lifetime high-water mark (its own docstring says "monotonically non-decreasing across
   calls within one process"), so running nine cells in one process makes cells 2-9's memory
   columns the running maximum of everything before them — and, because the grid iterates in
   ascending cost order, the wrong numbers look monotone and plausible. A subprocess per cell fixes
   that AND turns an OOM into a non-zero exit code the parent can record as `status=failed`, which
   the in-process `except Exception` provably cannot (a Windows OOM kills the process).
3. **H5 — every row carries its seed.** No benchmark record in the repository carries one today.

**E4's CPR columns describe E4's own configuration and do NOT feed `tab:cpr`.** The D-16 split was
withdrawn (H1): E3 now owns all six `tab:cpr` rows. E4 still reports its own `n_params`/`n_groups`/
`fd_reduction` because they are the cost story for the scaling curve; they are labelled with
`normal_fixed`/`shared_interface` so no reader can mistake them for the published table's rows.

**Ruled out by inspection, not preference — do not reopen it.** Running synthetic data through the
real pipeline so `benchmark.json` would be pipeline-written was checked:
`run_calibration_from_config` starts from videos/framesets and has **no precomputed-detection
entry point**, so it would mean rendering synthetic images.

**Why a subprocess and not a loop — do not "simplify" this back.** `capture_peak_memory()` returns
a process-lifetime high-water mark. In a single process, cell 2's `_baseline` already carries
cell 1's maximum, so `peak_bytes_*` for cells 2-9 measures "the largest cell so far" and
`delta_bytes_since_previous_boundary` collapses toward zero for any cell that is not a new maximum.
Because the grid iterates in ascending cost order, the wrong numbers would look monotone and
entirely plausible, and E2's tenth row — a genuine single-run peak — would not be comparable with
any of them. Separately, a Windows OOM or a failed `.toarray()` allocation on the 16x200 cell
typically kills the process outright, so `except Exception` never runs and the `status=failed` row
