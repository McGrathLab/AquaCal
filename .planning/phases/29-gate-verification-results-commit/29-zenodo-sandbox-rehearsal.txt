    verifiable. Zenodo's API exposes no scope-introspection endpoint; the scope
    is provable only by observing a production upload succeed while a publish
    attempt fails at Zenodo's end. Plan 29-01 makes no production call and never
    attempts a publish, so this plan produces no evidence either way.

    "the author publishes by hand" is enforced by the credential rather than by
    code review. Even if a publish call were somehow reached, it would be
    rejected by Zenodo. The `grep` gates in Task 3's acceptance criteria are the
    second, independent layer: no publish code path exists in the tool at all.

    Accounts are separate: sandbox.zenodo.org registration is distinct from
    zenodo.org, so the two tokens are not interchangeable and the distinct
    environment variable names (T-29-04) keep a sandbox-intended run from
    silently reaching production.

A NOTE ON THE `# pragma: allowlist secret` MARKER ABOVE
-------------------------------------------------------
Two lines of this transcript carry an inline `# pragma: allowlist secret` comment.
Both annotate the dummy payload's MD5, and they are there for a linter, not because
anything sensitive is present.

Zenodo's deposition response repeats each file's digest as a BARE 32-character hex
string (`"checksum": "534db6..."`), whereas the bucket PUT response uses the prefixed
`"md5:534db6..."` form. detect-secrets' HexHighEntropyString plugin flags the bare
form and not the prefixed one. The flagged value is the MD5 of a 16,896-byte dummy
file that this transcript prints in full three times over — it is the round-trip
evidence itself, and publishing it is the entire point.

The marker is used in preference to widening `.secrets.baseline` or the hook's
`exclude` pattern: a false positive is annotated where a reader can see the reasoning,
and the repository's secret-scanning tripwire is left exactly as strict as it was.
The same one-line annotation will be needed on plan 29-04's and plan 29-07's
production transcripts, for the same reason.
