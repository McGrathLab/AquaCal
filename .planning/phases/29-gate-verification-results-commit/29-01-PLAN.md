**The tool's surface.** `build_arg_parser()` returning an `argparse.ArgumentParser(description=__doc__)`,
and `main(argv: list[str] | None = None) -> int`. Flags:
`--sandbox` and `--base-url` as a mutually exclusive **required** group, with **no default value on
either** — RESEARCH § *Known threat patterns* names "uploading to production while intending
sandbox" as a tampering risk, and the mitigation is that the host is always an explicit act;
`--metadata <path>` (a JSON file); `--file <path>` and `--name <key>` (optional together — omit to
create a metadata-only draft, which is what Record B's first pass and any metadata correction
need); `--deposition-id <id>` (optional — supplied to update an existing draft instead of creating
one); `--out <path>` (the evidence file to append the result JSON to);
`--max-retries` default `5`; `--read-timeout` default `3600`.

**Token resolution.** `resolve_token(sandbox: bool) -> str` reads `os.environ` — the sandbox
variable when `--sandbox` was given, the production variable otherwise — and raises a
`ValueError` naming the missing variable when absent. The token never appears in a CLI argument
(CLI args are visible in `ps` output and shell history), never in a file, and never in a log line.
`scrub_headers(headers)` returns a copy with the authorization value replaced by a fixed redaction
marker; every log statement and every re-raised `requests` error message passes through it.

**Metadata validation before the network.** `load_metadata(path)` reads the JSON and checks the six
fields Zenodo requires for an open dataset deposition — `upload_type` (value `dataset`), `title`,
`description`, `creators`, `access_right` (value `open`), `license` — plus `publication_date`,
using the `.get()`-then-`raise ValueError` idiom `download.py:145-160` uses, with a message naming
the missing field. `version` and `related_identifiers` are optional and passed through untouched.
A malformed metadata block must fail in the first second, not after a four-hour transfer.

**`create_draft(base_url, token, metadata)`** issues `POST {base_url}/deposit/depositions` with
body `{"metadata": {...}}` and the bearer header, `timeout=(30, 120)`, `raise_for_status()`, and
returns the parsed body. It must **not** ask Zenodo to reserve a DOI on the draft under any
circumstance (D-29-03). **`update_metadata(base_url, token, deposition_id, metadata)`** issues
`PUT {base_url}/deposit/depositions/{deposition_id}` with the full metadata block.

**`put_file(bucket_url, token, path, name, max_retries, read_timeout)`** is the one hot path.
Compute the local digest first with `md5_of(path, block=1 << 20)` (the chunked
`iter(lambda: fp.read(block), b"")` loop from `download.py:167-169`, widened for a multi-gigabyte
file). Then `for attempt in range(max_retries)`, with the **entire** transfer inside the `try` so
the file handle is reopened on every attempt — a consumed file object uploads zero bytes on retry,
which is the single most important structural property here. Inside: open the file binary, wrap it
so a `tqdm(desc=name, unit="B", unit_scale=True, unit_divisor=1024)` bar advances on read (there is
otherwise no progress signal for hours), and `requests.put(f"{bucket_url}/{name}", data=<the
wrapped file object>, headers=<bearer>, timeout=(30, read_timeout))`. Pass a **file object**, never
a generator — a generator forces chunked transfer encoding, which multiple Zenodo issue reports
blame for aborted uploads, and it denies `requests` a real `Content-Length`. Never pass a read
timeout of `None`; a hung socket then blocks forever. On response: `raise_for_status()`, then guard
the body shape before comparing (a missing `checksum` key is a failed attempt, not a traceback —
ASVS V5), then compare the returned `checksum` against `"md5:" + <local digest>` and raise
`RuntimeError` on mismatch. Catch `(requests.RequestException, RuntimeError)` — the same two-type
tuple as the analog, so a checksum mismatch is itself retryable — sleep `2 ** attempt`, and on
exhaustion `raise RuntimeError(f"upload failed after {max_retries} attempts: {e}")`. Return the
response body, which carries `key`, `size`, `checksum` and `version_id` and **is** the round-trip
proof.

**There is no publish function and no discard function.** Do not import, reference, or leave
commented scaffolding for either. D-29-01 keeps DOI minting a deliberate human act in the web UI,
and `COVERAGE.md` records both as reasoned opt-outs. Do not add a `.tmp` staging path — the
analog's exists to protect a local write and there is no local write here; its role is taken by the
md5 round trip.

**The two metadata files.** `scripts/zenodo_metadata_a.json` describes the immutable input record,

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local process → zenodo.org / sandbox.zenodo.org | A bearer credential and multi-gigabyte payloads cross an authenticated HTTPS boundary to a third-party service. |
| process environment → log / evidence files | The token lives in the environment; log lines and the evidence file are written to disk and committed. |
| Zenodo JSON responses → local control flow | Server-supplied JSON drives the round-trip verdict. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-29-01 | Information disclosure | `resolve_token()` / any log statement | high | mitigate | Token read from `os.environ` only; no `--token` flag (CLI args leak via `ps` and shell history); `scrub_headers()` redacts the authorization value before any header dict or re-raised `requests` error is logged. |
| T-29-02 | Information disclosure | `scripts/zenodo_metadata_{a,b}.json`, `29-zenodo-sandbox-rehearsal.txt` | high | mitigate | Token never written to a file; only ids, `links.html`, `key`, `size`, `checksum`, `version_id` are recorded. `detect-secrets` with `.secrets.baseline` is the repo tripwire and is run scoped to these files before commit. |
| T-29-03 | Tampering (scholarly record) | Zenodo deposition lifecycle | high | mitigate | No publish and no discard code path exists (`grep` gate in acceptance criteria); the automation token is minted with `deposit:write` only, so the call fails at the credential. |
| T-29-04 | Tampering | host selection (`--sandbox` vs `--base-url`) | medium | mitigate | Required mutually-exclusive group with **no default**, and distinct env-var names per host, so a sandbox-intended run cannot silently reach production. |
| T-29-05 | Tampering / repudiation | `put_file()` round trip | high | mitigate | Local md5 computed before transfer and compared to the server's returned `checksum` on every attempt; a mismatch is a failed attempt, and exhaustion raises rather than returning success. |
| T-29-06 | Denial of service (self-inflicted) | `requests.put` timeout | medium | mitigate | Explicit `timeout=(30, read_timeout)` with a generous read timeout; never an unbounded read timeout, which would let a hung socket block indefinitely (documented 504 behaviour). |
| T-29-07 | Spoofing | Zenodo response shape | low | mitigate | Response body shape is guarded before the checksum comparison (ASVS V5); a missing key is handled as a failed attempt. |
| T-29-08 | Tampering | supply chain — new dependencies | high | mitigate | **No package installs in this phase.** `requests` (2.34.2) and `tqdm` (4.70.0) are already runtime dependencies (`pyproject.toml:44-45`); RESEARCH § *Package Legitimacy Audit* records zero `[ASSUMED]`, `[SUS]` or `[SLOP]` packages, so no legitimacy checkpoint is required. Third-party Zenodo clients are prohibited by this plan. |
| T-29-09 | Elevation of privilege | token scope | high | mitigate | `deposit:write` only, `deposit:actions` deliberately omitted (Task 2's gate); publishing authority is never delegated to automation. |
