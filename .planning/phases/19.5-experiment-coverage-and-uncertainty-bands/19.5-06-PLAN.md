<correctness_critical>
## E6's checkpoint cache is seed-blind. Isolated per-seed directories are correctness, not hygiene.

`_SCENARIO_IDENTITY_KEYS` **omits `seed`**, and `seed` is not in E6's `config` dict at all. A
`--seeds` loop that reuses one `--out` directory finds `e6_configs/{config_key}.json` already on
disk from the previous seed, treats it as a valid cache hit, and **silently reports seed 42's
numbers labelled as seed 43**. This is a known, dated, deliberately-deferred latent defect
(`e6_generalization_sweep.py:619-638`, called out in `rerun_19_4.sh`'s comments).

Do **not** fix `_SCENARIO_IDENTITY_KEYS` — it is an explicit Deferred Idea. Use the workaround that
already shipped, `rerun_19_4.sh`'s `run_stage_e6_seed43` (lines 258-283): one isolated output
directory per seed. In this plan that means `out_dir / "e6_band" / f"seed_{seed}"`, which isolates
each seed's `e6_configs/` cache completely.

A test must assert the isolation directly, by observing that two seeds in one band produce two
distinct `e6_configs/` directories. Without that assertion the band is worthless and looks fine.
</correctness_critical>

<design_decision>
**The `cameras` axis is band-mode-only, via `build_axis_configurations(include_cameras_axis=False)`.**
Adding a fourth axis unconditionally would add rows to `_run_full`'s `generalization_sweep.csv`,
which `--check` compares key-for-key against the committed baseline at `0ffbe15` — `--check` would
break and the committed artifact would be superseded for no reason. Defaulting the new parameter to
`False` keeps `_run_full`, `_run_check` and `_run_smoke` byte-identical in behaviour, and the band
path passes `True`. The band therefore carries 17 configurations (8 index + 3 layout + 3 scale +
3 cameras, with four baseline rows sharing one scene) against the production sweep's 14.
</design_decision>
