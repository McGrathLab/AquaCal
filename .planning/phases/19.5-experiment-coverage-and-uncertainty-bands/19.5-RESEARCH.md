## Summary

(`experiments/_io.py`'s `parse_seed_list`/`run_seed_band`, E1/E7's `--seeds` CLI convention, and
`rerun_19_4.sh`'s risk-first state-machine queue) and applies them to E5 and E6, adds one new

two reviewer questions that today have no code at all (COV-01 structural scaling, COV-02 FD
accuracy), and closes E2's known `--seed` gap. Every mechanism COV-01..08 needs already has a
close working analogue in the repository; this phase is composition and extension, not invention.

The single most important scoping fact: **E6 and E5 currently have NO `--seeds` flag.** Only E1
and E7 got that flag in Phase 19.4 (`D-19.4-14`); `experiments/_io.py:run_seed_band`'s own
docstring explicitly defers E4/E6 band support as "deliberately NOT done in this phase" (meaning
19.4). Phase 19.5's COV-03/04/05 plans must **add** `--seeds` to E6 (COV-03/04) and E5 (COV-05)
following the E1/E7 pattern exactly (`_run_band` closure + `parse_seed_list` + `run_seed_band` +
a script-local `--seeds` arg + `_validate_*_args` mutual-exclusion-with-`--check` check) — this is
new code, not configuration, contrary to how easy it may look from the CONTEXT.md's framing of
"the enabler is a side effect."

**Primary recommendation:** Sequence Tier A (COV-01, COV-02, COV-08 — all zero-runtime) as pure
composition tasks first, wave-gate them, then write the `--seeds`/axis additions to E5/E6/E2 as a
second wave, and assemble every solve-bearing requirement (COV-03, COV-04, COV-05, COV-06,

### Pattern 1: The `--seeds` band mode (E1/E7's shipped convention — COV-03/04/05 must copy it)

**What:** A script-local `--seeds` argparse flag, parsed via
`experiments._io.parse_seed_list`, executed via `experiments._io.run_seed_band`, mutually
exclusive with `--check`, writing a SEPARATE `*_band.csv` artifact (never overwriting the
single-seed production CSV), with `force=True` implied only for that band file.

**When to use:** Any experiment needing a reproducible multi-seed band (COV-03, COV-04, COV-05).

E6 needs an extra wrinkle: `run_configuration`'s on-disk checkpoint cache
(`out_dir/e6_configs/{config_key}.json`) is keyed by `config_key`, and E6's
`_SCENARIO_IDENTITY_KEYS` **deliberately omits `seed`** — confirmed directly in
`e6_generalization_sweep.py:630-638` and called out explicitly in `rerun_19_4.sh`'s comments as "a

### Pattern 2: Structural-only sweeps with no calibration solve (COV-01)

**What:** Build a synthetic detection-connectivity pattern (`_make_detections`, visibility=1.0),
call `build_jacobian_sparsity` + `build_structural_column_groups` directly, read off `n_params`,
`n_groups`, `fd_reduction` — no `least_squares` call anywhere.

**When to use:** COV-01's scaling sweep, exactly as E3 tier 3 (`build_cpr_grouping_df`) already
does at N ∈ {3, 8, 12, 13, 16}.

**Example:**
```python
# Source: experiments/e3_derived_quantities.py:446-495 (existing, extend the N/frame range)
detections = _make_detections(n_cameras, n_frames, visibility=1.0, seed=0)
jac_sparsity = build_jacobian_sparsity(
    detections, reference_camera="cam0", camera_order=camera_order,
    frame_order=frame_order, min_corners=1,
    refine_intrinsics=refine_intrinsics, normal_fixed=normal_fixed,
    shared_interface=shared_interface,
)
groups = build_structural_column_groups(
    jac_sparsity, n_cameras, n_frames,
    refine_intrinsics=refine_intrinsics, normal_fixed=normal_fixed,
    shared_interface=shared_interface,
)
n_params = int(jac_sparsity.shape[1])
n_groups = int(groups.max()) + 1
```
`jac_sparsity.shape` gives `(n_residuals, n_params)` directly — `nnz` is
`int(jac_sparsity.sum())` (it is an int8 0/1 array per its type annotation
`NDArray[np.int8]`), and `jacobian_elements` (dense-equivalent element count) is
`jac_sparsity.shape[0] * jac_sparsity.shape[1]`, the SAME quantity
`make_sparse_jacobian_func`'s `n_elements` computes internally and compares against
`dense_threshold=500_000_000` — this is the exact quantity to sweep to locate the boundary in
`(N, frames)` space (see Open Questions for how to make this an analytic rather than empirical
statement).

**COV-01's "well past N>10" requirement**: `_make_detections` builds detections purely in-memory
(`np.random.default_rng`, no real geometry), so `n_cameras` can scale arbitrarily — E3 already
proves N=16 works; nothing in `build_jacobian_sparsity`/`build_structural_column_groups` bounds N
structurally (both operate on the connectivity pattern, not physical camera positions). A sweep to
N=50 or N=100 is a matter of wall-clock (`build_jacobian_sparsity` builds an actual `(n_residuals,
n_params)` sparse-shaped array — at large N and frames this can itself become large; watch memory,
not correctness).

### Anti-Patterns to Avoid

- **Naive iid bootstrap over `reconstruction_errors.csv` rows (COV-08).** The file has 7,762 rows
  keyed by `frame_idx` (52 distinct values, confirmed by reading the committed CSV directly) — many
  rows per frame share the same estimated board pose and camera geometry, so they are NOT
  independent draws. An iid resample of individual rows understates the true interval width because
  it treats correlated observations as independent. **Resample `frame_idx` groups with
  replacement** (a cluster/block bootstrap), not individual rows.
- **Reusing E6's shared `--out` directory across seeds in a `--seeds` loop.** Silently resumes
  seed 42's checkpoint for every later seed — see Pattern 1 above. Each seed needs its own output
  directory, exactly like `rerun_19_4.sh`'s `run_stage_e6_seed43`.
- **Running the production queue inside an executor subagent's own turn.** See Common Pitfalls —
  this is CLAUDE.md's single most emphatic warning for this codebase and has cost multiple hours
  in three prior phases (19.2, 19.3, 19.4).
- **Quoting `optimality` to more than one significant figure**, per every prior phase's convention
  (D-19.3-17 lineage) — it varies ~2x run to run.
- **Treating `depth_range=None`'s "fix" as inert.** MF-08's E6 subsection explicitly records that

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Multi-seed band execution | A new per-experiment seed loop | `experiments._io.parse_seed_list` + `run_seed_band` | Already generic, already used by E1/E7, explicitly documented as the shared primitive for exactly this use case (its own docstring names E4/E6 as the deferred future callers) |

## Common Pitfalls

### Pitfall 1: An executor backgrounds the overnight queue and stalls permanently
**What goes wrong:** A subagent launches `rerun_19_5.sh` (or any multi-hour command) via a Bash
call that exceeds the tool's ~600s ceiling, gets auto-backgrounded with "You will be notified when
it completes," and then ends its turn — which IS its completion, so no notification is possible.
Five of six executors stalled this way in Phase 19.4 alone.
**Why it happens:** The tool's own message ("you will be notified") is true for the orchestrator
and false for a subagent, and prompt hardening does not fix a structural mismatch.
**How to avoid:** Per `CLAUDE.md` and `D-19.5-08`: the orchestrator runs the queue itself, never an
executor. Every executor plan gets a targeted, sub-10-minute test command covering only its own
files, with an explicit instruction not to run the production queue. The queue launch is
`nohup bash experiments/rerun_19_5.sh > experiments/rerun_19_5.log 2>&1 & disown`, run directly by
the orchestrator (or the user), never delegated.
**Warning signs:** A plan or executor return message describing "waiting for the notification" or
"the run is in progress in the background" — treat this as a stall, not progress. Verify against
`git log`, `git status --porcelain` in any worktree, and the presence of expected output files —
never trust a subagent's return text (per `CLAUDE.md`'s explicit instruction).

### Pitfall 2: E6's `_SCENARIO_IDENTITY_KEYS` omits `seed` — a shared `--out` silently resumes seed 42
**What goes wrong:** Any `--seeds` loop over E6 that reuses one output directory across seeds will
find `e6_configs/{config_key}.json` already on disk from an earlier seed, treat it as a valid
cache hit (the identity check compares `n_cameras`, `layout`, `n_water`, `depth_range`,
`xy_extent`, `spacing`, `normal_fixed` — not `seed`), and silently report seed 42's numbers
labeled as a different seed.
**Why it happens:** Documented as a known, deliberately-deferred latent defect
(`e6_generalization_sweep.py:619-638`; called out explicitly in `rerun_19_4.sh`'s comments).
**How to avoid:** One isolated output directory per seed in the band, exactly like
`rerun_19_4.sh`'s `run_stage_e6_seed43` (`experiments/results_e6_seedNN/`). Do not attempt to fix
the underlying identity-key gap in this phase — it is explicitly out of scope (a Deferred Idea).
**Warning signs:** A band whose per-seed metrics are suspiciously identical across seeds, or whose
`e6_configs/*.json` file count does not match `n_seeds × n_configs`.

### Pitfall 3: E4/E6 exit 0 even when every cell/configuration failed
**What goes wrong:** Reading a queue stage's exit code as evidence of success.
**Why it happens:** Both scripts record a per-cell/per-configuration failure as a `status="failed"`
row and the overall process still exits 0 (this was true before D-19.4-11's fail-fast default;
fail-fast now aborts the WHOLE run non-zero on the FIRST failure by default — but a resumed/cached
failure is still just a recorded row, and `--no-fail-fast` restores the old exit-0-always
behavior).
**How to avoid:** Check the `status` column counts in the written CSV, never the process exit code
alone — this is stated as a standing rule in `e6_legal_seed_probe.sh`'s own comments and in
`MANUSCRIPT-FINDINGS.md`'s E6 section.
**Warning signs:** A queue stage reports success but the row count with `status != "ok"` is
nonzero.

### Pitfall 4: `depth_range=None`'s "obvious" fix is NOT bit-inert
**What goes wrong:** Touching `derive_grid_depth_range`/`board_clearance_floor`/`depth_range=None`
call sites under the assumption that any refactor there is behavior-preserving.
**Why it happens:** MF-08 explicitly records that an earlier assertion of inertness for this exact
code path was WRONG and retracted — the holdout scenario's board depths shift up to 0.469 mm under
one candidate "fix."
**How to avoid:** COV-03/04/05 do not need to touch this code at all (D-19.5-04's prelaunch gate
re-verifies the EXISTING seed-invariant floor empirically; it does not change the floor
computation). If any plan proposes changing `derive_grid_depth_range` or
`board_clearance_floor`, that is scope creep outside this phase's "experiment scripts only, no
non-inert `src/` change" constraint — flag it, do not implement it.
**Warning signs:** Any task description that edits `board_clearance_floor` or
`derive_grid_depth_range`'s logic (not just calling them with new arguments from
`experiments/`).

### Pitfall 5: E2's `--config` path bypasses `--seed` entirely — the band mechanism is NOT `--seed`
**What goes wrong:** Assuming `python -m experiments.e2_real_rig --config ... --seed N` varies the
run. It does not: `_run_real_calibration`'s explicit-`--config` branch (`e2_real_rig.py:550-581`)
never reads `args.seed` at all — only the archive-download branch even logs it (and logs it as
explicitly NOT threaded, `e2_real_rig.py:587-593`). The seed that reaches `split_detections` comes
from `config.seed` INSIDE the YAML file (`pipeline.py:918-921`, confirmed:
`split_detections(all_detections, config.holdout_fraction, seed=config.seed)`), which is set once
at Phase 16-06 and is a property of the `config.yaml` file itself, not a CLI override.
**Why it happens:** Two different seed mechanisms exist in this codebase (a CLI `--seed` used by
every synthetic experiment, and a config-file `seed:` key used by the real pipeline) and E2 uses
the `--config` path, not the synthetic path.
**How to avoid:** COV-07's band needs N copies of the production config
(`Desktop\Aqua\AquaCal\release_calibration\config.yaml`, per `DATA-01a`'s established location)
differing ONLY in their `seed:` field, each run via `--config <variant>.yaml --out
<band-seed-dir>`. This does not disturb the committed single-run record (which stays whatever
`--config` points at by default, i.e. no `--config` flag / the Zenodo archive path, OR — if
reproducing the exact §3-comparable run — the existing full-frameset config unmodified). Confirm
with the user/CONTEXT whether the committed E2 record's own config gets a band, or whether the
band runs against a copy — do not overwrite the source-of-truth config.
**Warning signs:** A band whose per-seed `real_rig_metrics.json` are byte-identical — that means
the seed never reached the split.

### Pitfall 6: Newton's inner tolerance may floor COV-02's achievable FD accuracy
**What goes wrong:** Interpreting a large column-wise relative error between the shipped FD
Jacobian and a "tighter" reference as evidence the shipped step is bad, when the true cause is that
BOTH the shipped step's Jacobian and any tighter reference are being computed through a cost
function containing an inner Newton root-find (`_solve_newton_r_p` /
`_refractive_project_newton_batch`) that only converges `r_p` to **1e-9 m** tolerance
(`refractive_geometry.py:409,480,578,738`, all default `tolerance: float = 1e-9`). A finite
difference step small enough to probe changes in the cost function below ~1e-9 m of induced
position change cannot be resolved MORE precisely than the Newton solve itself resolves — the
inner solve is not exact, it has its own floor.
**Why it happens:** FD accuracy analyses conventionally assume the underlying function evaluation
is exact (machine precision); here it is not — it is itself an iterative solve with a declared
tolerance.
**How to avoid:** COV-02 should explicitly measure and report where this floor sits (e.g. sweep
step size and watch for a plateau or noise floor around ~1e-9-scale steps) rather than silently
treating the reference Jacobian as ground truth. This IS the "publishable finding" the phase's
additional context anticipates — do not bury it as an implementation detail.
**Warning signs:** A Richardson-extrapolated or very-tight-step reference Jacobian that behaves
erratically (non-monotonic error) at the smallest tested step sizes — that is the Newton floor
showing through, not noise to average away.
