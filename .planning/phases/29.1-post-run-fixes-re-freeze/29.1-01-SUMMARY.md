## Accomplishments

- **The writer half (D-01).** `_extract_pipeline_row` reads `degenerate_observations_at_solution` out of E2's own record — `discard_stats` first, `problem_shape` as fallback, via the existing `_get_nested` helper — instead of hardcoding `None`. The committed record yields **198**. A record carrying it in neither place still yields `None`, so "never measured" stays distinguishable from "measured zero"; that distinction is the property gate 1 was built on and it survives intact.
- **The gate half (D-02).** `_check_guard_column` excludes `record_source == "pipeline"` rows from `bad_mask`. One gate result is kept rather than a second gate id, because the roll-up's PASS/N/A/FAIL totals are an audited number. The exemption is legible in the gate's own output: the message names how many rows were gated, how many were exempt, each exempt row's `cell_key` and its count, and why a pipeline row is exempt.
- **Both halves were required.** Populating the field alone makes gate 1 see `198`, which fails the "non-zero" half of its predicate exactly as the null failed the "missing" half. That is why they landed in one task.
- **The stale rationale is replaced, not deleted (D-03).** The retired D-26 claim gave way to a comment stating the present-day source of the value, what the 198 physically are, and the exemption; the `> 0` publish rule now states it is scoped to `assembled` rows and that the pipeline exemption is intentional rather than an accident of control flow.
- **Both halves are pinned by 13 new tests**, written first and confirmed failing against the pre-change implementation before being confirmed passing against it.

## Decisions Made

- **Option 3 extended, not option 3 as written.** The todo offered three resolutions; the plan chose to publish the value *and* exempt the row. Keeping the null (option 3 verbatim) would have kept a measured number out of a Zenodo-bound artifact for no reason but a stale comment. Giving E4's rule a 1% threshold (option 2) would have relaxed the nine *synthetic* cells too, where the library's reasoning does not apply — a synthetic cell can be re-run with different geometry, so a non-zero count there is a defect to fix, not a fact to live with.
- **The exemption is keyed to row kind, never to magnitude.** `record_source == "pipeline"`, full stop. This is what makes T-29.1-01's mitigation testable: two of the seven gate tests assert FAIL for `assembled` rows, and a blanket relaxation would pass them only by deleting them.
- **One gate result, not a second gate id.** Allowed by the CONTEXT's "Claude's Discretion" clause, which set the requirement (the FAIL stops, the reason is visible) and left the mechanism open. A second id would have moved the roll-up's audited totals for a reason unrelated to the defect.
- **The pipeline exemption covers a *missing* count too, not only a non-zero one.** The committed CSV still nulls the cell — the writer fix reaches the artifact only on the next run — so gating a null pipeline row would have left the FAIL exactly where it was. `test_exempt_row_with_a_missing_count_is_still_exempt` pins this.
- **The `memory_pressure` D-26 comment was left alone.** It also says "predates", but its claim is about D-33 and is still true: E2's committed record has an empty `memory` object and no `memory_pressure` anywhere. The must-have was scoped to the `discard_stats` claim.
