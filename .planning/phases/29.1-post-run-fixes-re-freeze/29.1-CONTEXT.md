# Phase 29.1: Post-Run Fixes & Re-Freeze - Context

**Gathered:** 2026-08-20
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase repairs the defects the 2026-08-20 production run surfaced, corrects the frozen
package's install documentation, and cuts a new verified frozen tag that licenses a clean re-run.

It changes what the suite **records and reports**, never what it measures. No solver behaviour, no
scenario geometry, no published scientific value moves as a result of this phase — with one
deliberate exception recorded as D-01, where a value that already exists starts being published
instead of nulled.

**Not in scope:** running the suite (that is a re-execution of Phase 28), building or publishing
the Zenodo results package (RUN-05, waits on the new tag), and Phase 29's outstanding E7
before/after comparison.

## Implementation Decisions

### E4's real-rig guard count (criterion 1)

- **D-01:** Populate `degenerate_observations_at_solution` on the `record_source="pipeline"` row
  from E2's `benchmark.json` (198), **and** exempt pipeline rows from the `> 0` status downgrade,
  with the exemption documented at both sites. The value becomes published and auditable and
  Gate 1 sees a real number instead of a null, without the anchor row asserting
  `"first-order optimality is unreliable for this cell"` — which the library explicitly declines
  to say at 0.268% (`pipeline.py:1288`). — **Reversibility:** costly — the CSV column becomes
  populated for a row that has always been null, so `benchmark_grid.tex` and anything reading the
  real-rig row must tolerate a value there; reverting means re-nulling a number the manuscript may
  by then cite.

- **D-02:** The exemption must land in **two** places, not one. Populating the field makes Gate 1
  see `198`, which fails the "non-zero" half of its predicate just as the null failed the
  "missing" half. So `check_rerun_gates.py`'s Gate 1 also needs to know that a
  `record_source="pipeline"` row carries a count it does not gate on. Fixing only
  `e4_benchmark_grid.py` converts one FAIL into a different FAIL.

- **D-03:** Replace the stale D-26 comment at `e4_benchmark_grid.py:1380` rather than deleting it.
  Its claim — that E2's `benchmark.json` "predates this plan's discard_stats threading" — was true
  when written and was overtaken by Phase 24. The replacement should say what is true now and why
  the row is exempt, so the next reader does not re-derive this.

### E1's band degeneracy sidecar (criterion 2)

- **D-04:** **Unclaim it.** Remove `e1_seed_band_degeneracy_breakdown.json` from
  `suite_expectations.json` (two sites), `EXPECTATIONS.md` and `README.md`. Do not add a writer.
  The code already matches the authoritative design table in
  `2026-08-15-suspend-programmatic-check-for-reshaped-artifacts.md`, which carries `--seeds` rows
  for E5 and E7 and deliberately none for E1. — **Reversibility:** reversible — three manifest
  entries.

- **D-05:** Evidence behind D-04, recorded so it is not re-litigated: E1's synthetic scenario
  produces **zero** degenerate observations. `e1_degeneracy_breakdown.json`'s only non-zero fields
  are denominators (`observations_evaluated__* = 14949`) and PnP attempt counts. A band sidecar
  would carry per-seed denominators and nothing else. Noted for honesty: E7's band sidecar is
  *equally* all-zero on real counters (60 non-zero fields, 0 actual degeneracy counters) and is
  written anyway, so "it would be empty" is not disqualifying by precedent alone — the design
  table is the reason. E5's band sidecar, by contrast, does carry real content (seeds 45 and 46:
  `pnp_guard_rejected` = 44 and 33).

### E1's band write confirmations (criterion 3)

- **D-06:** `_run_band` must print `Wrote {path}` only when `write_direct_call_benchmark` returns
  `True`, and print the skip otherwise. Today it prints unconditionally
  (`e1_refractive_comparison.py:1328`), so `e1_band.log` claims two writes the resumability guard
  skipped (`_io.py:875-881`).

- **D-07:** Resolve the underlying contradiction, not just the log line. The comment at
  `e1_refractive_comparison.py:1209-1212` says band mode "must never overwrite" the
  `e1_benchmark_<model>.json` records; the call at `:1300-1328` passes `seed=seeds[-1]` and
  overwrites them. Only the `force=False` skip kept the policy last night.
  **Corrected mechanism (verified during planning, 2026-08-20):** a clean `experiments/results/`
  does NOT remove the skip. Stage `e1` runs with `--force` (`run_stage_e1`) and always precedes
  `e1_band`, so both records exist by the time the band runs — which is why the skip fired on
  2026-08-20 despite a clean start. The earlier claim in this file and in the ROADMAP was wrong.
  The real hazards are (a) a `--force` band run, and (b) a standalone band into a fresh `--out`
  with no preceding single-seed run, where the write proceeds and creates the records stamped
  `seed=seeds[-1]`. The defect stands; only the mechanism changed. Decide which of the two
  intents is correct and make the code say it. — **Reversibility:** reversible.

### Stale-string sweep (criterion 4)

- **D-08:** Fix E1's band scope string (`e1_refractive_comparison.py:1217+`) to state four seeds
  and 256/384 rows, citing ruling A1 (`run_experiment_suite.sh:1452`) for why four and not ten.
  This field's whole job is stating the domain a published number may be quoted over, and it
  currently authorises a ten-seed, 640/960-row domain that was never run.

- **D-09:** **Bound the wider sweep to what the 2026-08-20 run actually recomputed.** That is the
  literal ask of `2026-08-17-audit-static-strings-that-annotate-recomputed-values.md`, and the
  run's artifacts define a finite, checkable boundary where every finding carries evidence. Do
  **not** sweep all of `experiments/` — it is ~500 KB of heavily-commented Python, most of it
  annotating values no recent run touched, so findings there would be unevidenced.

- **D-10:** Rationale for the sweep existing at all: three stale rationales surfaced in a single
  day — the D-26 comment (D-03), the 198 todo's opening premise (D-13), and this scope string
  (D-08). The pattern is a claim outliving the conditions that produced it, and it has now twice
  produced a gate failure or a false provenance statement.

### Install documentation and the re-freeze (criteria 5 and 6)

- **D-11:** Correct `experiments/HANDOFF.md` §1.2 to `pip install -e ".[dev,bench]"`, and check
  every other place the install command appears rather than only that section. Verification is
  **by execution from a clean environment**, not by asserting the string changed: without `pytest`
  (`dev`) e3 exits 1 on both `--check` and `--force`; without `psutil` (`bench`)
  `cpu_count_logical` and `ram_total_bytes` go null in the run manifest.

- **D-12:** Tag the new freeze **`rerun-freeze-02`**, continuing Phase 27's numbered attempt log.
  It must not match `v*`: `.github/workflows/publish.yml` triggers on `push: tags: ['v*']` and
  publishes to PyPI. `git describe` is pinned to `--match 'v[0-9]*'` everywhere it anchors a
  version, so a non-version tag cannot displace the semver anchor. — **Reversibility:** one-way —
  a pushed tag matching `v*` fires `publish.yml` and ships a release to PyPI; that cannot be
  un-published, only yanked.

- **D-13:** Fix work happens in **this clone** (`~/aquacal-frozen-rerun-freeze-01`), on a branch
  based on **`results/rerun-freeze-01`**. This clone holds the verified conda env
  (`aquacal-freeze01`, python 3.11.15, cv2 4.13.0.92), the real rig image set E2 needs, and last
  night's committed output for regression comparison. Basing on `results/rerun-freeze-01` keeps
  `experiments/results/` present in the working tree — those files are tracked *only* on that
  branch, so checking out a branch without them removes them from the tree. That is the hazard
  RETURN-HANDOFF-2026-08-20.md §0.4 flagged as "merge, never checkout". The data survives either
  way (committed, plus `~/rerun-freeze-01-output.tar.gz`), but verification is far easier with the
  tree populated.

- **D-14:** The new tag must clear **Phase 27 attempt 1's full bar, run locally**: full test suite,
  local `--smoke` acceptance roll-up (target **72 PASS / 18 N/A / 0 FAIL**), 20/20 stages at
  exit 0, dry-run harness 20/20, clean tree at tag time, and a pre-push exposure audit.

- **D-15:** Why D-14 is not redundant: **nothing else runs the test suite on this branch.**
  `.github/workflows/test.yml` triggers only on push/PR to `main`, and `cc56eea` removed the
  pytest pre-push hook on 2026-08-20 on the reasoning that it duplicated `test.yml`. That
  reasoning holds for `main` and not for the experiments line, so between the removed hook and
  the branch-scoped CI, the local run is the *only* test gate before the tag is cut.

  bulk artifacts are excluded per path and ship via Zenodo. Extended on 2026-08-20 (`672be71`) to

## Specific Ideas

- The 198 are **above-water board corners** — stated by the user during discussion and confirmed
  against `benchmark.json` (198/198 `above_interface`). This is why D-01 frames criterion 1 as a
  reporting decision rather than an open scientific question, and why "thread it through and
  accept `degenerate`" was rejected: on measured hardware the library's own remedy ("move the
  board so no corner sits at or above the interface") is unavailable retrospectively, so a re-run
  reports the same count. The status must therefore be one the project is willing to live with
  permanently, not one it expects to clear.

- The verification bar is deliberately the *full* attempt-1 bar rather than a reduced one,
  specifically because D-15's CI gap means no other gate exists on this branch.
