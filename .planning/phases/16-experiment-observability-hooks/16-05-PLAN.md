<why_result_jac_is_trusted>
RESEARCH.md §Q1 verified this by reading scipy 1.17.0's `trf.py` and by experiment:
`jac(x)` is called only inside the `actual_reduction > 0` branch — i.e. strictly after a
trial step is accepted and `x` is reassigned. `result.jac` is therefore bit-identical to the
last value returned by the repo's own custom dense `jac` callable, evaluated at the accepted
point that becomes `result.x`. Never a rejected trial step. The locked "reuse `result.jac`"
decision stands; do not recompute the Jacobian.

Shape/type: a dense `(m, n)` `numpy.ndarray` on the normal path, because
`make_sparse_jacobian_func` calls `.toarray()` below its 500M-element `dense_threshold`.
Above that threshold it stays sparse. `compute_conditioning` (plan 16-01) already densifies
per chunk, so both are handled — do not add a second code path here.
</why_result_jac_is_trusted>

<memory_discipline>
`result.jac` for the 13-camera rig is on the order of gigabytes and the run already peaks near
3.6 GB. Two hard rules:

1. **Compute conditioning inside `on_solution`, while `result` is still in the optimizer
   function's scope.** Never store `result` or `result.jac` on the observer and never return
   them to the pipeline. The observer keeps only the small `ConditioningReport`
   (an (n, n) matrix, roughly 4 MB at n=727).
2. **Reducing that peak is explicitly out of scope** (PERF-01, deferred). Do not refactor the
   Jacobian path. If this phase surfaces a sharper number for the peak, record it in the
   SUMMARY for PERF-01 — that is the only deliverable there.
</memory_discipline>

<refuse_loudly>
CONTEXT.md is explicit: pre-check the allocation and refuse with a clear message naming the
estimated size and the config key to disable. Do **NOT** silently degrade to a narrower
metric — WP6 would then quietly receive a different quantity than intended, which is exactly
the paper/code divergence this milestone exists to close.

So: let `ConditioningMemoryError` propagate out of `on_solution` and fail the run. Do not
catch it and continue with a partial report. The only permitted handling is to re-raise with
the stage name added to the message.
</refuse_loudly>
</context>

1. Add a module-level function to `_observability.py`:

```python
def build_parameter_labels(
    camera_order: list[str],
    frame_order: list[int],
    reference_camera: str,
    refine_intrinsics: bool = False,
    normal_fixed: bool = True,
) -> list[str]:
```

It must mirror `_optim_common.pack_params`'s layout exactly, in this order:
- if `not normal_fixed`: `"ref_tilt_rx"`, `"ref_tilt_ry"`
- for each camera in `camera_order` skipping `reference_camera`:
  `f"{cam}_rvec_x"`, `_rvec_y`, `_rvec_z`, `f"{cam}_tvec_x"`, `_tvec_y`, `_tvec_z`
- `"water_z"`
- for each `idx` in `frame_order`: `f"frame{idx}_rvec_x"` ... `f"frame{idx}_tvec_z"`
- if `refine_intrinsics`: for each camera in `camera_order`: `f"{cam}_fx"`, `_fy`, `_cx`, `_cy`

Without these labels the correlation matrix is an unreadable 727x727 grid; the WP6 argument
specifically needs to point at the camera-height / `water_z` coupling, so `water_z` and the
per-camera `tvec_z` entries must be findable by name.

2. Extend `OptimizerObserver`:
   - `__init__` gains `conditioning: bool = False` and the observer grows a
     `self.conditioning_report: ConditioningReport | None = None`.
   - `configure_layout(...)` (added in plan 16-04) gains an optional
     `parameter_labels: list[str] | None = None` argument stored on the observer.
   - Replace the `on_solution` no-op body with:
     ```python
     if not self.conditioning:
         return
     from aquacal.validation.conditioning import compute_conditioning  # local import: avoids a calibration -> validation import at module load
     self.conditioning_report = compute_conditioning(
         result.jac,
         parameter_names=self.parameter_labels,
     )
     ```
     Wrap only to re-raise with context:
     ```python
     except ConditioningMemoryError as exc:
         raise ConditioningMemoryError(f"[{self.stage}] {exc}") from exc
     ```
     Do not catch anything else, and do not store `result` or `result.jac` anywhere.

3. In `optimize_interface` and `joint_refinement`, pass the labels through the existing
   `configure_layout(...)` call added in plan 16-04 — `camera_order`, `frame_order`,
   `reference_camera`, `refine_intrinsics`, and `normal_fixed` are all already in local scope
   at that point. This is a one-line addition to each; do not restructure those functions.
