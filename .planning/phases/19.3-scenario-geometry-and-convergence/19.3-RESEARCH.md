## Critical Finding — the board rotation pivot is a CORNER, not the centre (verify before locking the clearance constant)

**This does not re-litigate D-19.3-01's formula shape; it flags that the "half-extent" input to that
formula may need to change.** Confidence: HIGH — verified by direct execution against the shipped
code (`board.py::BoardGeometry`, `board.py::transform_corners`), not training-data assumption.

1. **`BoardGeometry.corner_positions`** places corner 0 at board-local `(0, 0, 0)` (top-left), and
   `transform_corners(rvec, tvec)` computes `R @ pos + tvec` for every corner — **rotation pivots
   about the board-local origin (corner 0), not the board centre.** `generate_board_trajectory` and
   `generate_real_rig_trajectory` both sample `tvec` directly as `(x, y, z)` with no re-centring, so
   `tvec` is literally corner 0's world position, and corner 0's world Z is `tvec_z` **regardless of
   tilt** (`R @ [0,0,0] = [0,0,0]`).
2. **Measured corner-cloud half-extents** (`BoardGeometry(default_board).corner_positions`, 12×9
   board, `square_size=0.060`): X spans `0.0 → 0.60` m, Y spans `0.0 → 0.42` m — i.e. **half-extents
   from the corner-cloud centre are 0.30 × 0.21 m**, not the 0.330 × 0.240 m stated in
   `19.3-CONTEXT.md` D-19.3-01. (`(squares_x-1)*square_size/2` = `11*0.06/2` = 0.33 counts one
   segment too many; the code's own `cols = squares_x - 1 = 11` corner columns span only
   `(cols-1)*square_size = 10*0.06 = 0.60` m, i.e. `(squares_x-2)*square_size/2` for the half-extent.)
3. **The lever arm that matters is from the PIVOT (corner 0) to the farthest corner, not from the
   centre.** That distance is `√(0.6² + 0.42²) = 0.732` m — roughly **2.2×** either half-extent
   figure above. A Monte-Carlo sweep of 200,000 random `(rx, ry, rz)` within the locked
   `rotation_range_deg=15.0` bound (`|rx|,|ry| ≤ 15°`, `rz` unrestricted) against the actual
   `BoardGeometry` corner cloud found a **worst-case upward excursion of any corner relative to
   corner 0's Z of 0.263 m** — closely matching the *pivot-based* prediction
   (`0.732 · sin(15°·√2) = 0.265` m) and roughly **double** the *centre-based* prediction D-19.3-01
   uses (`√(0.30²+0.21²)·sin(15°·√2) = 0.133` m using the correct half-extents, or `0.148` m using
   the context's stated 0.33×0.24).
4. **Consequence:** if the planner implements D-19.3-01's formula literally with `R_max` computed
   from *centre* half-extents, the derived floor may be **understating** the true worst-case
   protrusion risk by roughly a factor of two, in the rare frames that combine near-floor depth with
   near-maximal simultaneous tilt on both axes. The 10× margin math (k=0.1, i.e. `1.1×` multiplier)
   is nowhere near enough to absorb a 2× error in `R_max` itself — this is not a margin question, it
   is a "which formula computes the actual worst-case corner excursion" question.
5. **What this means for planning, concretely — two ways to close this, either legitimate:**
   - **(a) Change what `R_max` measures**, not the formula's shape: compute it as the maximum
     distance from `tvec` (the pivot) to any corner in `board.corner_positions`
     (`max(‖corner_pos‖)` over the board-local corner cloud, since `tvec` is corner 0 = board-local
     origin), rather than from the corner-cloud centroid. This is a **one-line, mechanical**
     correction inside the same derivation function and does not touch the locked `k=0.1` or the
     `θ√2` tilt-combination logic — it only changes where `R_max` is measured from, matching the
     actual pivot the generators use.
   - **(b) Re-centre the trajectory generators** so `tvec` represents the board *centre* rather than
     corner 0 (i.e. subtract the board-local centroid before applying `R`, add it back after). This
     is a bigger, non-inert change to two generators' semantics and is very likely **out of scope**
     given D-19.3-05/06 already accept one signature-breaking change; stacking a second geometric
     semantics change onto the same phase raises the review surface substantially. **Not
     recommended** unless the planner has an independent reason to want board-centre semantics.
   - **(a) is the minimal, mechanically verifiable fix** and is what this research recommends the
     plan adopt. It preserves every other part of D-19.3-01/02/03 untouched (the `θ√2` combination,
     `k=0.1`, deepest-per-camera `water_z`) and only changes the *input measurement* to `R_max`.
6. **This is flagged, not decided, because it touches a locked decision's numeric derivation.** Per
   the instructions governing this research, a locked decision's *intent* (derive-don't-hardcode,
   `k` never tuned to make a case pass, tilt combines as `θ√2` not `θ`) is unambiguous and must be
   preserved; what is unverified is whether "half-extent" in the formula was meant to be measured
   from centre or from pivot. **This should go back through `/gsd:discuss-phase` or be confirmed
   with the user before the plan locks a specific `R_max` measurement point** — recommend the
   planner surface this explicitly rather than silently picking (a) or the context's original
   centre-based reading. If the user reconfirms centre-based measurement is what was intended
   (e.g., because the observed evidence in D-19.3-01 — 146.5mm reach against a 147.5mm predicted
   maximum — was itself measured against actual per-frame corner excursions from a real run, which
   would already reflect the TRUE pivot-based geometry and might make the *stated* 147.5mm coincidentally
   close for other reasons), the fix-(a) delta should be re-validated against that same evidence
   before dismissing this finding.

**Cross-check against the seed's own numbers:** the SEED's measured "worst observed protrusion
66.1 mm" (over only 100 frames, not an exhaustive worst-case search) is well below both the
centre-based (~148 mm) and pivot-based (~265 mm) theoretical worst cases, which is expected — 100
frames sampled at `rotation_range_deg=15.0` uniformly on each axis independently rarely lands near
the joint worst case on both axes simultaneously *and* near the shallow end of `depth_range`. The
100-frame empirical measurement therefore cannot by itself discriminate between the centre-based and
pivot-based formulas; only a derivation from the actual code geometry can, which is what section 1-3
above did directly.

### Pattern: derive-don't-hardcode (established, D-29's own convention)

**What:** E6 already imports `GRID_DEPTH_RANGE`, `GRID_HEIGHT_ABOVE_WATER`, `GRID_SPACING` from
`e4_benchmark_grid.py` rather than restating them, and derives `_BASELINE_DEPTH_BELOW_WATER` /
`_BASELINE_XY_EXTENT` from those imports (`e6_generalization_sweep.py:129-135`).

**When to use:** Any new derived constant (the clearance floor, the corrected `R_max`) should follow
this same import-and-derive pattern rather than restating a number.

**Example (existing code, the pattern to extend):**
```python
# Source: experiments/e6_generalization_sweep.py:129-135
_BASELINE_DEPTH_BELOW_WATER: tuple[float, float] = (
    GRID_DEPTH_RANGE[0] - GRID_HEIGHT_ABOVE_WATER,
    GRID_DEPTH_RANGE[1] - GRID_HEIGHT_ABOVE_WATER,
)
```

### Pattern: trailing-kwarg-with-safe-default (established, but DELIBERATELY BROKEN for `board`)

**What:** Optional behavior in this codebase is normally added as a trailing kwarg defaulting to the
historical behavior (`shared_interface=True`, `observer=None`, `normal_fixed=True`). D-19.3-05
explicitly breaks this pattern: `board: BoardConfig` becomes **required**, not optional-with-skip,
because an optional path that silently skips the check is the exact failure mode being fixed. The
planner should NOT "soften" this into an optional parameter during implementation — that would
re-introduce the bypass the phase exists to close.

### Anti-Patterns to Avoid

- **Tuning `k=0.1` to make a failing scenario pass** (explicitly named anti-pattern in CONTEXT.md,
  carried from 19.2's anti-pattern table). If a scenario fails the clearance check, the scenario's
  geometry moves; `k` never does.
- **Smoothing the refractive/pinhole hinge with a blend constant** — locked out (real physics, C0
  not C1 is correct for a flat interface).
- **Judging convergence by reprojection RMS** instead of the recorded guard count / optimality
  (anti-pattern #2 from 19.2, carried forward — this is precisely what GEOM-04 exists to prevent).
- **Concluding a fix works from a low frame count.** Every geometry variant in the `stage3-diverges`
  debug session converged at 6 frames with the bug present; the failure needs ~50 frames. All GEOM-05
  acceptance runs MUST be at production frame counts (E4: up to 200; E6: 100 baseline).

## Guard count and inertness (GEOM-04)

**Key finding: the "final solution evaluation" requirement in D-19.3-11 is ALREADY satisfied by the
existing code.** Both `interface_estimation.py:404-424` and `refinement.py:306-321` call
`compute_residuals(result.x, *cost_args, invalid_count_out=invalid_counts)` **exactly once**, after
`least_squares` returns, evaluated at `result.x` (the final solution) — NOT per-iteration. There is
no running/iteration-time count to confuse this with; the guard fires legitimately during
*iteration* only in the sense that intermediate residual evaluations inside `least_squares` itself
may invoke the pinhole extension (that's `_extend_invalid_projections`, called from inside
`compute_residuals` on every solver-internal evaluation) — but the DIAGNOSTIC COUNT the warning
reports is only ever computed once, post-solve, on the final iterate. GEOM-04's job is therefore:

1. **Record, don't just warn.** Currently `n_invalid` is a local variable, discarded after the
   `warnings.warn(...)` call. Thread it out via a new/reused `discard_stats_out` param on
   `compute_residuals` — **`compute_residuals` already carries a `invalid_count_out` parameter that
   does exactly this (append-only list)**, so no new parameter is even needed on that function; the
   work is in `interface_estimation.py`/`refinement.py`, which must forward `n_invalid` into the
   `discard_stats` dict that's already threaded through `optimize_interface`/`joint_refinement` via

   `diagnostics.json` at `pipeline.py:1677`/`validation/diagnostics.py:944-945`).
2. **Key naming.** Follow the existing `discard_stats` naming convention (`pnp_attempts_total`,
   `pnp_guard_rejected`, etc. — flat snake_case keys, no stage prefix in the *dict itself*, but note

## E6 scale axis (GEOM-03)

**Current code (`experiments/e6_generalization_sweep.py:129-166`):**

```python
_BASELINE_DEPTH_BELOW_WATER: tuple[float, float] = (
    GRID_DEPTH_RANGE[0] - GRID_HEIGHT_ABOVE_WATER,
    GRID_DEPTH_RANGE[1] - GRID_HEIGHT_ABOVE_WATER,
)

def _scaled_depth_range(factor: float) -> tuple[float, float]:
    """Scale the baseline's depth-below-water interval by `factor`, then
    re-express it as an absolute Z (world-frame) depth_range by adding back
    `GRID_HEIGHT_ABOVE_WATER` -- keeping the board underwater at every
    scale factor."""
    lo, hi = _BASELINE_DEPTH_BELOW_WATER
    return (
        GRID_HEIGHT_ABOVE_WATER + factor * lo,
        GRID_HEIGHT_ABOVE_WATER + factor * hi,
    )
```

This anchors the scale axis at the **water surface** (`GRID_HEIGHT_ABOVE_WATER`), then scales the
depth-below-surface interval. Per D-19.3-07, this is exactly the mechanism that puts `half_scale`
in conflict with the clearance floor: scaling the standoff *below the surface* by 0.5× also halves
the *available clearance*, while the clearance *requirement* (driven by fixed `square_size` and
fixed tilt) does not shrink.

**Required change:** anchor at the derived floor (`min_depth`, from GEOM-01's derivation function),
not at `GRID_HEIGHT_ABOVE_WATER`:

```python
# Conceptual — exact derivation function name is GEOM-01's to define
_BASELINE_DEPTH_ABOVE_FLOOR: tuple[float, float] = (
    GRID_DEPTH_RANGE[0] - MIN_DEPTH_FLOOR,   # should be 0 at baseline since
    GRID_DEPTH_RANGE[1] - MIN_DEPTH_FLOOR,   # GRID_DEPTH_RANGE[0] IS the floor
)

def _scaled_depth_range(factor: float) -> tuple[float, float]:
    lo, hi = _BASELINE_DEPTH_ABOVE_FLOOR
    return (
        MIN_DEPTH_FLOOR + factor * lo,
        MIN_DEPTH_FLOOR + factor * hi,
    )
```

Every scale value is then legal by construction, since `factor * lo >= 0` for `factor >= 0` and
`lo >= 0` when `GRID_DEPTH_RANGE[0] == MIN_DEPTH_FLOOR` at baseline (or `>=` it with margin).

**Docstring prose that becomes false and must be corrected (D-19.3-07 explicit requirement):**
`e6_generalization_sweep.py:118-122`'s comment block currently says this axis measures "does
accuracy hold as the whole rig/tank scales up or down together" — CONTEXT.md states this claim is
"no longer exactly what the axis measures" once the anchor changes to the derived floor rather than
the water surface, because the board-to-surface standoff stops scaling (deliberately — "standoff is
set by the tank and the target, not by rig size"). The corrected docstring should describe the axis

## Common Pitfalls

### Pitfall 1: Assuming D-19.3-01's centre-based `R_max` is the correct measurement point
**What goes wrong:** implementing the clearance formula with `R_max` from the corner-cloud centroid
under-estimates the true worst-case corner excursion by roughly 2× (see Critical Finding).
**Why it happens:** the board's rotation pivot (corner 0, per `BoardGeometry`/`transform_corners`)
is not the board centre, but nothing in the existing code or docs states this explicitly — it only
falls out of reading `transform_corners`'s `R @ pos + tvec` against `corner_positions`' origin
convention.
**How to avoid:** measure `R_max` as `max(‖corner_local_pos‖)` over `board.corner_positions.values()`
(distance from the pivot, i.e. board-local origin, to each corner) rather than from the corner
cloud's centroid.
**Warning signs:** if the derived floor, once implemented, still allows `DegenerateObservationWarning`
to fire on a handful of frames in a 100+-frame production run even after the "fix" lands, this is
the most likely reason — check corner-Z excursions directly (Monte Carlo simulation, as done in this
research) rather than trusting the formula's algebra alone.

### Pitfall 2: Reusing the OLD `generate_real_rig_trajectory` frozen-anchor test unchanged
**What goes wrong:** `test_generate_real_rig_trajectory_matches_frozen_anchor`
(`tests/unit/test_datasets.py:684-687`) asserts bit-identical output at
`depth_range=(1.1, 2.0)`. This depth_range will become ILLEGAL once GEOM-01 lands (raises
`ValueError`), so the anchor test cannot pass unchanged — it must be regenerated at a NEW, legal
`depth_range`, deliberately and with the regeneration recorded (matching the established pattern:
"anchors are regenerated deliberately with the regeneration recorded").
**Why it happens:** frozen-anchor tests exist specifically to catch UNINTENDED movement; this is one
of the rare cases where movement is intended and must be distinguished from a regression.
**How to avoid:** regenerate the anchor at the new legal `depth_range`, note the regeneration
explicitly in the plan's summary (mirroring how `4ed8259`'s "ideal" preset anchor regeneration under
D-27 was recorded).

### Pitfall 3: E6's paired determinism sweep silently reusing checkpoints
**What goes wrong:** if the second repeat of the 14-config sweep runs against the same `--out`
directory the first repeat used, `e6_configs/*.json` checkpoints from repeat 1 may cause repeat 2 to
silently "resume" rather than genuinely recompute, making the 63/308-style cell-reproduction-count
statistic meaningless (comparing repeat 1 against itself).
**Why it happens:** the resumability feature (review M7, intentional for interrupted-sweep recovery)
and the determinism-testing use case are in tension — the same mechanism that makes an interrupted
sweep resumable also makes an intentional re-run look like a resume.
**How to avoid:** point the second repeat's `--out` at an isolated directory, or explicitly clear
`e6_configs/` before the second invocation. Confirm the exact resume-detection mechanism (checkpoint
presence vs. a flag) before relying on `--force` alone.
**Warning signs:** if repeat 2 completes suspiciously fast relative to repeat 1's measured ~107 min,
it likely resumed from stale checkpoints instead of recomputing.

### Pitfall 4: Treating E3/E5's forced call-site edits as "E3/E5 need re-running for accuracy reasons"
**What goes wrong:** E3 and (the calibration-trajectory half of) E5 are forced to edit their
hardcoded `depth_range=(1.1, 2.0)` call sites purely because GEOM-01 makes that value illegal — NOT
because their science changes. Conflating "this file needs a mechanical edit to keep running" with
"this experiment is part of GEOM-05's five-experiment re-measurement set" risks scope creep (E3 is
explicitly NOT one of the five in D-19.3-18/GEOM-05) or, conversely, under-scoping the mechanical
fix as if it were optional.
**How to avoid:** treat "make E3/E5's hardcoded depth_range calls legal again" as a small, mandatory,
non-optional fix bundled with GEOM-01 (since GEOM-01 is what breaks them), independent of whether E3
itself needs a full re-run under GEOM-05 (it doesn't — E3 is not in the five).

## Code Examples

### The clearance-floor derivation (conceptual signature, GEOM-01)

```python
# Source: derived from D-19.3-01/02/03 (19.3-CONTEXT.md) + this research's Critical Finding
def _min_legal_depth(
    board: BoardConfig,
    water_zs: dict[str, float],
    rotation_range_deg: float,
    margin_factor: float = 0.1,  # k=0.1, NEVER tuned to make a case pass
) -> float:
    """Derive the minimum board-centre depth that keeps every corner submerged.

    R_max is measured as the maximum distance from the board's rotation pivot
    (board-local origin, i.e. BoardGeometry corner_positions' frame -- NOT the
    corner cloud's centroid, since transform_corners rotates about the origin,
    not the centre) to any corner.
    """
    geometry = BoardGeometry(board)
    pivot_distances = [
        float(np.linalg.norm(pos)) for pos in geometry.corner_positions.values()
    ]
    r_max = max(pivot_distances)
    theta = np.deg2rad(rotation_range_deg)
    theta_normal = theta * np.sqrt(2)  # combined-axis tilt, per D-19.3-01
    deepest_water_z = max(water_zs.values())
    return deepest_water_z + (1 + margin_factor) * r_max * np.sin(theta_normal)
```
