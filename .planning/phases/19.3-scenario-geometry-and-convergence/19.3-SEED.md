## What we found, and how

Phase 19.2 plan 27 added solver-optimality capture to E6 (closing WR-02). On its first run
(plan 28) it immediately exposed something nobody was looking for.

**Three of fourteen E6 configurations sit 3–4 orders of magnitude above the rest in first-order
optimality, and every one was published under `status="ok"` with a plausible reprojection RMS:**

| axis | value | RMS px | optimality (interface) | optimality (intrinsic) |
|---|---|---|---|---|
| index | 1.42 | 0.789 | **51.92** | 0.054 |
| scale | half_scale | 1.007 | **27.32** | **140.31** |
| layout | ring | 0.705 | 0.0016 | **4.20** |
| the other 11 | | 0.70–0.78 | 0.0016–0.035 | 0.002–0.117 |

### But the accuracy is fine — this is a diagnostic failure, not a bad answer

| group | n | reconstruction RMSE mean | max | water_z error mean |
|---|---|---|---|---|
| high-optimality | 3 | 0.5938 mm | 0.7174 | 3.71 mm |
| healthy | 11 | 0.5622 mm | 0.7516 | 3.56 mm |

Indistinguishable. `half_scale` — optimality 27/140 — has the **best** reconstruction accuracy in the
table (0.4935 mm), while the **worst** reconstruction belongs to `double_scale`, which is healthy on
optimality. These are synthetic scenarios scored against ground truth, so reconstruction error is the
direct measure of correctness, and it says the solutions are good.

### Root cause: board corners protrude through the water surface

Every one of the 14 configurations emits `DegenerateObservationWarning` — 22 warnings total. Corners
land at or above the interface, where the refractive model has no solution, and are continued with a
pinhole projection.

Measured on the baseline scenario (12 cameras, 100 frames, seed 42):

| | |
|---|---|
| frames with ≥1 corner above the interface | **2 / 100** |
| corners above the interface | **61 / 8800 (0.69%)** |
| worst protrusion | **66.1 mm above the surface** |
| shallowest board centre | 1.1049 m = **80.4 mm** below the shallowest `water_z` (1.024489) |
| board half-extents | 0.330 × 0.240 m (12×9 squares × 0.06 m) |
| default tilt | `rotation_range_deg = 15.0`, applied independently to both axes |
| clearance needed at 15° on both axes | **147.5 mm** |
| implied minimum safe centre depth | **~1.18 m** — current `GRID_DEPTH_RANGE` starts at **1.100** |

So the shallow limit is ~70–80 mm too shallow for this board and tilt range. **0.69% of corners is
enough to inflate optimality by four orders of magnitude**, because optimality is a max-norm and a
handful of kinks dominates it.

`corr(degenerate count, optimality) = 0.646` across the 14 configurations.

### The same kink also makes the solution non-unique

Plan 28's re-run moved 63 of 308 cells (worst 6.1e-5 relative, most ~1e-6) against the committed
values. A direct probe settled the cause: **the same configuration run TWICE on IDENTICAL code gives
different answers.**

| `scale_half_scale`, seed 42, same tree | rms | focal_error_pct |
|---|---|---|
| run 1 | 1.0071565426644968 | 0.0831694334341944 |
| run 2 | 1.0071564703805398 | 0.08316997058208937 |
| delta | −7.2e-8 (rel) | 6.5e-6 (rel) |

Iteration counts are byte-identical between sweeps and costs match to all printed digits, but
optimality differs by up to 2×. Near a minimum, cost moves as O(δ²) and the gradient as O(δ), so a
~1e-6 difference in the final iterate is invisible in cost and loud in optimality. A C0-but-not-C1
residual does not pin the minimum down: several nearby iterates all satisfy the termination test.

`corr(degenerate count, movement) = 0.19` — weak, so the link between degeneracy and *movement* is
suggestive, not established. Worth testing properly in this phase. (Every configuration with ≤2
degenerate observations reproduced bit-exactly; every one with ≥6 moved — but the baseline, with 12,
also reproduced exactly, so a simple threshold rule does not hold.)

## The key insight — do NOT try to smooth the hinge

**The pinhole continuation is not a hack, and the kink is not a modelling artifact.** For a point
*above* the water surface there is no water between camera and point, so the straight-line pinhole
projection is the *physically correct* model. The two models agree in value at the interface (C0) but
not in derivative, because the refractive side carries the n₁/n₂ bending factor. **For a flat
interface, that derivative discontinuity is real physics.**

So the fix is NOT to blend the two models smoothly. A blend would:
- introduce an arbitrary blend-width constant — anti-pattern #6 in 19.2's table, *"adding a constant
  that makes a failing case pass"*, which that phase was already bitten by once; and
- make the residual non-physical inside the band.

**The fix is to stop putting board corners on the interface**, which is what a real calibration does
anyway (user, 2026-08-01: *"in a real-life calibration, we would always keep the board underwater"*).
The synthetic generator is unfaithful to practice, not the model.

---

## Proposed fix, three parts

### 1. Scenario — derive the depth limit, don't hardcode it

```
min_depth ≥ max(water_zs) + (half_x + half_y)·sin(rotation_range) + margin
```

Computed from `BoardConfig` and the rotation range, and asserted at scenario construction, so it
cannot silently break when the board size or tilt range changes. A derivation, not a magic constant.

Note `water_zs` is **per-camera** (1.0245–1.0367 in the baseline, because interface tilt is enabled),
so use the deepest for safety.

### 2. Keep the pinhole continuation, but demote it

The optimizer needs a **total** residual — a defined value for every parameter vector it tries,
including intermediate iterates where an estimated pose or `water_z` transiently puts a corner above
the estimated interface. Removing it re-opens exactly the defect `7e0cb90` fixed (undefined/NaN
residual → zero-gradient absorbing region).

What changes is its status: from a *modelling branch that routinely fires* to a *numerical guard that
should never fire at convergence*. Firing at the solution should become a loud failure with the count
recorded, because it means the scenario is invalid or the solve wandered.

**The prize: this restores optimality as a meaningful convergence measure.** No kinks at the solution
means the gradient can actually reach zero — the assumption the whole WR-02 fix rests on.

### 3. Correct the warning text (a shipped-library defect, independent of the rest)

`DegenerateObservationWarning` currently says *"judge convergence on optimality, not on the
reprojection RMS"* — advice that is wrong in precisely the situation that emits it, since the
continuation is what inflated optimality. It should say optimality is unreliable when this fires.

## Blast radius and re-run sequence

`generate_real_rig_trajectory` carries the **same** `depth_range = (1.1, 2.0)` default as the grid
family, so this is not confined to E4/E6.

| experiment | affected | re-run cost |
|---|---|---|
| E4 grid | yes (D-29 coupling) | ~3.5 h |
| E6 sweep | yes | ~1.8 h |
| E7 | yes (10 seeds) | ~1 h |
| E1 | yes (5 seeds) | ~0.5 h |
| E5 | yes | ~0.35 h |
| **E2** | **NO — real data**, unaffected by a scenario change | — |

**≈7 hours of serialized box time.** Two overnights. Comfortable inside the 2026-08-21 deadline.

**Critical scoping constraint:** part 2 touches library code. If it is not provably inert, **E2's §3
numbers come back into scope** and the blast radius becomes six experiments including the one that
takes 48–87 minutes on real data. Scope the change to the diagnostic path and prove inertness by
test, the way 19.2 plan 27 did (exact-equality tests against the uninstrumented path).

Per D-26: **all code changes land and are proven inert BEFORE any run that yields a publishable
result.** Per review H4: **one production run per wave.** That implies a code-only wave first, then
one wave per experiment.

## Decisions already taken (user, 2026-08-01) — do not reopen

- **Fix it properly rather than document it.** *"20 days is a lot of time, I'm not against re-running
  if we can genuinely fix this. The reviewers are clearly knowledgeable about and interested in the
  optimization complexities, and this flaw in the construction is going to be pretty obvious now with
  these results."*
- **Real calibrations keep the board underwater**, so the generator should match.
- **Keep the pinhole fallback** (see part 2) rather than removing it.
- **Finish 19.2 first** so there is a coherent baseline to measure the fix against, and isolate this
  work as its own phase rather than extending an already-sprawling one.

## Open questions for discuss-phase

1. **Margin above the derived minimum** — how much, and justified how? Resist a round number chosen
   by feel; derive it or measure it.
2. **Does the real rig's own trajectory need the same treatment**, or only the synthetic generators?
   E2 uses real data, but `generate_real_rig_trajectory` is used by synthetic E1/E5/E7.
3. **Should `rotation_range_deg = 15°` stay?** A larger tilt improves intrinsic observability but
   needs more depth. There is a real trade here, and the current value may not be the right one once
   depth is derived from it.
4. **Does D-29's E4/E6 coupling survive?** Changing `GRID_DEPTH_RANGE` invalidates the coupled grid;
   both must move together, and `WATER_Z` is frozen by user decision (do NOT re-derive it).
5. **How should the before/after be reported in the manuscript?** The numbers will move across five
   experiments. Framing matters: this is a corrected benchmark construction, not a change in library
   accuracy — and the accuracy evidence above supports that framing.
6. **Is the degeneracy↔movement link real?** corr 0.19 is weak. Worth a proper test, because if the
   fix removes the non-determinism too, that is a strong result worth reporting.

## Things not to do

- Do not smooth the hinge with a blend constant (see "key insight").
- Do not re-derive `WATER_Z` — frozen at 1.031 by user decision; E4/E6 are coupled to it by D-29.
- Do not quote optimality to more than one significant figure anywhere; it varies ~2× run-to-run.
- Do not assert bit-identical reproduction as a gate on marginally-conditioned configurations —
  19.2 plan 29 was amended for exactly this reason. Attribute movement to a mechanism instead.
