## F1 — `degenerate_observations_at_solution` conflates two opposite cases

**Where:** `src/aquacal/calibration/_optim_common.py:699-712`

`n_invalid` increments once per observation whose *refractive* projection returned
NaN. But the handling immediately below splits those into two categories with
opposite numerical character:

| case | handling | gradient |
|---|---|---|
| corner at/above interface | pinhole continuation (`_extend_invalid_projections`) | smooth, non-zero |
| point behind camera | `INVALID_PROJECTION_PENALTY_PX = 100.0` | **exactly zero** |

The second case is the original `7e0cb90` absorbing-region defect, still present
by design ("no continuous extension exists" — which is true). The problem is not
that it exists; it is that **the published count does not distinguish it**.

Consequences:

- A non-zero `degenerate_observations_at_solution` is uninterpretable without the
  split. "14,949 observations were continued smoothly" and "14,949 observations
  are pinned at a flat 100 px with zero gradient" are very different statements
  and currently render identically.
- The gate direction is safe: a count of **0** genuinely means neither case
  occurred, so phase 19.3's headline claim is unaffected.
- It is only the *diagnostic* that is ambiguous, and only when non-zero.

**Does this undermine MF-08's claim that E1's 14,949 is bookkeeping?** No — but
the null-direction proof alone does NOT establish it, and I should not have
implied it did. Behind-camera status is independent of `water_z`, so a
constant-cost `water_z` sweep looks identical either way. What settles it is the
pinned run: pinning `water_z` at ground truth drove the count to **exactly 0**,
and pinning cannot rescue a behind-camera point. Therefore all 14,949 were the
benign above-interface case. Claim survives on a better argument.

**Proposed fix (after the sweep):** count the two cases separately, e.g.
`degenerate_observations_at_solution` (continued) and
`unextendable_observations_at_solution` (flat-penalty). Purely additive to the
diagnostics sink; no numerics change. Until then, MF-08 should note that a
non-zero count would need the split before interpretation.

**Status:** does not change any current published number.

## F10 — `_build_dataframes` accepts a `seed` argument and silently ignores it

**Where:** `experiments/e1_refractive_comparison.py:279` (signature) and `:327`

`_build_dataframes(scenario, results, seed, test_depths=None)` is called as
`_build_dataframes(scenario, results, args.seed)`, but the only seed actually used
inside is `depth_seed = 42 + int(depth * 100)` -- hardcoded to 42, not derived from
the argument. Grep inside the function body finds exactly three mentions of "seed":
the signature and two `seed=depth_seed` call sites.

Verified empirically: `n_points` per depth is byte-identical across all ten sweep
seeds (4054 / 4247 / 4282 / 4294 ...), so the evaluation test set and its detection
noise are constants across the entire sweep.

**Consequences:**
1. **The measured band is the correct reproducibility number.** Anyone running
   `--seed N` gets exactly the corresponding sweep result, because the CLI really does
   behave this way. 97-178x is what a reproducer sees.
2. **The band is calibration-variance only** -- a lower bound on total variance if the
   evaluation set were also resampled. Worth stating whenever the band is quoted.
3. **Latent trap:** a maintainer who "fixes" the dead parameter to honour `args.seed`
   silently invalidates every band recorded in MF-05 and MF-08. If that change is ever
   made, the bands must be re-measured, not carried forward.

**Not a defect in any published number.** A fixed evaluation set is arguably the
cleaner design for isolating calibration variance; the problem is that the signature
advertises control it does not provide.
