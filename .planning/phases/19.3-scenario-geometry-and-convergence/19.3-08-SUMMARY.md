## Task 1 — E6's verified resume mechanism

**Finding 1 (the one the plan flagged as needing a live test, not just a read): `--smoke` does
NOT exercise the production resume path.** `_run_smoke_configs` unconditionally calls
`run_sweep(..., force=True, ...)` for its main pass — every configuration is recomputed
regardless of what's on disk — then separately probes the skip-path with one hand-picked
config at `force=False` (a self-test built into the smoke path, `run_configuration` at
`e6_generalization_sweep.py:1085-1114`). Running `--smoke` twice against the same `--out`
therefore does **not** demonstrate whether the full sweep resumes — it demonstrates the internal
probe passing, which is a narrower claim.

**Finding 2 (verified via a direct-call live probe, not `--smoke`):** `run_configuration` — the
exact function `_run_full` calls — gates resume on **checkpoint file presence AND `force=False`**
(`e6_generalization_sweep.py:730`), never on `--force` alone. Live probe (`n_frames=3`, seed 42,
baseline config, scratch directories):

```
[A] first call (fresh dir), force=False: status=ok elapsed=175.07s   (genuine solve)
[A] second call (SAME dir), force=False: status=ok elapsed=0.00s     (skipped, cached checkpoint returned verbatim)
[B] call against a DIFFERENT (fresh) dir, force=False: status=ok elapsed=173.85s  (genuine re-solve)
```

Exact commands run (via a scratch Python script calling `run_configuration` directly, not the
CLI): see the probe embedded at the top of this section's log — `run_configuration(config,
seed=42, n_frames=3, out_dir=<dir>, force=False)` called once against a fresh directory, once
again against the same directory, and once against a second fresh directory.

**Consequence:** `--force` is not the mechanism that guarantees a genuine second computation — a
fresh, isolated `--out` directory is, because no checkpoint can exist there. This is exactly why
D-19.3-20 rejects `--force` on a shared directory as the isolation mechanism: it would work
*only if `--force` were reliably remembered*, whereas a distinct directory makes resume
structurally impossible regardless of the flag.

**Named positive re-solve signal for repeat 2 (what plan 09 asserts):** zero occurrences of the
string `"already exists (resumability)"` in repeat 2's own stage log — this is the exact message
`run_configuration` logs on every skip (`e6_generalization_sweep.py:744-748`). Elapsed wall-clock
time per configuration is a secondary corroborating signal (a skip is ~0 s; a genuine solve is
the full per-config runtime), but the log-line count is the primary, greppable assertion
`rerun_19_3.sh` itself computes and prints after repeat 2 (see Task 3).

**Finding 3 (E6 does not literally emit `status="skipped_existing"`, unlike E4):** the plan's own
task text asked whether the second invocation "reports `skipped_existing`." It does not — E6's
`run_configuration` returns `cached.get("status", "failed")` verbatim on a skip, which for a
healthy prior run is `"ok"`, not a distinct skip-status string. `"skipped_existing"` is E4's
convention (`e4_benchmark_grid.py`), not E6's. This is why the named re-solve signal above is
log-based, not status-based — a status-based check would be silently vacuous for E6.

## Task 2 — `check_rerun_gates.py`

Four gates, applied per experiment (E1, E3, E4, E5, E6, E7):

1. **Guard count** — `degenerate_observations_at_solution == 0` everywhere it's recorded. A
   **missing** field is treated as FAIL, not as an implicit zero — an un-instrumented artifact is
   not evidence of a clean solve. This is exactly what makes the gate fail correctly on the
   current, pre-plan-19.3-07 committed artifacts.
2. **Published status** — no row/cell published with `status == "degenerate"`. Reported **N/A**
   (with a named reason), not silently skipped, for every artifact that carries no `status`
   column at all (E1, E5, E7 — the record-only experiments per plan 19.3-07's harness-gating
   split) and for E3 (no calibration at all).
3. **Provenance completeness** — `environment.git_sha`, a seed, and the water refractive index
   present per artifact, PLUS one cross-artifact check that every `git_sha` found across the
   **whole run** is identical (the machine-checkable form of "commit nothing while a run is in
   flight"). E3's sidecar is exempted from the water-index sub-check (E3 never touches one); E5's
   sidecar is checked against `n_true` rather than `n_water` (E5 sweeps assumed-vs-true index, so
   its field is named differently). **This project's provenance schema carries no explicit
   timestamp field anywhere** (verified by inspection of `capture_environment` and every
   `build_provenance_sidecar`) — the gate substitutes the artifact file's own filesystem mtime as
   that evidence and documents this explicitly in the module docstring, rather than silently
   treating "timestamp" as satisfied by nothing.
4. **Optimality presence** — first-order optimality present (never null), for every stage. N/A
   for E3 (no calibration) and for E5 (its committed artifacts record no per-stage optimality at
   all — confirmed by inspection, not assumed).

E3 is handled explicitly, not by omission: gates 1, 2 and 4 print
`N/A ... E3 runs no calibration (N/A per this gate script's design, see plan 19.3-08)` rather than
being absent from the report.

## Task 3 — `rerun_19_3.sh`

**Seven stages, in this order, with expected wall clock:**

| # | stage | expected wall clock | invocation(s) |
|---|---|---|---|
| 1 | `e3` | ~10 s | `--check` (records pre-regeneration tier state) then `--force` (regenerates), in that load-bearing order |
| 2 | `e7` | ~7 min | `--force` |
| 3 | `e1` | ~20-25 min | `--force` |
| 4 | `e5` | ~21 min | `--force` |
| 5 | `e6_repeat1` | ~107 min | `--force`, into the shared `experiments/results/` — this **is** the production E6 re-run **and** determinism repeat 1 (D-19.3-13) |
| 6 | `e6_repeat2` | ~107 min | `--force`, into an **isolated** `experiments/results_e6_repeat2/` (D-19.3-20) |
| 7 | `e4` | ~3.15-3.5 h | `--force` |

Total ≈ 9 h, matching D-19.3-13's costed estimate.

**Why E3's `--check` runs before its `--force` (source-verified, not just documented):**
`grep -n -- "--check\|--force" experiments/rerun_19_3.sh | grep e3_derived` shows `--check` at
line 149, `--force` at line 156 — `--check` first by line number. Tier 2
(`newton_iterations.csv`) is geometry-dependent and expected to move (134 mismatched cells,
plan 19.3-05); tiers 1 and 3 are not, and running `--force` first would regenerate all three
before the pre-fix tier-2 mismatch was ever recorded, destroying the only evidence of what moved.

**E6 isolation (source-verified):** the two `e6_generalization_sweep` invocations use different
`--out` values (`experiments/results` vs `experiments/results_e6_repeat2`); neither uses `--force`
against a *shared* directory as the isolation mechanism — repeat 2's isolation is the distinct
directory itself, per Task 1's finding that a fresh directory (not the flag) is what structurally
prevents a resume. After repeat 2, the script computes and logs the positive re-solve signal named
in Task 1: the count of `"already exists (resumability)"` lines in repeat 2's own captured stdout
(expected: `0`).

**Stage-level recovery state.** Location: `experiments/rerun_19_3_state.tsv` (repo-root-relative,
append-only). Format: `<stage>\t<stage-index>\t<start|complete>\t<ISO-8601 UTC timestamp>\t<exit-code-or-empty>`.
A start line is written before a stage launches; a completion line is written only after it
returns. A stage that started and died therefore carries a start line with **no** matching
completion line, and `is_stage_complete()` (an `awk`-based check, chosen over `grep -P` after a
live locale warning on this Windows/Git-Bash box) only returns true when a `complete` line exists
for that stage — a started-but-died stage is never mistaken for done.

**Verified mechanics (a dry-run substitution mode, `RERUN_19_3_DRY_RUN=1` +
`RERUN_19_3_DRY_RUN_CMD`, used ONLY for these tests — never cited as evidence about geometry or
convergence, and never launching a production run):**
- Full 7-stage run: all 7 stages executed in declared order, 7 start + 7 complete lines, 14 gate
  verdict blocks (begin+end per stage), exit 0.
- **Kill-mid-stage simulation:** pre-seeded the state file with `e3`/`e7` complete and `e1`
  start-only (simulating a process killed mid-`e1`). Re-invoking the script: `e3`/`e7` were
  skipped ("already has a recorded completion line"), `e1` was **re-run from scratch** (a second
  `start` line was appended for `e1`, followed by its own `complete` line) rather than being
  treated as done, and the queue continued through the remaining stages to completion.
- **`resume-from-stage-N`:** invoking `bash experiments/rerun_19_3.sh 5` skipped stages 1-4
  ("below the requested start stage 5") and ran stages 5-7.

## Deviations from Plan

**1. [Rule 1 - discrepancy, not a bug] Gate 3's "timestamp" field does not exist in this
project's provenance schema.** Found during Task 2. `capture_environment()` and every
`build_provenance_sidecar` in `experiments/` were inspected directly; none emits an explicit
timestamp field. The gate script substitutes each artifact file's own filesystem mtime and
documents this substitution in its module docstring rather than silently treating the
requirement as satisfied by nothing. No `src` or `experiments/` schema change was made to add a
timestamp field — that would be an architectural addition to a settled schema, out of this
plan's `files_modified` scope, and is flagged here rather than done silently.

**2. [Rule 1 - discrepancy] E3's provenance sidecar has no water-refractive-index field.** The
plan's Gate 3 language names `git_sha, seed, n_water` as universally required, but E3 runs no
calibration and its `e3_provenance.json` never carries an `n_water`/`n_true` value. Implemented
as a per-artifact `require_water_index` flag, `False` for E3 only, documented in the gate
script's own docstrings.

**3. [Rule 1 - discrepancy] `--smoke` does not exercise E6's production resume path.** Discovered
during Task 1's live testing (see above) — `_run_smoke_configs` always passes `force=True` to
`run_sweep`. The plan's task text asked for a `--smoke`-based live test; a direct-call probe of
`run_configuration` (the function `_run_full` actually calls) was substituted instead, since the
`--smoke` path would have produced a false "resume works" reading. Documented as Finding 1 above,
not silently worked around.
