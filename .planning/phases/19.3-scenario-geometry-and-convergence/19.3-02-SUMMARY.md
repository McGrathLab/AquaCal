# Phase 19.3 Plan 02: Convergence guard -- record degeneracy count, correct warning text, prove inert Summary

**Demotes the pinhole continuation from a silent numerical rescue to a recorded diagnostic: `discard_stats['degenerate_observations_at_solution']` now carries the final-solution guard count from both solver stages into `diagnostics.json`, the `DegenerateObservationWarning` text is corrected in all three places, and the recording change is proven inert by exact-equality test -- keeping E2 out of this phase's scope.**

## Accomplishments

- **Task 1 (Warning text correction, D-19.3-12):** All three sites that previously said "judge convergence on optimality, not on the reprojection RMS" -- `schema.py`'s `DegenerateObservationWarning` docstring, `interface_estimation.py`'s literal message, `refinement.py`'s literal message -- now state that first-order optimality is **UNRELIABLE** as a convergence measure when the warning fires, because the pinhole continuation puts the residual on a C0-but-not-C1 kink at exactly that point. Neither optimality nor RMS should be trusted when this fires; the fix is correcting the scenario geometry, not re-tuning the solver. A new `TestDegenerateObservationWarning` class in `test_schema.py` asserts both the corrected substance ("unreliable" present) and the absence of the old backwards advice.
- **Task 2 (Record the guard count, D-19.3-11):** Added `degenerate_observations_at_solution` to the closed `DISCARD_KEYS` vocabulary. Both `interface_estimation.py`'s existing guard block and `refinement.py`'s existing guard block now call `_bump(discard_stats_out, "degenerate_observations_at_solution", n_invalid)` unconditionally (present-and-zero on a clean run), immediately after the pre-existing single post-solve `compute_residuals(result.x, ...)` call -- no new evaluation site was added. `joint_refinement` gained a new `discard_stats_out: dict[str, int] | None = None` trailing parameter (it previously had none), forwarded from both places that already thread `discard_stats` to `optimize_interface`: `datasets/pipelines.py::calibrate_synthetic`'s `joint_refinement` call and `calibration/pipeline.py`'s `joint_refinement` call site. The library never raises on a non-zero count.
- **Task 3 (Exact-equality inertness proof, D-19.3-11 reasoning point 2):** New `tests/synthetic/test_guard_inertness.py`, reproducing 19.2 plan 27's proof pattern exactly. Three parametrizations against the "ideal" scenario (cheapest, deterministic, 4 cameras/20 frames/0 noise) cover both solver stages and both `normal_fixed` values real experiment call sites use: Stage-3-only (calibrate_synthetic's own defaults), with the intrinsic pass (exercising `joint_refinement`'s new parameter), and `normal_fixed=False` with the intrinsic pass (E2's real-rig / `tab:cpr` configuration). All three assert exact bit-identity (`==` / `np.testing.assert_array_equal`, never a tolerance) across extrinsics R/t, per-camera water_z, every board pose rvec/tvec, and final RMS, between a run with `discard_stats_out=None` and one with `discard_stats_out={}`. **All three pass. Exact equality held in every parametrization -- the recording change is provably inert.**

## Decisions Made

- **Single flat `degenerate_observations_at_solution` key**, summed across every solver-stage call in a run, not per-stage-suffixed. This follows 19.2-27's E5 band-summed precedent and D-19.3-11's own framing: "did degeneracy occur anywhere in this calibration run" is a whole-run question, and any non-zero count invalidates the optimality diagnostic for the whole run regardless of which stage produced it.
- **`_bump` is unconditional**, called immediately after `n_invalid` is computed and BEFORE the `if n_invalid > 0:` branch that triggers the warning -- this is what makes "requested and zero fired" (`{}`) distinguishable from "never requested" (`None`), matching the convention 19.2-27 established.
- **`compute_residuals`, `_extend_invalid_projections`, and `cost_args` are untouched.** The research file's early exploration suggested wiring through `_optim_common.py`; the locked plan text explicitly forbids touching those three, and the existing single post-solve `compute_residuals(result.x, *cost_args, invalid_count_out=invalid_counts)` call in each guard block already satisfies D-19.3-11's "final solution evaluation, not any evaluation" requirement -- no new evaluation site was needed.
- **The `>0` guard-count test constructs board poses directly** (hand-built `BoardPose` list, not via `generate_board_trajectory`/`generate_real_rig_trajectory`), per the plan's explicit instruction, since 19.3-01 makes those generators raise on a shallow `depth_range`. Seed 2 with `depth_range=(0.155, 0.18)` against water at 0.15 was empirically verified (2026-08-01) to leave 2 observations unprojectable at the converged solution -- a legitimate "solver wandered to an estimated pose above the estimated interface despite a legal ground-truth scenario" case (D-19.3-11 point 3), pinned in the test's docstring rather than re-derived on every run.
- **The inertness test replicates `calibrate_synthetic`'s internal call sequence directly** (`build_pose_graph` / `estimate_extrinsics` / `optimize_interface` / `joint_refinement`) rather than calling `calibrate_synthetic` itself, because `CalibrationResult` does not expose board poses and the plan's required behavior list explicitly includes "every board pose rvec/tvec" in the bit-identity assertion. The call shape (arguments, defaults, sequencing) matches `calibrate_synthetic`'s own internals exactly.
