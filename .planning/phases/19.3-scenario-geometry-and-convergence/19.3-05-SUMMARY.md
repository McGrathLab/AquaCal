# Phase 19.3 Plan 05: E3/E4/E5 Board-Threading and Derived Clearance Summary

**Derives `GRID_DEPTH_RANGE` from `board_clearance_floor` at import time, threads `board=GRID_BOARD_CONFIG` through `build_grid_scenario`, and updates E3's and E5's three hardcoded `depth_range=(1.1, 2.0)` call sites -- closing all 8 test failures left by plan 19.3-01's required `board` parameter.**

## Accomplishments

- `GRID_DEPTH_RANGE` is now a computed-at-import value: `(board_clearance_floor(GRID_BOARD_CONFIG, water_zs, 15.0), 2.0)`, where `water_zs` comes from the SAME `generate_camera_array(n_cameras=12, layout=GRID_LAYOUT, spacing=GRID_SPACING, height_above_water=GRID_HEIGHT_ABOVE_WATER, seed=42)` construction `build_grid_scenario` itself performs -- computed value is `(1.181852..., 2.0)`, matching plan 19.3-01's ~1.1819/1.181 reference figure. Moving `GRID_SPACING` block ahead of it in the constants section was required (Rule 3 -- blocking `NameError` on the original placement).
- `build_grid_scenario` now passes `board=GRID_BOARD_CONFIG` to `generate_board_trajectory`. Confirmed (not assumed) that `run_grid_cell`'s held-out trajectory goes through a SECOND `build_grid_scenario` call (`holdout_scenario = build_grid_scenario(n_cameras, n_frames, holdout_seed)`) rather than a bare `generate_board_trajectory` call, so it inherits the fix automatically -- no separate edit needed there.
- E3's `build_newton_iterations_df` now passes `board=_REAL_RIG_BOARD_CONFIG`, `water_zs=water_zs`, `depth_range=None` (derived) instead of the hardcoded `(1.1, 2.0)`.
- E5 gained a new `_e5_real_rig_depth_range(water_zs)` helper (`board_clearance_floor(BOARD_CONFIG, water_zs, _E5_ROTATION_RANGE_DEG=20.0)`, matching `generate_real_rig_trajectory`'s own internal 20 deg tilt) called at BOTH `build_real_rig_scenario` (the calibration trajectory) and the held-out trajectory site inside `run_index_point`, passing the SAME `water_zs` (the scenario's own, not independently re-fetched) at both call sites -- so the two trajectories cannot resolve to different depths by construction.
- Added tests: `GRID_DEPTH_RANGE` matches an independent recomputation and moves when `GRID_BOARD_CONFIG.square_size` changes; no corner protrudes above `max(water_zs)` at a production 12x100 cell; every declared grid cell (8/12/16 cameras x 50/100/200 frames) constructs legally at its own real production `n_frames` with zero `calibrate_synthetic` calls; the E4 holdout-geometry spy test now also asserts `board=` matches between the calibration and holdout calls; a new E5 spy test proves the calibration and held-out `generate_real_rig_trajectory` calls share one `depth_range` and one `board`, differing only in `seed`.

## Decisions Made

- **GRID_DEPTH_RANGE's anchor camera count is 12**, matching E6's own documented baseline (`build_grid_scenario(12, <baseline frames>, seed)`, D-11) and this module's own comments describing the 12-camera cell as canonical -- not an arbitrary choice, and not one of the swept `CAMERA_COUNTS` picked at random.
- **E5's two trajectories share `water_zs` by value, not just by equal derivation** -- `run_index_point`'s holdout call passes `scenario.water_zs` (the SAME dict object produced inside `build_real_rig_scenario`), not a fresh `generate_real_rig_array()` call. This makes the "cannot drift apart" property structural rather than an artifact of both calls happening to use the same deterministic no-seed generator.
