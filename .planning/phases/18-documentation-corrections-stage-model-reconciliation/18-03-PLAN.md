<objective>
Give the v1.7-v1.8 features a proper documented home by creating
`docs/guide/configuration.md` — the repository's first configuration reference page —
registering it in the guide index, and adding forward links from troubleshooting (DOCS-04).

Purpose: `reject_outlier_frames`, `detection.start_frame` / `detection.stop_frame`, the
seeded `cv2.calibrateCamera` intrinsics initialization, and the fronto-parallel view-diversity
warning shipped in v1.7-v1.8 but are documented only in `docs/guide/troubleshooting.md` (the
first two) or nowhere at all (the last two). Troubleshooting is where a user lands when
something breaks, not where features should be introduced. Config material today is split
between `docs/guide/cli.md` and the autodoc'd `docs/api/config.rst`, neither of which is a
place a user browses for "what keys exist". Phase 21's DOCS-05 will add four more surfaces on
top of this page, so it is worth creating now.

Output: A new guide page, its registration, and cross-links.

This plan is deliberately independent of the manuscript-vocabulary checkpoint (plan 18-02):
none of these features are stage-vocabulary-dependent. It therefore owns
`docs/guide/index.md` and `docs/guide/troubleshooting.md` in wave 1 for the DOCS-04 edits
only. The stage-vocabulary edits to those same two files (index.md line 9's "Four-stage
calibration pipeline", troubleshooting's eleven "Stage 3/4" phrasings) belong to plan 18-08
and are sequenced into a later wave by that file overlap. D-16's "in the same edit"
instruction is therefore split across two commits — its substance (page linked, stage line
fixed) is fully honored, but the stage half is checkpoint-gated and this half is not.
</objective>

    The four DOCS-04 features must each get a substantive entry, not a one-line mention:

    1. `optimization.reject_outlier_frames` (default `true`) — after the main bundle
       adjustment, per-frame reprojection RMS is scored against INDEPENDENTLY estimated
       per-frame board poses, catastrophic outliers are dropped, and the solve is re-run once.
       No-op on clean data. Document the three tuning keys with their real defaults:
       `frame_rejection_k: 5.0` (reject above k x median per-frame RMS),
       `frame_rejection_floor_px: 5.0` (and only if RMS also exceeds this absolute pixel
       floor), `frame_rejection_max_fraction: 0.25` (guardrail — if more than this fraction
       would be dropped, rejection is suppressed and a warning is emitted, so a broadly
       contaminated dataset surfaces loudly instead of being silently gutted).
    2. `detection.start_frame` / `detection.stop_frame` — inclusive start, exclusive stop,
       applied uniformly to all EXTRINSIC cameras so frame-index synchronization is preserved,
       and with no effect on intrinsic calibration videos. State the discrimination rule from
       troubleshooting: automatic rejection catches discrete catastrophic frames; a contiguous
       segment of mildly contaminated frames needs a manual trim, because position in the
       capture is the meaningful signal there. Link to the contaminated-frames section of
       `troubleshooting.md` for the diagnostic workflow.
    3. Intrinsics seeding — this has NO config key; it is always-on v1.8 behavior and belongs
       under `paths`/`cameras` or its own "In-air intrinsic calibration behavior" subsection.
       Document that `cv2.calibrateCamera` is invoked with `CALIB_USE_INTRINSIC_GUESS` and a
       physically plausible seed (fx = fy = max(image width, height), principal point at image
       center) instead of OpenCV's DLT-based auto-init, because the homography-based
       auto-init can be badly ill-conditioned for some board-pose distributions and send the
       nonlinear refinement into a wildly wrong local minimum (fx off by 2-3x with implausible
       distortion), which then poisons extrinsic initialization downstream. State that the
       seed was verified to reproduce the unguided result to 6+ significant figures for
       well-behaved cameras. Use `:class: tip`.
    4. The fronto-parallel warning — also no config key. Document that after in-air
       calibration, `validate_view_diversity` inspects the board-view angle distribution and
       emits a `UserWarning` naming the camera when views were held nearly fronto-parallel
       throughout, because that leaves focal length degenerate with board distance. Tell the
       reader what to DO about it (re-shoot with tilted board views), not just that it exists.
       Use `:class: warning`. Cross-reference
       `{func}`aquacal.calibration.intrinsics.validate_view_diversity``.

    Add `(configuration-frame-trimming)=` and `(configuration-frame-rejection)=` anchors above
