# AquaCal — Experiment Suite consolidation and execution plan

**Context:** the AquaCal SoftwareX paper is in minor revision (revised MS due **2026-08-21**).
This document covers the **experiment side**: consolidating every run that produces a number
or figure in the manuscript into one directory, porting the experiments that already exist,
and specifying the new runs the reviewer response requires.

**Relationship to the other desktop docs:**

| Doc | Covers |
|---|---|
| `aquacal-post-review-milestone.md` | **Library** work — instrumentation, hooks, ablation mode, docs. Explicitly scopes out running the experiments. |
| `aquacal-docs-accuracy-fixes.md` | Line-level doc corrections (Phase 18 input) |
| `aquacal-column-grouping-change.md` | The CPR structural grouping change (landed) |
| **this doc** | The experiments themselves — directory, ports, new runs, provenance, sequencing |

**Guiding principle:** every quantitative claim in the manuscript and supplement should trace
to one committed script, one committed output file, and one figure generator. The paper has
already been bitten twice by hand-carried numbers (the dissertation appendix's
`P → log(P)` claim, and the docs' "~12× fewer evaluations"). Provenance is the deliverable
here, not just the results.

**Scope boundary.** This plan ends at "the result exists, is committed, and has a figure."
Writing the results into `main.tex`/`supplement.tex` and drafting the response letter belong to
`papers/aquacal/reviewer_response_plan.md`. One handoff point is already marked in the
manuscript: `supplement.tex:543` carries `% HOOK (WP2 benchmark): insert measured iteration
counts / wall-clock for the 13-camera, 200-frame calibration once the benchmark run is
available` — E2 and E4 fill it.

## Provenance finding — correct before porting anything

**The paper's synthetic CSVs were produced by the tutorial notebook, not by
`tests/synthetic/experiments.py`.** Three independent confirmations:

1. `DissertationFigures/data/aquacal/synthetic_validation/README.md` states it outright:
   *"docs/tutorials/02_synthetic_validation.ipynb produced this data."*
2. Schema match. The committed `exp1_parameter_errors.csv` header is long-format
   (`camera,model,focal_length_error_pct,z_position_error_mm,xy_position_error_mm,gt_x_m,…,reprojection_rms_px`)
   — the notebook's `rows_exp1` dict exactly. `experiments.py::_save_parameter_errors_csv`
   writes a **wide** format (`focal_length_error_pct_refr`, `..._nonrefr`, `k1_error_refr`, …)
   that appears nowhere downstream.
3. `RIG_SIZE = "large"` (12 cameras, realistic noise, "~60 min total") with
   `TEST_DEPTHS = [1.10 … 2.50]` matches `exp2_depth_generalization.csv`, which starts at 1.1.

So `tests/synthetic/experiments.py` (1,532 lines) is a **superseded** earlier implementation
of the same three experiments whose outputs feed nothing. It must be reconciled, not merely
relocated. The notebook's logic is what carries forward.

**Carry this forward carefully:** the notebook applies a mean-shift correction that
`experiments.py` does not — it computes `_mz`, the mean Z error across *free* cameras
(excluding reference `cam0`), and subtracts it from every `z_position_error_mm` before export.
That is why `cam0`'s row reads `xy_position_error_mm = 0.0` against all-zero ground truth. It
is a gauge-freedom correction, it is real, and it currently exists in exactly one notebook cell
with no explanation anywhere. It must survive the port and be documented — a reviewer reading
the CSV would reasonably ask why one camera has zero error.

# Part 0 — Organizing principles

Seven scripts, four output kinds, and a library still changing underneath them. The governing
idea is **one number, one origin** — every quantity in the paper has exactly one place it comes
from, and everything else references it. Each principle below names the failure it prevents,
because each of these failures has already happened in this project at least once.

### P1. Measurement and presentation are separate programs

An `experiments/` script measures and writes a tidy CSV. It does not plot, and it does not
format LaTeX. Rendering belongs to `DissertationFigures`; table fragments come from a thin
renderer that reads the CSV and never recomputes.

*Prevents:* the actual failure that produced this plan. `experiments.py` fused run logic,
plotting, and CSV writing across 1,532 lines, so reusing the measurement meant importing the
plots — which was easier to reimplement than to untangle, and notebook 02 duly reimplemented
it. Two implementations, silently divergent schemas, and the paper quietly depending on the
one nobody would have guessed.

### P2. The library computes; the experiment orchestrates

An experiment script may loop, sweep, aggregate, and write. It may not compute a scientific
quantity the library could have recorded. If a number is needed and the library does not expose
it, the fix is a hook in `src/aquacal/` — the Phase 16 pattern — not a calculation in the
script.

*Prevents:* numbers a reader cannot reproduce by running AquaCal. BENCH-05 already states this
narrowly ("computing nothing the pipeline did not record"); it should hold suite-wide. It is
also what keeps E3 tier 3 a thin aggregator rather than a second implementation of the grouping
logic.

### P3. Shared code in `experiments/` is I/O only

`_io.py` owns output paths, the run-metadata sidecar, CSV writing, and CLI parsing. Anything
scientific — scenario construction, calibration invocation, error metrics — lives in
`src/aquacal/datasets/pipelines.py` (X1), where it is importable, documented, and tested.

*Prevents:* `experiments/_common.py` quietly becoming a second library with no tests and no
users outside this directory. That is what `experiment_helpers.py` became inside `tests/`.

### P4. The grid is data, not control flow

Each script declares its configurations as a literal at module top and a generic runner loops
it. Adding a rig size is editing a list, not editing a loop. If a run set is truncated —
top-N, sampling, a skipped configuration — the script logs what it dropped and the CSV carries
a column recording it.

*Prevents:* silent coverage gaps. A sweep that quietly skipped a configuration reads exactly
like a sweep that covered everything, and the reader has no way to tell.

### P5. Every unit is resumable and idempotent

E1 is ~60 minutes, E4 is roughly a day, E6 is the largest. Each configuration writes its own
output keyed by its config; the runner skips completed units unless `--force`. A crash eight
runs into a ten-run grid loses eight minutes, not eight hours.

*Prevents:* the deadline pressure that makes someone patch a partial CSV by hand — which is how
hand-carried numbers get into papers.

### P6. Determinism is asserted, not hoped

Seeds thread through (Rule 1). Beyond that: sort keys before writing, keep timestamps and
hostnames in the sidecar rather than the CSV, and never let wall-clock or dict ordering reach
committed content. Every script takes `--check`, which re-runs and diffs against the committed
result instead of overwriting it.

*Prevents:* E1's acceptance test degenerating into noise. "Reproduces every committed value" is
only a meaningful bar if a clean re-run is byte-stable; otherwise every diff needs adjudication
and the check gets skipped.

### P7. A smoke mode keeps the suite from rotting

Every script accepts `--smoke`: the same code path at trivial scale, seconds not hours, wired
into CI. It asserts nothing about the science — only that the script still imports, the API
still exists, and the output schema is unchanged.

*Prevents:* the suite silently breaking against its own library. The v1.7/v1.8 releases landed
outside the phase framework and left the committed tutorial outputs stale for five months
because nothing re-executed them (`nbsphinx_execute = "never"`). The experiments will face the
same drift across Phases 20–22 and every release after.

### Uniform CLI contract

Every script, no exceptions — a reviewer should be able to guess the invocation:

```
python -m experiments.eN_name [--seed 42] [--out results/] [--force] [--smoke] [--check]
```

## E3 — Derived quantities and code constants *(new script, broadened)*

**Backs:** supplement `tab:cpr`, the surrounding sparsity prose, the solver-configuration
paragraph, the Newton root-find claim, the pose-graph figure caption, and Phase 18's DOCS-01
correction.
**Dependencies:** `build_structural_column_groups` (landed). Tiers 2–3 are otherwise unblocked;
tier 1's tolerance row can only be asserted once **BENCH-06** lands in Phase 19.
**Runtime:** seconds to minutes.

**Why this is broader than one table.** Every number in the supplement that describes *how the
library behaves* — as opposed to what an experiment measured — currently exists only as text
someone typed. That is the exact failure mode that put `P → log(P)` into the dissertation
appendix and "~50 groups, ~12×" into the published docs. An audit of `supplement.tex` finds
three distinct kinds, and only the third has a generator today.

**Tier 1 — code constants, to be asserted (not measured).** Each of these is a literal in the
source that the supplement states as fact. A test that reads the source value and compares it
to a single declared table means a future default change breaks the build instead of silently
falsifying the paper. All four verified correct as of 2026-07-24:

| Supplement claim | Source | Status |
|---|---|---|
| `water_z` bounded to `[0.01, 2.0] m`; refined intrinsics to 50–200% | `_optim_common.py:519-520,534-536` | ✅ matches |
| Huber robust loss, `f_scale = 1.0 px` | `interface_estimation.py:343,677` | ✅ matches |
| Invalid/TIR configurations take a fixed 100 px penalty | `_optim_common.py:639`, `interface_estimation.py:654` | ✅ matches |
| Newton root-find tolerance `1e-9 m` | `refractive_geometry.py:330` | ✅ matches (`max_iterations = 10`) |

**⚠️ One that needs attention — the solver tolerances.** Supplement line 334 states termination
tolerances of `1e-8` "on the cost, parameters, and gradient." **AquaCal never sets them.**
Stage 3 (`interface_estimation.py:337-348`) and Stage 4 (`refinement.py:237-248`) both call
`least_squares` with `method`, `loss`, `f_scale`, `bounds`, `jac`, `verbose`, and `**ls_kwargs`
— and `ls_kwargs` only ever carries `callback` (`:317,333` and `:217,233`). So `ftol`, `xtol`,
`gtol`, and `max_nfev` are inherited SciPy defaults. The claim is *true today* — SciPy's
defaults are `1e-8` — but it is true by inheritance, not by choice, and it would silently
become false if SciPy changed a default or someone extended `ls_kwargs`.

This matters beyond hygiene: **R3.2 asks for the stopping criteria by name**, and BENCH-04
promises to record "solver configuration in force (tolerances, `max_nfev`, …)" — but
`OptimizeResult` does not report the tolerances back, so Phase 19 can only record values the
caller passed.

**Filed as BENCH-06** (added to `.planning/REQUIREMENTS.md` and roadmap Phase 19, 2026-07-24):
Stage 3 and Stage 4 pass `ftol`/`xtol`/`gtol` explicitly at their current effective values,
`max_nfev`'s effective value is recorded including the unset/auto case, and a regression test
asserts the change is bit-unchanged. Sequencing constraint 5 records that **BENCH-06 must
precede BENCH-04** — the record cannot be truthful before the values are set. So this is
Phase 19 work, not experiment work; E3 tier 1 only asserts the result.

**Tier 2 — measured behavior, currently unmeasured.** Supplement line 226 claims the Newton
iteration "converges to a tolerance of `1e-9 m` in two to four steps." That is an empirical
claim about the solver's behavior, not a constant, and nothing produces it. Measure the actual
iteration-count distribution over a representative ray set — spanning incidence angles out to
the rig's most oblique views, where the root-find works hardest — and report the observed range.
If it exceeds four steps anywhere, the supplement sentence needs adjusting.

**Tier 3 — derived structure (the original CPR scope).** For each configuration, build the
sparsity pattern, run the library's own grouping, and report `P`, group count, and `P / groups`.
Cover the six rows already in `tab:cpr` — (3 cam, 3 frames, tilt), (16, 200, tilt), (8, 100,
tilt+intrinsics), (12, 100, tilt+intrinsics), (13, 200, tilt+intrinsics), (16, 200,

## E5 — Refractive-index sensitivity (WP4 primary) *(new)*

**Answers:** R2 — and it answers by **refuting the premise**. The reviewer's concern is that
"miniscule changes in n could ruin the calibration." The expected result is that index error
maps almost entirely into a small apparent-depth scale bias rather than into reprojection
residuals, because n and depth are coupled: `Δdepth/depth ≈ Δn/n`.
**Dependencies:** `evaluate_calibration` as a standalone callable (Phase 16, landed) — the
experiment calibrates at one index and evaluates against ground truth generated at another.
Phase 20's `water_refractive_index()` helper is the *secondary* half of the R2 response and is
sequenced **after** this phase; it gates nothing here, needs no experiment, and its manuscript
sentence can be written independently of this result.
**Runtime:** the fine band is cheap; folds into E6's runs.

**Procedure.** Generate ground truth at index `n_true`, calibrate assuming `n_assumed`, and
evaluate held-out reconstruction. Sweep `n_assumed` in a fine band around 1.333 (±0.01 covers
the realistic temperature and salinity envelope) on the real rig's actual geometry, so oblique
ray angles across the full tank are represented rather than a near-normal best case.

**Report:** depth/scale bias and held-out RMSE vs Δn. The argument needs both — the point is
that the bias moves while the reprojection residual does not.

**Do not quote the back-of-envelope numbers in the paper.** The planning estimate (Δn ~ 1e-3
worst case → ~0.075% depth bias, against a 1.1% held-out noise floor) is a sanity target for
the sweep, not a result. Tucker's earlier dev-time analysis reached the same conclusion but is
**not committed anywhere in the repo** (searched 2026-07-22; the KB's `dev/tasks/` path is
stale and `dev/` no longer exists). Regenerate fresh.

**Emits:** `index_sensitivity.csv`. One supplement panel, one main-text sentence.

## E7 — Shared vs per-camera interface ablation (WP6) *(new)*

**Answers:** R4.2 (the CalibMar comparison) and R4.3 (convergence), which reduce to one
question — *is the shared interface a real methodological contribution or an engineering
convenience?* This is the single highest-value new experiment: it converts the paper's central
claim from an assertion into a measurement.
**Dependencies:** Phase 17 `shared_interface` (landed) + Phase 16 HOOK-03 conditioning
diagnostics (landed). No library dependencies remain; it leads the experiment phase behind
E2's 20-minute re-run, and BENCH-01 gives it solver diagnostics for free.
**Runtime:** four configurations on identical synthetic data; hours, not days.

**Configurations** — identical scenario, noise, target, and seed across all four:

| | intrinsics fixed | `refine_intrinsics=True` |
|---|---|---|
| `shared_interface=True` | baseline | baseline + refine |
| `shared_interface=False` | **primary result** | secondary result |

**The primary result is the fixed-intrinsics row.** It demonstrates the height/distance
degeneracy (`main.tex:201`, citing Treibitz): each camera's world-Z trades against its own
interface distance, since only the sum `C_z + d` — the absolute surface height — is physically
meaningful and must be common to all cameras. With a private `d_i`, each camera slides along
its own valley and the recovered heights scatter. This needs no intrinsic refinement and is
the airtight demonstration.

The refine-ON row is a **secondary** add-on showing the focal-length/standoff degeneracy
(`main.tex:149,210`, citing Sedlazeck), which only appears when focal length is free.

**Metrics — this is where the experiment succeeds or fails.** Report per-camera surface-height
spread, camera-height drift vs ground truth, focal/standoff drift and correlation, and the
conditioning report (singular-value spectrum / condition number, and the camera-height ↔
interface-distance correlation block). **Do not report reprojection RMSE as the headline** — a
degeneracy is a flat cost valley, so RMSE stays low in *both* arms and would make per-camera
look acceptable. Phase 17 already ships a `water_z` spread report (console mm + internals JSON)
that is a ready-made primary metric.

Use the optimization trace (Phase 16, 16-04) to show drift along the valley. A cost trace plus
a parameter trace is far more convincing than a final number, and it doubles as the direct
evidence R4.3 asks for about convergence behavior.

**Two framing disciplines, carried from the response plan:**
1. **Label the failure correctly.** A naive per-camera mode is N free `water_z_i` alongside
   the existing N free camera centers, which reintroduces the `C_z_i ↔ water_z_i` redundancy.
   That is the **height/distance** degeneracy, not focal/standoff. A code-reading reviewer will
   notice a mislabel.
2. **Do not present the refine-ON result as "what CalibMar produces."** CalibMar solves each
   camera in its own frame, so it has no `C_z`↔distance redundancy; that redundancy is specific
   to putting per-camera distances into a *shared world frame* at meter-scale standoff.
   CalibMar works correctly in its intended regime. Frame refine-ON as *our own* rationale for
   importing intrinsics from air. Presenting it otherwise is a strawman a reviewer could call.

**Emits:** `interface_ablation.csv` (per camera × configuration: recovered `water_z`, height
drift, focal drift, standoff), `interface_ablation_conditioning.json`, and per-run trace CSVs.

# Part 4 — Reproducibility contract

Five rules, all cheap now and expensive to retrofit once numbers are in the manuscript.

1. **Every script takes `--seed` and threads it through.** Phase 16's HOOK-06 already does
   this pipeline-side; the experiment layer must not break it.
2. **Every script writes a JSON sidecar next to its CSV** — seed, AquaCal version, git SHA,
   CPU/RAM/OS, Python/NumPy/SciPy versions, wall-clock, and the full config used. Because
   Phase 19 lands first, this is `benchmark.json` re-used rather than anything hand-rolled;
   experiment scripts should copy or reference it, never recompute it. **Carve-out:** E3's
   tiers 1–2 never run a calibration, so there is no `benchmark.json` to reuse — they still
   need a minimal sidecar carrying library version, git SHA, and Python/SciPy versions, which
   is exactly the provenance that makes a constants table meaningful a year later.
3. **`experiments/README.md` maps one command to each paper artifact**, with expected runtime.
   A reviewer following the SoftwareX reproducibility path should never have to guess which
   script made which number.
4. **Tag a release at submission** (v1.9.0 or later, per Phase 22). The response letter then
   cites `experiments/e4_benchmark_grid.py` at a tag rather than at `main`. This also settles
   the manuscript's C1 cell, currently stale at v1.6.0 against v1.8.0 shipped.
5. **Commit the CSVs.** They are small, they are the figure inputs, and they are the only thing
   standing between a number in the PDF and a claim nobody can check. Raw calibration artifacts
   stay out.

## Three risks worth naming

1. **E2's numbers will move.** Two feature releases have landed since the committed real-rig
   run, which predates outlier-frame rejection and intrinsics seeding entirely. §3's real-rig
   paragraph is the most likely place the revision springs a leak, and fixing it is a prose

3. **Word budget.** These experiments add a table and roughly six sentences to the main text.
   The supplement is the release valve, but the trimming pass should happen *after* content
   settles, not during. The cut of last resort is condensing the two-scale (local/absolute)
