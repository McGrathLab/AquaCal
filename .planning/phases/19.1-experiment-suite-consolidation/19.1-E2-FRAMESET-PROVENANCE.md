**Established:** 2026-07-27, during Phase 19.1 wave 3 review.
**Status:** resolved. Supersedes two conclusions in `19.1-E2-DELTA-TABLE.md`.

`C:\Users\tucke\Desktop\Aqua\AquaCal\release_calibration\diagnostics.json` is the **exact
source of every §3 real-rig number**. All nine reconcile against it, most to 4+ significant
figures:

## What this corrects

`19.1-E2-DELTA-TABLE.md` rows 2, 8, and 9 concluded that the §3 prose was a *rounded
approximation* of the committed `DissertationFigures` CSV, and called this a "pre-existing
prose-vs-committed-CSV discrepancy". **That conclusion is wrong.** The §3 prose is exact
against the release run. The discrepancy is not prose-vs-data — it is **run-vs-run**.

There are three distinct datasets in play, not two:

| Run | Frames | Validation frames | Comparisons | Produces |
|---|---|---|---|---|
| **Release calibration** (`Desktop\Aqua\AquaCal\release_calibration`) | ~260 usable | 52 | 7,762 | **the §3 paper numbers** |
| **Zenodo `real-rig` archive** (192 MB, pre-extracted JPEGs) | 60 usable | 12 | 1,817 | the committed `DissertationFigures` CSV |
| **Phase 19.1 fresh run** (wave 3) | 60 usable | 12 | 1,817 | reproduces the Zenodo run bit-identically |

## Root cause

Both datasets come from the **same source videos**
(`Desktop\Aqua\AquaCal\raw_videos\{intrinsics,extrinsics}\*.avi`, 13 + 13 files, all present
on disk). The release config uses `detection.frame_step: 30` with
`optimization.max_calibration_frames: 200` and `validation.holdout_fraction: 0.2`, yielding
~260 usable frames → 52 validation. The Zenodo archive is a **~4.3× frame-subsampled
extraction** of that same capture, presumably to keep the published archive at 192 MB.

The ratio check confirms it: 7762 / 1817 = 4.27, and 52 / 12 = 4.33.

## Consequence for the delta table

The wave-3 delta table's central observation still stands and is *strengthened*: every primary
camera's per-camera RMS and `h_c` was bit-identical between the fresh run and the committed
Zenodo-derived CSV, so **the calibration itself did not drift**. But the aggregate rows could
not answer the question the gate actually asks — "did v1.7/v1.8 move the paper's numbers?" —
because they compared a 12-frame validation set against a 52-frame one.

`reject_outlier_frames` (v1.7) did not fire on the fresh run (median 0.96 px vs a 5.00 px
threshold, zero frames dropped), so that mechanism is ruled out by evidence regardless.

## Decision (user, 2026-07-27)

**Re-run E2 against the local raw videos using the release config**, giving a true
like-for-like comparison against §3. Regenerating and republishing the Zenodo archive is NOT
pulled into this phase.

Implementation note: `experiments/e2_real_rig.py` currently hardcodes
`load_example("real-rig")` and uses the archive's own `config.yaml`. It needs a `--config`
override so **both** paths remain available — the default keeps the published-archive
reproducibility path intact for a reader with no local videos.

Settings to match exactly: `refine_intrinsics: true`, `refine_auxiliary_intrinsics: true`,
`frame_step: 30`, `max_calibration_frames: 200`, `holdout_fraction: 0.2`, `n_water: 1.333`,
`initial_water_z: 1.0` for all 13 cameras, `robust_loss: huber`, `loss_scale: 1.0`.

## Carried forward to Phase 21 — REQUIRED BEFORE PUBLICATION

**The published Zenodo archive must be regenerated to the full frameset before the paper
ships.** If §3 reports numbers from a ~260-frame run while the published archive contains 60
frames, a reader following the reproducibility path gets materially different numbers — which
is precisely the "one number, one origin" failure this phase exists to prevent, and the same
class of error as the two hand-carried numbers already in publications (see `19.1-CONTEXT.md`
`<specifics>`).

This is Phase 21 / DATA-01/02/03, which already carries a "do not action standalone"
sequencing constraint. This document is the record that the regeneration is now a **hard
prerequisite**, not a nice-to-have — the archive and the manuscript must describe the same
run.

Note also that after this re-run, `experiments/results/`'s committed CSVs will come from the
local-video run, which a reader **cannot currently reproduce** from the published archive.
That gap closes only when DATA-01/02/03 lands.
