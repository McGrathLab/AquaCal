**When to use:** Any time logic is promoted out of `tests/` into `src/`.

### Pattern 2: Direct-call provenance (new to this phase)

**What:** An experiment that bypasses `run_calibration_from_config` still produces a
schema-compliant `benchmark.json` by calling `assemble_benchmark_record` itself, filling
every block it legitimately can and using D-15's null-with-reason discipline for the rest.
**When to use:** E1, E7 (any experiment calling `optimize_interface`/`joint_refinement` directly).
**Example (concrete construction, no library change needed):**
```python
# experiments/e1_refractive_comparison.py — sketch, not literal final code
from aquacal.calibration._observability import SolverDiagnostics
from aquacal.io import assemble_benchmark_record, capture_environment, write_benchmark_json

diag_stage3 = SolverDiagnostics()
diag_stage3_intrinsic_pass = SolverDiagnostics()

result, detections = calibrate_synthetic(
    scenario, n_water=1.333, refine_intrinsics=True, seed=args.seed,
    gauge_correct_z=True,
    diagnostics_out={
        "stage3_interface_optimization": diag_stage3,
        "stage3_intrinsic_pass": diag_stage3_intrinsic_pass,
    },
)

record = assemble_benchmark_record(
    problem_shape={
        "n_cameras": len(scenario.intrinsics),
        "n_frames_calibration": len(scenario.board_poses),
        "n_frames_holdout": 0,  # E1 evaluates on freshly generated test grids, not a holdout split
    },
    timings={
        "stage3_interface_optimization": t_stage3_seconds,
        "stage3_intrinsic_pass": t_intrinsic_pass_seconds,
    },
    diagnostics={
        "stage3_interface_optimization": diag_stage3,
        "stage3_intrinsic_pass": diag_stage3_intrinsic_pass,
    },
    solver_config={
        "robust_loss": "huber", "loss_scale": 1.0,
        "refine_intrinsics": True, "n_water": 1.333, "n_air": 1.0,
        "shared_interface": True,
    },
    accuracy={"reprojection_rms_px": result.diagnostics.reprojection_error_rms},
    environment=capture_environment(),
    memory_readings=None,  # D-11: omit the "memory" key entirely
)
write_benchmark_json(record, out_dir / "e1_benchmark_refractive.json")
```
Note: E1 calibrates **twice** (refractive and non-refractive) — this produces **two**
`benchmark.json`-shaped records, one per model, so the plan should name them distinctly
(e.g. `e1_benchmark_refractive.json` / `e1_benchmark_nonrefractive.json`), not one shared file.

### Anti-Patterns to Avoid

- **Re-deriving `gt_x_m`/`est_x_m` in `experiments/`:** D-06(3) is explicit that these belong in
  the widened `compute_per_camera_errors`, not computed at the experiment call site the way the
  notebook currently does it inline (`rows_exp1.append({... "gt_x_m": C_gt[0], ...})` at
  `e3jl81minof`). Porting that inline construction unchanged into `experiments/` would recreate
  exactly the "library computes, but the script also computes" duplication P2 forbids.
- **Hardcoding `1e-8` as a magic number in more than one place:** Stage 3/3b's `ftol`/`xtol`/`gtol`
  are inline literals at `interface_estimation.py:359-361` and (confirmed below) an identical
  triple at `refinement.py`'s call site — there is no public module constant to import. If E1/E7's
  `solver_config` block needs these values, either read them back off the populated
  `SolverDiagnostics.ftol/xtol/gtol` fields (`capture_solver_diagnostics` already stores them —
  **this is the correct approach, no hardcoding needed**) rather than retyping `1e-8` in the
  experiment script.
- **Recomputing `_build_interface_spread_report`'s five-line stats block inline:** see "Gap:
  `_build_interface_spread_report` is private" below — promote it instead of duplicating it.

## Common Pitfalls

### Pitfall 1: E1's two calibrations are not directly comparable without shared plumbing

**What goes wrong:** A naive port runs `calibrate_synthetic` twice (refractive, non-refractive)
independently and assembles two unrelated `benchmark.json`-shaped dicts, then the plan discovers
late that `TEST_DEPTHS` sweep evaluation (exp2/exp3) needs `test_detections` generated once per
depth and *reused* for both models' evaluation (the notebook does this at `cell-exp2-depth-sweep`:
`exp2_test_poses`/`exp2_test_detections` lists are built once, then `evaluate_reconstruction` is
called against each model using the *same* stored test data).
**Why it happens:** It's tempting to structure a script as two independent per-model loops.
**How to avoid:** Follow the notebook's structure exactly: generate the scenario once, calibrate
both models, generate each test depth's detections once (not once per model), evaluate both
models against the same stored detections.
**Warning signs:** If your ported CSV values differ in the 2nd or 3rd significant digit from the
committed baseline, check whether the two models are evaluated against independently-regenerated
(same-seed but separately-called) detections rather than a single shared set — `seed=42 + int(depth*100)`
is deterministic, so re-calling `generate_synthetic_detections` with the same args does reproduce
bit-identical detections, but confirm this before assuming it — the notebook's structure exists
this way for a reason (single source of truth per depth) even if it may be numerically
equivalent to calling it twice.

### Pitfall 2: `cam0`'s Z error is the *raw* per-camera error before mean-shift correction, not literally zero from the library

**What goes wrong:** A reader (or an executor writing `compute_per_camera_errors`) assumes
`xy_position_error_mm = 0.0` for the reference camera means `pipelines.py` should special-case
`cam0`.
**Why it happens:** The committed CSV's `cam0` row genuinely reads `0.0` for both
`xy_position_error_mm` (always exactly 0 — the reference camera is pinned at the world origin, an
exact geometric fact, not a correction) and `z_position_error_mm` (only 0 *after* the mean-shift
correction — before correction it is nonzero, e.g. `-0.824` for the refractive model, verified
directly against `experiment_helpers.py`'s raw `z_position_error_mm` computation, which uses
`C_cal[2] - C_gt[2]` with no reference-camera special case).
**How to avoid:** `gauge_correct_z=True` in `pipelines.py` must subtract the mean of the *free*
cameras' raw Z error from **every** camera's raw Z error, `cam0` included — it is not a
special-cased zero, it is the generic subtraction landing on (near-)zero for `cam0` only because
`cam0`'s own raw error happens to be excluded from the mean being subtracted. See the exact
quoted cell below.
**Warning signs:** If `cam0`'s corrected Z error is not extremely close to (but not exactly) the
committed CSV value (`-0.8238055920285546` mm for refractive, `12.810646003200702` for
non-refractive), the correction was implemented as "hardcode `cam0` to 0" instead of "subtract
the free-camera mean from all cameras."

### Pitfall 3: `calibrate_synthetic(refine_intrinsics=False)` is not the E7 "fixed intrinsics" arm

**What goes wrong:** A naive E7 implementation reuses `calibrate_synthetic`'s existing
`refine_intrinsics` boolean and assumes `refine_intrinsics=False` gives "fixed intrinsics
estimated from air" for the ablation's fixed-intrinsics arm.
**Why it happens:** `experiment_helpers.py:135-137` shows exactly this branch: when
`refine_intrinsics=False`, `opt_intrinsics = scenario.intrinsics` — **ground-truth** intrinsics,
not intrinsics independently estimated from an in-air calibration (Stage 1). D-18's framing
discipline requires E7's fixed-intrinsics arm to demonstrate "importing intrinsics from air" as
*our own* rationale, which is a materially different (weaker, more realistic) starting point than
handing the optimizer the exact ground truth.
**How to avoid:** E7 must not call the existing `calibrate_synthetic(refine_intrinsics=False)`
path unmodified for its fixed-intrinsics arms. Either (a) call `optimize_interface`/
`joint_refinement` directly with intrinsics fixed at a value with realistic Stage-1-like noise
(the synthetic generator can inject intrinsic noise, or the scenario's `intrinsics` dict can be
perturbed by a small deterministic amount before being passed in as "fixed"), or (b) explicitly
document in `interface_ablation.csv`/README that "fixed" here means ground-truth-fixed and this
is a best-case bound, not the CalibMar-import scenario the paper's R4 response describes. Flag
this explicitly to the user during planning — it is exactly the kind of "what does 'fixed
intrinsics' mean" ambiguity D-18 warns a code-reading reviewer will catch.
**Warning signs:** If E7's fixed-intrinsics arm shows near-zero focal/standoff drift alongside the
expected height/distance drift, that is consistent with GT-intrinsics-as-fixed (no focal noise to
propagate) and should prompt re-checking whether this matches the paper's intended comparison.

### Pitfall 4: `evaluate_reconstruction`'s `test_detections` argument name mismatch when porting

**What goes wrong:** `experiment_helpers.py::evaluate_reconstruction` takes
`(calibration, board, test_detections)` in that order — a straightforward positional port from
the notebook's `evaluate_reconstruction(result_refr, board_exp2, test_detections)` call works,
but any refactor that reorders keyword args risks a silent semantic swap since `calibration` and
`board` are both project-specific dataclasses with no runtime type-check preventing accidental
reordering at the call site.
**Why it happens:** Simple porting error under time pressure.
**How to avoid:** Keep the promoted `pipelines.evaluate_reconstruction` signature byte-identical
to the current one; add a bit-exact regression test (`assert numerically identical output for
identical input`) per the phase's own zero-numerical-change discipline (established in Phases
16/17/19).
**Warning signs:** N/A — this is a process pitfall, not a numeric one; the fix is a signature
freeze plus test, not a runtime check.

### Pitfall 5: `--check`'s per-CSV key columns are not uniform

**What goes wrong:** A single generic "diff every row by row-index" comparator silently produces
false failures if rows are written in a different order across a clean re-run (CSV writing order
is not guaranteed to be stable unless explicitly sorted).
**Why it happens:** `exp1_parameter_errors.csv` keys on `(camera, model)`; `exp2_depth_generalization.csv`
and `exp3_xy_vs_z_anisotropy.csv` key on `(test_depth_m, model)` (verified against the committed
headers). A row-index-based diff assumes a fixed iteration order the writer must also guarantee
(sort keys before writing — P6 already requires this) — but the *comparator* must still declare
which columns are the join key, not assume "row N of file A corresponds to row N of file B" is
automatically true after any refactor.
**How to avoid:** `_io.py`'s comparator takes an explicit `key_columns: list[str]` parameter
per CSV (declared as a constant in each experiment script, e.g.
`EXP1_KEY_COLUMNS = ["camera", "model"]`), sorts both the fresh and committed DataFrames by
those columns before comparing, and only then applies the numeric tolerance.
**Warning signs:** A `--check` failure that disappears when you `sort_values()` the two
DataFrames before comparing manually means the writer's sort-before-write discipline slipped, not
that the science changed.

### The gauge-freedom correction, quoted verbatim

Source: `docs/tutorials/02_synthetic_validation.ipynb`, cell `e3jl81minof`:

```python
# --- Exp1: per-camera parameter errors ---
# Compute mean Z shift of free cameras for mean-shift correction
_free = [c for c in camera_names if c != camera_names[0]]
_mz = {
    "refractive": np.mean([errors_refr[c]["z_position_error_mm"] for c in _free]),
    "non_refractive": np.mean([errors_nonrefr[c]["z_position_error_mm"] for c in _free]),
}

rows_exp1 = []
for cam in camera_names:
    for label, errors, result in [
        ("refractive", errors_refr, result_refr),
        ("non_refractive", errors_nonrefr, result_nonrefr),
    ]:
        C_gt = scenario.extrinsics[cam].C
        C_est = result.cameras[cam].extrinsics.C
        rows_exp1.append({
            "camera": cam,
            "model": label,
            "focal_length_error_pct": errors[cam]["focal_length_error_pct"],
            "z_position_error_mm": errors[cam]["z_position_error_mm"] - _mz[label],
            "xy_position_error_mm": errors[cam]["xy_position_error_mm"],
            "gt_x_m": C_gt[0], "gt_y_m": C_gt[1], "gt_z_m": C_gt[2],
            "est_x_m": C_est[0], "est_y_m": C_est[1], "est_z_m": C_est[2],
            "reprojection_rms_px": result.diagnostics.reprojection_error_rms,
        })
```

**What it computes, precisely** (answering research question A.2):
- `camera_names` is `sorted(scenario.intrinsics.keys(), key=lambda s: int(s.replace("cam", "")))`
  — `camera_names[0]` is always `cam0`, the reference camera.
- `_free` = all cameras except `cam0` (the free/non-reference cameras).
- `_mz[label]` = the **mean of the raw (uncorrected) `z_position_error_mm`** across only the free
  cameras, computed separately per model (`refractive`/`non_refractive`).
- Every camera's (including `cam0`'s) `z_position_error_mm` in the exported row is
  `errors[cam]["z_position_error_mm"] - _mz[label]` — i.e. **every camera's raw Z error minus the
  free-camera mean**, in millimeters (the raw error from `compute_per_camera_errors` is already
  in mm: `(C_cal[2] - C_gt[2]) * 1000`).
- **Why `cam0` lands near (not exactly) zero:** `cam0` is pinned at the world-frame origin during
  optimization by construction (it is the reference camera — its extrinsics are never part of the
  optimized parameter vector), so its *raw* Z error is a very small residual near zero already
  (verified: `-0.8238` mm for refractive), not exactly zero. After subtracting `_mz` (the mean of
  the *other* cameras' errors, which is a global datum shift the reference camera does not share
  in the same way), `cam0`'s corrected value in the committed CSV is `-0.8238055920285546` — this
  is **not exactly 0.0** in the committed data (only `xy_position_error_mm` is exactly `0.0` for
  `cam0`, an unrelated geometric fact — `cam0`'s XY position literally is the world origin, `[0,0]`
  by definition, with zero optimizable freedom). CONTEXT.md D-07's claim "cam0's row reads
  `xy_position_error_mm = 0.0`" is confirmed exactly; do not conflate this with `z_position_error_mm`,
  which is a small nonzero number after correction, driven by the residual gap between `cam0`'s own
  (near-zero-by-construction) error and the free-camera mean.
- **What it does not do:** it does not zero out `cam0` specially. It is a uniform subtraction
  applied to every camera's row, and `cam0`'s XY zero is unrelated (geometric, not statistical).

**Docstring text to carry into `pipelines.py`'s `gauge_correct_z` keyword** (per D-07's
requirement that the reason must appear in both the docstring and `experiments/README.md`):

> A per-camera Z position error is only meaningful up to the world frame's Z datum, which the
> reference camera pins at zero by construction. Without this correction, a global datum offset
> the optimizer applied to the entire rig (an artifact of choosing where "Z=0" is, not a real
> geometric error) is charged entirely to every non-reference camera while the reference camera's
> own near-zero raw error is left uncorrected, making cross-camera Z-error comparisons
> attribution-confounded. `gauge_correct_z=True` subtracts the mean raw Z error across the
> non-reference (free) cameras from every camera's raw Z error, including the reference camera's
> own — revealing the systematic Z shift a model's biased geometry would apply to the entire rig,
> rather than an artifact of the reference camera's fixed position. This is why the reference
### camera's `xy_position_error_mm` is exactly `0.0` (it is pinned at the origin, a separate,
> unrelated geometric fact) while its `z_position_error_mm` after correction is a small nonzero
> residual, not zero.

   defensible home). This is a small, safe, additive change (BENCH-adjacent, zero behavior
   change to the pipeline itself) that the plan should schedule as part of X1 or its own tiny
   task, not skip. **If the planner decides not to promote it**, the fallback is E7 computing the
   same five numbers inline with a one-line comment citing `pipeline.py:731-763` as the reference
   implementation — acceptable but strictly worse (duplicated, untested-in-common logic).
5. **Per-camera seeding for identical data across all four arms:** `optimize_interface`'s
   `initial_water_zs: dict[str, float]` and `joint_refinement`'s implicit seeding from
   `stage3_result`'s distances are the *initial guess*, not the ground-truth generation — the
   **detections themselves** must be generated exactly once (single `scenario`, single
   `generate_synthetic_detections(..., seed=<fixed>)` call) and reused unchanged across all four
   arms. Only `shared_interface` and (at the `joint_refinement` step) `refine_intrinsics` may vary
   between arms; `initial_water_zs` should also be held identical across arms (the same seed dict,
   e.g. `{cam: 0.15 for cam in ...}` or `scenario.water_zs` scaled by a fixed offset) so that
   convergence differences are attributable to the ablation variable, not to different starting
   points. **Do not reseed `initial_water_zs` per-arm from a random draw** — this would confound
   the ablation's conclusion.
