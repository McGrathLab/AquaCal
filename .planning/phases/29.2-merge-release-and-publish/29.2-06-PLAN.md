<objective>
Take the package-index door: put the released version in front of the author with the artifact's
member list and the live index state, let the author approve the gated job, then confirm from the
public index that the version is really there.

Purpose: this project's stated core value is that a researcher can install it by name. The public
index currently offers a version two minors behind the code the paper cites, because the two
intervening releases never got past this same gate. This phase closes that, and it does so before
the results record is published, so the record's claim about the version it was produced by is true
at the moment the permanent identifier is minted.

Output: one evidence file carrying the go/no-go, the ruling, and the confirmation.
</objective>

  <context>
The publish workflow has run its test, build and test-index jobs successfully and is waiting on the
production-index environment's required-reviewer rule. Approving releases the artifact the build job
already produced from the tag; nothing is rebuilt at approval time.

**Why this is in scope rather than a side effect.** The project's core value is that a researcher can
install it by name. The public index currently offers a version two minors behind the code the paper
cites, because the two intervening releases never got past this same gate — one failed its test job
before reaching build, and the other reached this gate and waited. A version that exists only as a
tag does not close that.

**Why now rather than after the record is published.** The results record's prose names the version
it was produced by. Approving first means that when the permanent identifier is minted, the version
that prose names is genuinely installable. Both acts are manual presses, so the ordering costs
nothing and buys a stronger claim.

**What cannot be undone.** An index version can never be replaced. Withdrawal is the only remedy and
it is itself public. That single property is why every mitigation upstream exists: the member list
was asserted against the rehearsal's build and again against the workflow's own artifact, the
approval rule is a human gate rather than an automated push, and the credential model uses short-lived
identity tokens rather than a long-lived index secret stored in the repository.

**What is measured and satisfying.** The target version is free on both indices, so no duplicate
collision is possible. The artifact's member list is the source tree plus five metadata files and
nothing else, matched element for element against the rehearsal. The test index already accepted the
same artifact.
