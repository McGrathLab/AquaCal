--------------------------------------------------------------------------------
THREE THINGS THIS RUN MEASURED THAT THE PLAN AND THE RESEARCH DID NOT
--------------------------------------------------------------------------------

These are recorded because each one would have let a defect through.

1. `semantic-release --version` DOES NOT DETECT FINDING 1.
   The plan's task-2 step 4 says: "assert `semantic-release --version` exits 0.
   That single assertion is what Finding 1 costs to detect." Measured, that is
   false. With the broken GitPython 3.1.60 installed, `semantic-release
   --version` prints "semantic-release, version 10.6.1" and exits 0, because
   `--version` never loads the config and therefore never reaches
   semantic_release/cli/config.py:745. The break surfaces only on a subcommand
   that loads config. A CI smoke test built on `--version` would have passed and
   the release would still have died.
   THE ASSERTION THAT DOES DETECT IT is `semantic-release version --print` on a
   release-group branch -- exit code 1, "::ERROR:: type object 'Actor' has no
   attribute 'name_email_regex'". That is measured below, both ways.

2. AND IT DOES NOT DETECT IT ON A NON-RELEASE BRANCH EITHER.
   With the same broken GitPython, `semantic-release version --print` run on
   `results/rerun-freeze-02` exits 0 with "branch ... isn't in any release
   groups; no release will be made" -- PSR short-circuits on the branch check
   BEFORE constructing the runtime context that reads the missing attribute. So
   the pre-merge check has to happen on a branch named `main`, which is exactly
   what the /tmp clone is for. Two independent reasons the clone is not optional.

3. THE MERGE'S PR NUMBER IS #3, NOT #1.
   PATTERNS records "no PR has ever been opened on this repo (`gh pr list
   --state open` -> [])". That query was scoped to OPEN pull requests. `gh pr
   list --state all` returns #1 and #2, both closed. The next PR is #3. This is
   cosmetic for the bump -- PSR's `ignore_merge_commits` default means the merge
   commit's own message is not parsed at all -- but plan 29.2-04 opens the real
   PR and should not expect #1.

--------------------------------------------------------------------------------
ONE DEVIATION, RECORDED RATHER THAN HIDDEN
--------------------------------------------------------------------------------

The FIRST full `semantic-release version --no-vcs-release` invocation ABORTED at
build_command. It is transcribed below in full, together with the state it left
behind, because pretending it did not happen would waste the most useful thing it
produced: an exact, accidental reproduction of RESEARCH Q6f's half-way abort.

  Q6f predicted: PSR writes the three version files, runs build_command, and
  aborts BEFORE the commit, the tag and the push.
  Measured after the abort: HEAD still the merge commit; ` M CHANGELOG.md
  M CITATION.cff  M pyproject.toml`; `git tag --list v2.1.0` empty; fake-remote
  ref count 0. The prediction holds to the letter. The abort is benign.

  Cause, read from the installed source rather than guessed: PSR runs
  build_command through `bash -c` with a curated environment that forwards the
  CALLER's PATH verbatim (semantic_release/cli/commands/version.py:278,
  `"PATH": os.getenv("PATH", "")`). This shell's `python` is the anaconda base
  interpreter, which has no `build` module; the pinned venv's bin directory was
  not on PATH.

  THIS IS A DEFECT IN THE REHEARSAL HARNESS, NOT IN THE REPOSITORY AND NOT IN
  release.yml. On the runner, actions/setup-python puts its interpreter first on
  PATH and `pip install ... build` installs into that same interpreter, so
  `python -m build` resolves correctly there. No workflow change is warranted and
  none was made.

  Fix applied: the clone's tree was reset to the merge commit with a targeted
  `git checkout -- CHANGELOG.md CITATION.cff pyproject.toml` (three named files,
  inside the /tmp clone -- no blanket reset, no `git clean`, and nothing in the
  working repository), the earlier manual build output was removed so that dist/
  could only contain build_command's own product, and the release was re-run with
  the venv's bin first on PATH. It then completed.
