## The red cells — reported, not explained away

All four `test` cells failed **identically**: `5 failed, 2319 passed, 23 skipped, 71 deselected`.
Every failure is in `tests/unit/test_run_manifest.py::TestBuildRunManifest`, and every one traces to
three manifest fields being `None` on the runner.

**This is new information and it is reported as such.** 29.2-03 measured the same selection on this
tree at **0 failed, 2326 passed, 21 skipped**. Both tallies are printed in §11; neither was adjusted
toward the other.

Diagnosed from the run logs, not surmised:

- `git_describe` is `None` because the checkout is `fetch-depth: 1`, `fetch-tags: false` — the log
  shows `git fetch --no-tags ... --depth=1`. `experiments/_run_manifest.py` resolves the field with
  `git describe --match 'v[0-9]*'`, which has nothing to anchor to in a one-commit, zero-tag clone.
- `cpu_count_logical` and `ram_total_bytes` are `None` because `psutil` sits in the **`bench`** extra
  while `test.yml` installs only `.[dev]`. The string `psutil` appears zero times in the install log.
  `benchmark.py:158` documents this exact outcome.

The production code therefore behaves as its own docstrings specify; what fails is five tests
asserting those fields are always populated, in an environment that cannot populate them. **That
these would go green if the checkout fetched tags and the test extra carried psutil is labelled in
§11 as an inference, not a measurement.** It has not been executed.

**No repair was attempted**, because no author ruling exists for this one and every candidate fix is
a decision — workflow checkout config, dependency extras, or the tests' own semantics — rather than
an obvious correction. Nothing was skipped, xfailed, deselected, re-run or cancelled.
