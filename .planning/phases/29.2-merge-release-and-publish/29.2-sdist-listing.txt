TWO MEASUREMENTS MAKE THAT RULING STRONGER THAN THE DECISION CLAIMED, and both
are recorded here because neither was known when the plan was written:

  1. THE SDIST IS NOT BYTE-REPRODUCIBLE. Two builds from the IDENTICAL tree with
     the IDENTICAL toolchain, taken about twenty seconds apart, produced
     200,871 B and 200,891 B -- a 20-byte difference -- while their member lists
     diffed clean. setuptools stamps build times into the tar headers and gzip
     compresses those differing bytes differently. A size assertion tight enough
     to catch a leak would therefore fail on consecutive builds of the same
     source.

  2. THE 66-BYTE GAP FROM RESEARCH'S FIGURE IS THE SAME PHENOMENON, PLUS A
     TOOLCHAIN DRIFT. 200,871 here against 200,937 there is 0.03%. The member
     lists and the 66 src/ entries are identical between the two runs, so the
     difference lives in generated metadata and compression framing, not in
     content; and build isolation resolves its own setuptools at build time, so
     the two runs did not necessarily use the same one (RESEARCH recorded
     80.10.2; the latest today is 84.0.0). BOTH NUMBERS ARE PRINTED. The
     rehearsal's own figure was not quietly replaced with the more familiar one.

--------------------------------------------------------------------------------
WHY THE SDIST IS CLEAN -- recorded at the check, so a future contributor knows
what they would be turning on
--------------------------------------------------------------------------------

There is NO `MANIFEST.in` in this repository (`ls` -> No such file or directory),
and `[build-system] requires = ["setuptools>=77.0.0", "wheel"]` names NO
file-finder plugin -- no setuptools-scm, no setuptools-git, nothing else
providing a `setuptools.file_finders` entry point.

That absence is the whole reason the sdist is clean. It is not luck and it is not
a .gitignore effect. setuptools' DEFAULT sdist walk is deliberately narrow: the
packages found by `[tool.setuptools.packages.find] where = ["src"]`, whatever
`[tool.setuptools.package-data]` matches, pyproject.toml/setup.cfg, the readme
and license named in [project], and the generated PKG-INFO/*.egg-info. It does
not walk arbitrary top-level directories, so experiments/ and .planning/ cannot
reach it.

A file-finder plugin REPLACES that narrow walk with "every file tracked by git".
This repository tracks 1,706 files, including the 227 committed run artifacts and
the entire .planning/ tree. So:

  DO NOT add setuptools-scm (or any other file-finder plugin) for version
  management without also adding an explicit MANIFEST.in prune or an sdist
  exclude. Doing the first without the second would silently publish the run
  artifacts and the planning tree to PyPI, permanently, at the next release.

An explicit MANIFEST.in / sdist exclude that would make the file set enforced
rather than merely observed is a GOOD idea and is deliberately OUT OF SCOPE here
(CONTEXT § Deferred Ideas). D-29.2-17's caution is honoured by verifying, once,
against the property itself.

--------------------------------------------------------------------------------
A LOCALE TRAP WORTH THE THREE LINES IT COSTS TO CLOSE
--------------------------------------------------------------------------------

`sort` is collation-dependent. This machine's default (LANG=en_US.UTF-8) orders
the six names LICENSE, PKG-INFO, pyproject.toml, README.md, setup.cfg, src --
case-insensitively, so pyproject.toml precedes README.md. Under LC_ALL=C the
order is LICENSE, PKG-INFO, README.md, pyproject.toml, setup.cfg, src, because C
collation compares bytes and 'R' (0x52) precedes 'p' (0x70).

The expected string is the C-collation one. Every comparison in this file
therefore pins LC_ALL=C. An unpinned sort passes on a POSIX-locale machine and
FAILS on an en_US.UTF-8 one against an identical, healthy artifact -- a false
alarm on whichever machine happens to run it next.

================================================================================
SCOPE -- what this listing does NOT establish
================================================================================

  * It does not prove the artifact INSTALLS or IMPORTS. It enumerates what is in
    the archive; it does not `pip install` it into a clean environment and import
    aquacal. Nothing in this phase's criteria asks for that.
  * It does not prove PyPI will ACCEPT it. Name/version collision, metadata
    validation and the required-reviewer gate on the `pypi` environment are all
    plan 29.2-06's subject.
  * It does not pin the file set for the future. It observes today's set. Until
    a MANIFEST.in or an sdist exclude exists, a future dependency change can
    alter it silently and only a repeat of this check would notice.
  * It is valid for THIS build. Per D-29.2-28b the rehearsal is re-run
    immediately before the merge; this listing should be re-derived from that
    run's artifact, not carried forward from this one.
