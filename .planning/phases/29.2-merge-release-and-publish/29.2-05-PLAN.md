<task type="checkpoint:decision" gate="blocking">
  <name>Task 3: Take the merge door — merge commit, never a squash</name>
  <reversibility rating="one-way">The merge pushes to a branch other systems read, and it immediately fires the release workflow, the version tag and the publish chain with no pause between them. A wrong merge method cannot be corrected without rewriting published history on an unprotected branch, and a correct one cannot be un-fired.</reversibility>
  <decision>Given the evidence assembled in Task 1, merge the pull request now with a merge commit, or hold?</decision>
  <context>
This is the door everything after it depends on, and it is the one with a silent failure mode.

**The failure mode.** All three merge methods are enabled on this repository, and the interface's
split button defaults to whichever method was last used by that account in that browser. A squash
collapses every commit on the branch into a single message, and the release tool parses only that
message: if it reads as a documentation change, **no release fires at all**, there is no tag, no
error and no notification. The rehearsal measured this contrast directly. The command-line form that
names the method explicitly cannot be overridden, which is why it is the recommended mechanism.

**What fires, and in what order.** The merge commit pushes to the default branch; the release
workflow's guard passes on the merge commit's own message and it runs; it writes the version into
both version files, generates the changelog, commits, tags and pushes using the personal access
token; that release commit re-fires the workflow and is suppressed by the guard, which has correctly
suppressed the loop on every cut in this repository's history; and the tag push fires the publish
workflow, which runs its own test and build jobs, uploads to the test index, and then **waits** on
the required-reviewer gate before the production index. Nothing reaches the production index without
a further press, which is the next plan's door.

**What a part-way failure costs: nothing.** Measured — the release tool writes the version files,
runs the build, and aborts before the commit, the tag and the push. The runner's checkout is
ephemeral, so the default branch is untouched, no tag exists and nothing is published. Fix the cause
and re-run the workflow.

**The state of the evidence.** The version assertion has been re-run against the pinned toolchain
minutes ago; the rehearsal produced the exact release commit, tag, changelog and artifact; the check
board is green on the real runners; the whole-tree hook sweep passed without rewriting a byte; and
the stale deployment has been ended. The default branch carries no protection and no ruleset, so a
red board would not have blocked this — the repairs exist so the board is green on its merits, not
so a red one can be merged past.
  </context>
