### 1. `.pre-commit-config.yaml` (config, declarative path-regex filter)

**Analog: the same file's own `detect-secrets` hook.** This is the highest-value extraction in the
phase — D-29.2-04 and D-29.2-27 both explicitly ask for "the reason at the constant, in this
shape". The shape is a comment block *immediately above* the `exclude:` line, inside the hook
mapping, that (a) names the artifact families, (b) explains **why a baseline/one-off cannot hold**,
(c) justifies each regex sub-part by name, and (d) names the future event that retires each arm.

**Current state to be edited (verbatim, `.pre-commit-config.yaml:9-17`):**

```yaml
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: trailing-whitespace
        exclude: ^\.planning/
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files
        args: ['--maxkb=1000']
```

Note `trailing-whitespace` **already carries `^\.planning/`** and pre-commit allows **exactly one
`exclude` per hook** — this is why D-29.2-02b folds the `.planning/` arm into the new alternation
by hand rather than adding a second key. `end-of-file-fixer` currently has none.

**The rationale-block shape to copy (verbatim, `.pre-commit-config.yaml:24-54`):**

### 3. `tests/unit/test_optim_common.py` L1452-1500 (test, numeric comparison)

**Analog: `tests/unit/test_datasets.py:955-973`.** This is a near-perfect match and is the house
idiom D-29.2-08 should be expressed in — the *same phenomenon* (1-2 ULP, Windows-captured anchors
failing on Linux), already solved once, with the reason written at the constant.

**The house tolerance-with-reason idiom (verbatim, `tests/unit/test_datasets.py:958-973`):**

```python
# Tolerance for every frozen-anchor comparison below.
#
# These anchors were captured on Windows. Compared with assert_array_equal
# (exact float equality) they failed on the Linux CI runner by 1-2 ULP --
# 5.55e-17 absolute, 3.4e-16 relative -- in the tvec columns only, with rvec
# untouched. That is the centroid re-centring sum reassociating under a
# different BLAS/libm, not a change in the generator. It went unseen because
# the last Linux publish run predates the phase-19.3 regeneration of these
# anchors.
#
# rtol=1e-12 is ~4 orders of magnitude above observed platform noise and ~10
# orders below any real algorithmic change (the 19.3 regeneration moved tvec
# by centimetres), so this still fails loudly if the generator drifts. Do NOT
# tighten it back to exact equality: bit-identity across platforms is not a
# property this generator has.
_ANCHOR_RTOL = 1e-12
```

**The five-part structure to copy** (this is the template for D-29.2-08's docstring rewrite):

1. **What the constant governs**, one line.
2. **The measurement** — the observed gap in absolute *and* relative terms, and *which columns*.
3. **The mechanism** — "That is X, not a change in the generator." (Here: NumPy's SIMD array path
   vs. its scalar path on the *same* machine — D-29.2-06 — **not** a Windows-pinned constant. The
   plan must state the correction, since the D4 todo's framing is wrong for this member.)
4. **Why the chosen value, in orders of magnitude both ways** — headroom above noise, and how far
   below a real change. (Here: `maxulp=4`/`8` are ~4× the measured 1/2, and still ~9 orders of
   magnitude tighter than the forbidden `pytest.approx` default `rtol=1e-6` — RESEARCH §Q2c's table
   gives the exact figures: 8 ULP = 1.110e-16 absolute, 1.04e-15 relative.)
5. **An explicit DO-NOT**, aimed at the next reader who will want to tighten or loosen it.

**Two caveats when copying it:**
- `_ANCHOR_RTOL` is a **module-level constant with the comment above it**. The D4 fix lives inside
  one method, so the natural home is the method docstring (which D-29.2-08 requires be rewritten
  anyway) plus a short inline comment at each of the two changed assertions.
- `test_datasets.py` uses `rtol`; **`rtol` is explicitly rejected here** (RESEARCH §Q2c: 1 ULP maps
  to a relative size anywhere in `[eps/2, eps]`, so any single `rtol` is up to 2× loose). Copy the
  *documentation shape*, not the mechanism.

**The code to be changed (verbatim, `tests/unit/test_optim_common.py:1452-1459` and `1493-1500`):**

```python
    def test_detail_sink_recomputed_geometry_matches_projector(self):
        """h_q/h_c/r_q must be the projector's own quantities, not an approximation.

        Recomputed here from `refractive_geometry.py:661,675,676-679` verbatim and
        compared with `==`, never `pytest.approx` -- a tolerance would pass on a
        sink that had drifted to a different (but nearby) formula.
        """
```

```python
            r_q = np.sqrt(dx * dx + dy * dy)

            assert row["h_c_m"] == h_c, row
            assert row["h_q_m"] == h_q, row
            assert row["r_q_m"] == r_q, row
            assert row["chord_incidence_deg"] == np.degrees(
                np.arctan2(r_q, h_c + h_q)
            ), row
```

Per D-29.2-07 the **first two lines keep `==` unchanged** (0/22 mismatches). Only the last two
convert. `np` is already imported in the module; `np.testing.assert_array_max_ulp` needs no new
import.

**Two house conventions visible in the surrounding method that the replacement must preserve:**
- **Every assertion carries `, row` as its message** — the failing row dict is printed. The
  `assert_array_max_ulp` call cannot take a message argument, so the plan must decide how to keep
  the row visible (e.g. wrap, or assert on the returned ULP array). RESEARCH §Q2a notes the
  function **returns the per-element ULP difference array**, which is the natural way to keep the
  observed gap in the failure output — and is D-29-16's "report both numbers" applied to an
  assertion.
- **Assertion messages in this file explain what a failure would mean**, not what failed — e.g.
  `"the view is entirely flagged or entirely clean; the index spaces coincide and the test proves
  nothing"` (L1420-1423). Match that register.

**Repo-wide comparison idiom census** (so the planner knows what is and is not house style):
`np.testing.assert_allclose` is pervasive (~180 call sites across 17 test modules, usually with an
explicit `atol=`); `np.testing.assert_array_equal` is the exact-equality idiom;
**`assert_array_max_ulp` and `assert_array_almost_equal_nulp` appear nowhere in `tests/` today.**
This will be the first use — so the docstring is carrying more weight than usual, and
`tests/synthetic/test_guard_inertness.py:20,160` shows the *counter*-idiom the codebase has written
down twice ("Exact equality only — `==` / `np.testing.assert_array_equal`. Never a tolerance."),
which is precisely the policy sentence D-29.2-08 says must be replaced with a *reason* here. Do not
touch `test_guard_inertness.py`; its policy is correct for its own subject.
