## Decisions Made

- **Pin both packages, not one.** PSR declares `gitpython~=3.0`, so pinning only PSR still resolves the broken GitPython; and PSR's latest release predates the removal with its fix open and unmerged, so pinning only GitPython leaves no working PSR to pair with. Only naming both closes it.
- **Do the merge simulation in a `/tmp` clone rather than the working repository.** Required twice over: PSR refuses to release on a branch outside its `(main|master)` release group, and the working repository has no local `main` and must not gain one.
- **Gate the whole rehearsal on a string-equality check of `git remote get-url origin`.** A clone of a local repository inherits that repository's path as `origin`, and `semantic-release version` pushes. The gate runs before any PSR invocation; PSR additionally ran with `GH_TOKEN`/`GITHUB_TOKEN` stripped and `--no-vcs-release`.
- **Read the pins out of the workflow by `grep` rather than retyping them** (D-29.2-28b), and additionally diff the clone's merged `release.yml` against the file they were grepped from. Both came back identical, so the rehearsal tested CI's toolchain rather than the planner's memory.
- **Leave the scratch root in place.** Plan 29.2-05 re-runs against `/tmp/aquacal-29.2-rehearsal`, and D-29.2-28b requires that re-run because the upstream GitPython situation is live.

**1. [Rule 1 - Bug] The plan's prescribed Finding-1 detection assertion does not detect Finding 1**

- **Found during:** Task 2 (step 4, building the pinned venv)
- **Issue:** The plan states "assert `semantic-release --version` exits 0. That single assertion is what Finding 1 costs to detect." Measured against a control venv holding the broken GitPython 3.1.60, `semantic-release --version` prints `semantic-release, version 10.6.1` and **exits 0** — `--version` never loads the config and so never reaches `config.py:745`. A CI smoke test built on that assertion would pass while the release still died. A second, compounding fact: on a branch outside PSR's release group, `semantic-release version --print` **also** exits 0 (with a refusal message), because PSR short-circuits on the branch check before constructing the runtime context that reads the missing attribute.
- **Fix:** The detecting assertion was identified, executed and recorded: `semantic-release version --print` on a branch named `main` → exit code **1**, `::ERROR:: type object 'Actor' has no attribute 'name_email_regex'`. The rehearsal now carries both the pinned run and the unpinned control, on both branch kinds, so the pin is demonstrated load-bearing rather than assumed.
- **Files modified:** `29.2-release-rehearsal.txt` (§ 4b and § "Three things this run measured that the plan and the research did not")
- **Verification:** Four measurements transcribed with exit codes; `hasattr(git.Actor, 'name_email_regex')` printed `False` for 3.1.60 and `True` for 3.1.59.

**2. [Rule 3 - Blocking] The first full release invocation aborted at `build_command`**

- **Found during:** Task 2 (step 8)
- **Issue:** `semantic-release version --no-vcs-release` failed with `CalledProcessError: Command '['bash', '-c', 'python -m build']' returned non-zero exit status 1` and `Build failed, aborting release`.
- **Fix:** Cause read from the installed source rather than guessed — PSR runs `build_command` through `bash -c` with a curated environment that forwards the **caller's** `PATH` verbatim (`semantic_release/cli/commands/version.py:278`). This shell's `python` is the anaconda base interpreter, which has no `build` module. **This is a rehearsal-harness defect, not a repository or `release.yml` defect**: on the runner, `actions/setup-python` puts its interpreter first on `PATH` and `pip install ... build` installs into that same interpreter. No workflow change was made. The clone's tree was reset with a targeted `git checkout -- CHANGELOG.md CITATION.cff pyproject.toml` (three named files, inside `/tmp`, no blanket reset and no `git clean`), the earlier manual build output was removed so `dist/` could only hold `build_command`'s own product, and the release was re-run with the venv's bin first on `PATH`.
- **Files modified:** `29.2-release-rehearsal.txt` (§ "One deviation, recorded rather than hidden")
- **Verification:** The abort state was captured and matches RESEARCH § Q6f's prediction to the letter — HEAD still the merge commit, the three version files modified in the working tree, `git tag --list v2.1.0` empty, fake-remote ref count 0. The re-run then completed and produced the full artifact set.
- **Committed in:** `efcc7bc`

**3. [Rule 3 - Blocking] The sdist member-set assertion is locale-dependent**

- **Issue:** The plan's expected string, `LICENSE,PKG-INFO,README.md,pyproject.toml,setup.cfg,src,`, is C-collation order. Under this machine's `LANG=en_US.UTF-8`, `sort -u` yields `LICENSE,PKG-INFO,pyproject.toml,README.md,setup.cfg,src,` — the same set, a different order — and the assertion fails against a perfectly healthy artifact.
