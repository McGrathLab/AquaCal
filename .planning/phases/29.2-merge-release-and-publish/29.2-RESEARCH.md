## Summary

Almost every question in the brief was answerable by **execution rather than recall**, so the
confidence here is unusually high. A `--no-hardlinks` clone of the repo was placed in scratch, the
PR merge was simulated in it with a real merge commit, and `python-semantic-release` was run against

repository, no branch was created or switched in it, `pre-commit run --all-files` was never invoked
against it, and no Zenodo write was attempted.

The headline is that **the release pipeline's arithmetic is correct and its plumbing is broken.**
The bump really is exactly `2.1.0`; the merge-commit requirement really is load-bearing (a `docs:`
squash yields "No release will be made"); the sdist really is clean; the tag→publish chain really
does fire across the PAT. But `release.yml` installs an unpinned toolchain that, as of 2026-08-25,
cannot start; the `pre-commit` job has a third failing hook nobody has counted; and the exclude
pattern chosen to protect the byte-sensitive artifacts protects none of the ones actually at risk
from `trailing-whitespace`.

All three are cheap to fix and all three are **found before any irreversible act**, which is
precisely what D-29.2-24's prepare/verify split exists to buy. The one-way doors themselves are in
better shape than expected: the half-way-failure mode turns out to be benign (PSR aborts before
commit/tag/push), the changelog can be previewed exactly, and the sdist that would reach PyPI has
been built and listed.

**Primary recommendation:** treat the phase as *four* CI repairs (pre-commit ×3, release.yml pin ×1)
plus the D4 assertion, then run the merge-and-release rehearsal in a throwaway clone as the single
go/no-go gate before the author touches Merge — the rehearsal simultaneously proves the bump, the
changelog, the tag, and the sdist.

### Q1.0 — Config: two of the repo's keys do not mean what they look like

`[VERIFIED: semantic_release/cli/config.py:361-384 read this session]`

`RawConfig` declares exactly these fields (verbatim from source):

```python
class RawConfig(BaseModel):
    assets: List[str] = []
    branches: Dict[str, BranchConfig] = {"main": BranchConfig()}

    ...
    commit_parser: NonEmptyString = "conventional"
```

and `BranchConfig` (verbatim, `config.py:250-253`):

```python
class BranchConfig(BaseModel):
```

Two consequences:

1. **`branch = "main"` in `pyproject.toml` is a dead key.** There is no `branch` field on

2. **`commit_parser` is unset, so it defaults to `"conventional"`** in PSR 10 (in PSR 9 the default

### Q1a — Does PSR traverse merge commits' parents? **YES — and the merge-commit requirement is load-bearing.**

Simulated the real PR merge in the clone: `git merge --no-ff` of `results/rerun-freeze-02` into a
local `main` at `origin/main` (`d27bda7`). First-parent-only from `v2.0.1` is **2 commits**; full

| Scenario | `semantic-release version --print` |
|---|---|
| **Merge commit** (`--no-ff`, `Merge pull request #99 from …`) | **`2.1.0`** ✅ |
| Squash, subject `docs(results): land the rerun-freeze-02 run artifacts (#99)` | **`2.0.1`** + *"No release will be made, 2.0.1 has already been released!"* |
| Squash, subject `feat(results): …` | `2.1.0` |

`[VERIFIED: executed in scratch clone]`

the correct approach.


### Q1d — The dry-run invocation: **`semantic-release version --print`. `semantic-release version --noop` is INVALID.**

`[VERIFIED: executed; and semantic_release/cli/commands/version.py:317-331, main.py:79 read this session]`

| Form | PSR 10.6.1 result |
|---|---|
| `semantic-release version --print` | ✅ prints the next version, exits 0, **mutates nothing** |
| `semantic-release version --print-tag` | ✅ prints `v2.1.0` instead of `2.1.0` |
| **`semantic-release version --noop`** | ❌ **`Error: No such option '--noop'`** |
| `semantic-release --noop version` | ✅ valid — `--noop` is a **group-level** flag on the `semantic-release` command, not on `version` |

**D-29.2-18 names `semantic-release version --print` (or `--noop`).** The `--print` form is correct.
The parenthetical `--noop` form, *written in that order*, is rejected outright by click. The plan
must use `--print` (or move the flag: `semantic-release --noop version`). Belt-and-braces is
`semantic-release --noop version --print`.

Non-mutation verified directly after the `--print` run: `git status --porcelain` empty and
`git tag --list v2.1.0` empty.

Provenance of the flag names across majors, for the record: `--print` and `--print-tag` are `version`
subcommand flags introduced in PSR v8's CLI rewrite and present through v10; `--noop` has been a

## Q2 — numpy ULP comparison

**Version under test: numpy 2.4.3** (the interpreter this repo runs on locally) and **2.5.2**
(current latest). `[VERIFIED: python -c "import numpy; print(numpy.__version__)"]`

> Note for the planner: the brief says the pinned numpy is 2.4.6; the **measured** local version is
> **2.4.3**. Tagged `[ASSUMED]` either way — see §Assumptions Log A1. It does not affect the
> recommendation, because the mechanism has been stable for many years (§Q2d).

### Q2a — Exact semantics

`[VERIFIED: inspect.getsource(np.testing.assert_array_max_ulp) read this session]`

```python
def assert_array_max_ulp(a, b, maxulp=1, dtype=None):
    ret = nulp_diff(a, b, dtype)
    if not np.all(ret <= maxulp):
        raise AssertionError("Arrays are not almost equal up to %g "
                             "ULP (max difference is %g ULP)" %
                             (maxulp, np.max(ret)))
    return ret
```

- **The bound is INCLUSIVE** — `ret <= maxulp`. `maxulp=1` passes a 1-ULP gap.
  `[VERIFIED: assert_array_max_ulp(0.10681280743540097, 0.10681280743540099, maxulp=1)` returns
  `array([1.])`; `maxulp=0` raises `Arrays are not almost equal up to 0 ULP (max difference is 1 ULP)`]
- **Default `maxulp=1`** — so an unqualified call is already a 1-ULP bound, not an exact-equality check.
- **It returns the per-element ULP difference array.** This is genuinely useful: the test can capture
  it and report the observed gap, which is exactly the "report both numbers, not only the flattering
  one" pattern (D-29-16) applied to a numeric assertion.
- **Scalars are wrapped, not rejected.** `nulp_diff` does `x = np.array([x], dtype=t)`
  unconditionally, so a scalar pair returns shape `(1,)` and a 2-element list pair returns shape
  `(1, 2)`. Harmless for `np.all`, but do not index the return value assuming it mirrors the input shape.
- The error message names the observed max — good failure ergonomics.

### Q2b — Sign, zero-crossing, and the `arctan2`/`degrees` output

`nulp_diff` maps each float to a **sign-magnitude integer** via `integer_repr`
(`rx = x.view(int64); rx[rx < 0] = -2**63 - rx[rx < 0]`) and takes `|Δ|`. That is the standard
Dawson "comparing floating point numbers" transform, and it is *correct across zero and across sign*.
`[VERIFIED: numpy/testing/_private/utils.py `_integer_repr`/`integer_repr` read this session]`

Measured `[VERIFIED: executed]`:

| Pair | ULP diff |
|---|---|
| `(0.0, -0.0)` | `0` ✅ |
| `(0.0, 5e-324)` (smallest subnormal) | `1` ✅ |
| `(1e-300, -1e-300)` | `2.37e17` (correct — they really are that far apart in ULP terms) |
| `(-1.0, 1.0)` | `9.21e18` |
| `(nan, nan)` | `0` |
| `(nan, 1.0)` | huge → fails |
| `(inf, inf)` | `0` |

**For `chord_incidence_deg` this is exactly the behavior wanted.** It is
`np.degrees(np.arctan2(r_q, h_c + h_q))` — a strictly positive quantity of order 10⁰–10¹ degrees,
nowhere near zero or a sign change, so the transform is in its simple regime and 1 ULP is just the
spacing at that magnitude. The measured 2-ULP worst case (D-29.2-07) is the inherited `r_q`
perturbation amplified by at most one rounding in each of `arctan2` and `degrees` — which is
precisely 1 (inherited) + up to 1 (the two library calls) = 2. **The measurement is consistent with
the mechanism**, which is a good sign that D-29.2-06's diagnosis is right.

### Q2c — Against the alternatives

`pytest.approx` is FORBIDDEN by D-29.2-08 and is not considered. Comparing the two permitted
alternatives:

| Idiom | Verdict |
|---|---|
| **`np.testing.assert_array_max_ulp(actual, expected, maxulp=N)`** | ✅ **Recommended.** Scale-free, exact, inclusive, returns the observed gap, ships with numpy, and expresses the intent ("≤ N representable steps") in the units the phenomenon actually occurs in. |
| `math.ulp`-based manual bound (`abs(a-b) <= N*math.ulp(expected)`) | Workable and dependency-free, but `math.ulp(x)` is the spacing **at x**, and `a` and `b` can straddle a binade boundary where the spacing doubles. Then `N*ulp(expected)` is either half or twice the intended bound depending on which operand you pass. It also loses the observed-gap report. Reimplements a solved problem — see §Don't Hand-Roll. |
| `assert_allclose(..., rtol=tiny)` | ❌ **Cannot express "N ULP".** 1 ULP corresponds to a *relative* size anywhere in `[eps/2, eps] = [1.110e-16, 2.220e-16]` depending on position within the binade. Any single `rtol` is therefore up to **2× loose or 2× tight** — and being 2× loose is the failure mode D-29.2-08 exists to prevent. It also has an `atol` defaulting to 0 which interacts confusingly near zero. |

**Concrete recommendation, satisfying D-29.2-08 and the discretion note:**

```python
# r_q_m: measured worst gap 1 ULP over 22 rows (D-29.2-07). Bound = 4 ULP.
np.testing.assert_array_max_ulp(row["r_q_m"], r_q, maxulp=4)

# chord_incidence_deg: inherits r_q through arctan2/degrees; measured worst 2 ULP.
np.testing.assert_array_max_ulp(
    row["chord_incidence_deg"], np.degrees(np.arctan2(r_q, h_c + h_q)), maxulp=8
)
```

`h_c_m` and `h_q_m` keep `==` (0/22 mismatches — D-29.2-07).

**Why 4 and 8 rather than 1 and 2.** The discretion note asks for "modest headroom … with the bound
re-derived in CI's own environment rather than pinned to this machine's". CI runs ubuntu **and**
windows × 3.11/3.12 on runners whose numpy SIMD dispatch we do not control, and the whole diagnosis
(D-29.2-06) is that the gap *is* a dispatch artifact. A bound equal to the locally-measured maximum
would be pinned to this machine by construction — the exact mistake the note warns about. 4× and 4×
headroom is the smallest step that is clearly not a local pin.

**And it remains an extraordinarily tight assertion.** At the measured value `0.10681280743540097`,
1 ULP is `1.388e-17`; so `[VERIFIED: computed via math.ulp]`

| Bound | absolute | relative | vs. `pytest.approx` default `rtol=1e-6` |
|---|---|---|---|
| 1 ULP | 1.388e-17 | 1.30e-16 | 7.7e9 × looser |
| **4 ULP** | **5.551e-17** | **5.20e-16** | **1.9e9 × looser** |
| **8 ULP** | **1.110e-16** | **1.04e-15** | **9.6e8 × looser** |

So `maxulp=8` is still **~9 orders of magnitude** tighter than the forbidden `pytest.approx`
default — confirming D-29.2-08's "~10 orders of magnitude" characterisation with the exact number,
and preserving the docstring's guarantee that a drifted-to-a-different-formula sink is still caught.

**A note on the tempting alternative the planner may consider and should reject.** One could
"fix" the test by making it recompute `r_q` *vectorized* (matching `refractive_geometry.py:676`)
so exact equality is restored. That is more fragile, not less: identical SIMD dispatch depends on
array length and memory alignment, so the test would pass by coincidence on this machine and could
break on a runner with different vector width. The ULP bound is the more honest instrument, and
D-29.2-05/08 are right to choose it.

**Docstring update required by D-29.2-08** — the current text says the comparison is `==`, "never
`pytest.approx`", as policy. It must instead state the scalar-vs-vectorized reason **at the
constant**, i.e. that the library evaluates `r_q` vectorized over N points while the test evaluates
it scalar on one, that NumPy's array and scalar paths may differ by ≤1 ULP on the same machine
(D-29.2-06), and that the bound is a hard ULP count precisely so that a changed formula still fails.

### Q2d — Availability and stability

`assert_array_max_ulp` and `assert_array_almost_equal_nulp` are long-standing public members of
`numpy.testing`, present and identical in **2.4.3** and **2.5.2**, and they survived the NumPy 2.0
namespace cleanup (which removed much of `numpy.testing`'s private surface but retained these).

### Q6f — What if semantic-release fires but stops half-way? **Measured. It is benign.**

Encountered accidentally and then measured deliberately: the build step failed (missing `build`
module) and PSR reported *"Build failed, aborting release"*. State immediately afterwards
`[VERIFIED: executed]`:

```
HEAD           : d459122 (the merge commit — UNCHANGED)
tag v2.1.0     : (empty)
git status     :  M CHANGELOG.md   M CITATION.cff   M pyproject.toml
remote refs    : unchanged
```

So PSR's order is: **compute version → write the version into the three files → run `build_command`
→ commit → tag → push → (GitHub release)**. A build failure aborts **after the working-tree writes
but before the commit, the tag and the push.**

**Recovery: none needed.** The runner's checkout is ephemeral, `main` is untouched, no tag exists,
nothing was published. Fix the cause and re-run the workflow. This is the good case, and it means
the most likely half-way failure is fully recoverable.

**The genuinely awkward window** is narrow and later: if the push of the commit+tag partially
succeeds, or `publish.yml` fails *after* TestPyPI upload but before PyPI. TestPyPI is not
load-bearing for the paper, and the PyPI step is behind the human approval gate — so nothing
irreversible happens without a press. See §Risks.

## Common Pitfalls

### Pitfall 1: Trusting an unpinned CI toolchain on a one-way-door step
**What goes wrong:** `pip install <tool>` in a release workflow resolves differently every run. A
transitive dependency released *yesterday* can break it.
**Why it happens:** release workflows run rarely, so the drift accumulates invisibly between cuts.
**How to avoid:** pin the release toolchain; run the dry-run with the *same* pins.
**Warning signs:** the last successful release was weeks ago; the workflow has no lockfile.
**Status here:** 🔴 **realised** — Finding 1.

### Pitfall 2: Assuming an exclude pattern covers the files you care about because it covers a lot of files
**What goes wrong:** 593 matched files feels conclusive; the 10 that matter are elsewhere.
**Why it happens:** the pattern was validated against the *artifact* tree, and the byte-sensitive
driver-state files live one directory up from it.
**How to avoid:** derive the exclude from the hook's *actual rewrite set*, not from the artifact
inventory. Set-subtract, don't spot-check.
**Status here:** 🔴 **realised** — Finding 2.

### Pitfall 3: Counting the blockers you already know about
**What goes wrong:** `pre-commit run --all-files` has never been run, so *every* hook is an unknown —
but only the two hooks with known-bad files were analysed.
**How to avoid:** enumerate all hooks and measure each, including the ones you expect to pass. Four
of seven did pass; measuring them is what makes that a fact.
**Status here:** 🔴 **realised** — Finding 3.

### Pitfall 4: A flag that exists in a neighbouring position
**What goes wrong:** `semantic-release version --noop` looks right, is documented in *some* PSR
majors' idiom, and fails with `No such option`.
**How to avoid:** verify flags against the installed version's own `--help`, not memory.
**Status here:** caught before use — Q1d.

### Pitfall 5: Asserting on a proxy instead of the property
**What goes wrong:** D-29.2-17 says assert the sdist size "is in line with 1.8.0's". 2.1.0's sdist is
1.7× larger for legitimate reasons; that assertion fails on a healthy artifact.
**How to avoid:** assert the member list (the actual property); record size as corroboration.

### Pitfall 6: The merge button remembers
**What goes wrong:** all three merge methods are enabled and GitHub defaults the split button to the
last method *you* used. A squash yields `2.0.1` and "No release will be made" — silently.
**How to avoid:** `gh pr merge --merge`, or positively select "Create a merge commit"; then verify
two parents on `origin/main`.

| # | Step | What can go wrong | Recovery |
|---|---|---|---|
| 0 | **Editing `.pre-commit-config.yaml`** | Exclude too narrow → `--all-files` rewrites byte-sensitive artifacts locally | **Full.** Reversible by two lines (D-29.2-01). The D-29.2-03 proof exists to catch it; if it fires, `git checkout -- .` restores. **Run the proof on a clean tree so the restore is unambiguous.** |

| 2b | 🚪 Merge to `main`, red CI | Nothing mechanically blocks it (D-29.2-22, and no rulesets either) | The merge itself is fine; a red `test` job means `publish.yml`'s own `test` gate will fail later and nothing reaches PyPI. Not a data risk — a wasted cycle. |
| 3 | 🚪 **`release.yml` fires** | **Toolchain cannot start (Finding 1)** | **Full and clean.** Fails before touching anything. Fix the pin, re-run the workflow. |
| 3b | 🚪 `semantic-release version` | Build step fails half-way | **Full, no cleanup.** Measured: version files written in the ephemeral checkout, **no commit, no tag, no push** (§Q6f). |
| 3c | 🚪 Tag `v2.1.0` pushed | Wrong version cut (e.g. 3.0.0 or 2.0.2) | **Poor.** A pushed tag can be deleted, but `publish.yml` fires immediately on the tag push and may reach TestPyPI first. **This is exactly what D-29.2-18's `== 2.1.0` assertion prevents**, and it is now proven to yield `2.1.0`. |
| 3d | 🚪 `RELEASE_TOKEN` expired | `actions/checkout` fails at step 1 | Full — regenerate the PAT, re-run. Loud failure. |
| 4 | 🚪 **TestPyPI upload** | Version already exists → HTTP 400 | N/A — `2.1.0` is free on TestPyPI `[VERIFIED]`. If it ever happened, TestPyPI is not paper-load-bearing. |
